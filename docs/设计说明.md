# 设计说明

> 技术栈：Java 17 + MySQL 8.0 + JSqlParser 5.3 + Jackson + HikariCP + JUnit 5。
> 本文说明项目为什么这样设计、各模块如何协作、关键决策与已知局限。
> 完成流程图：[build-process.html](build-process.html)（下载到本地用浏览器打开）。

---

## 1. 项目目标

输入一条 `SELECT`，输出：

1. **为什么慢**：执行计划 + AST 特征，定位全表扫描、索引失效、回表、filesort、临时表、深分页；
2. **该建什么索引**：按"等值 → 范围 → 排序 → 覆盖"生成 DDL，并与现有索引比对；
3. **优化前后差多少**：同一连接、预热 2 次、正式 3 次取中位数，同时记录 `Handler_read_*` 差值。

---

## 2. 架构与模块

```
SQL 文本
   │
   ├─► SqlAnalyzer (JSqlParser) ──► SqlFeatures
   │      tables / eq / range / join / order / group
   │      functionWrapped / leadingWildcard / or / cartesian / limit
   │
   ├─► ExplainCollector ──► EXPLAIN FORMAT=JSON + SHOW WARNINGS
   │      └─► ExplainParser (Jackson 递归) ──► ExplainPlan / TableAccess
   │
   ├─► TableMetaLoader ──► information_schema
   │      columns / indexes / cardinality / row count
   │
   ├─► RuleEngine ──► 10 条规则 ──► List<Issue>
   │
   ├─► IndexAdvisor ──► List<IndexSuggestion>
   │
   └─► ReportGenerator ──► Markdown + HTML
```

| 包 | 职责 |
|---|---|
| `parse` | 解析 SQL 为 AST 特征；只支持单条 `PlainSelect` |
| `collect` | 采集并解析 EXPLAIN JSON；`SessionStats` 读 Handler 计数 |
| `meta` | 从 `information_schema` 读表、列、索引、Cardinality |
| `rule` | 规则接口、引擎、10 条规则 |
| `advise` | 索引列序、覆盖索引、现有索引比对 |
| `bench` | 预热 + 多次测量的中位数 |
| `report` | Markdown / HTML 报告 |
| `slowlog` | 慢日志解析、归一化、指纹聚合 |
| `service` | `DiagnosisService` 编排一次完整诊断 |
| `tools` | `SeedData` 造数、`BaselineRunner` 基线采集 |

## 3. 运行时序

### 3.1 默认诊断（`Main` 无参数或传 SQL）

1. `Main.runAnalyze`：`AppConfig.load()` → `new Db(config)` → `getConnection()`。
2. `DiagnosisService.analyze`：
   1. `SqlAnalyzer.analyze`：JSqlParser 解析**人写的 SQL**，产出 `SqlFeatures`；不是 `PlainSelect` 直接拒绝。
   2. `ExplainCollector.collect`：发 `EXPLAIN FORMAT=JSON` + `SHOW WARNINGS`；`ExplainParser` 用 Jackson 解析 **MySQL 返回的 JSON**，产出 `ExplainPlan`。`EXPLAIN` 不执行原 SQL。
   3. `plan.remapTableNames`：用 `SqlFeatures` 的别名映射把 `u` / `o` 还原成 `t_user` / `t_order`。不还原的话，后面 `tables.get(alias)` 查不到元数据，规则和建议会被跳过。
   4. `TableMetaLoader.load(conn, currentSchema)`：查 `information_schema`，加载**该 schema 下所有表**，不是只加载当前 SQL 涉及的表；`TABLE_ROWS` / `CARDINALITY` 是估算，Cardinality 只有索引列才有。
   5. `new QueryContext(sql, features, plan, tables)`。
   6. `RuleEngine.analyze`：10 条规则，去重后按严重度排序；单条规则异常只记日志。
   7. `IndexAdvisor.advise`：独立从 `QueryContext` 生成建议，**不消费 `Issue`**；笛卡尔积直接返回空。
   8. `Benchmark.measure`：`measure=true` 且非笛卡尔积才执行；2 次预热 + 3 次正式，`SessionStats` 记录前后 Handler 差值。
   9. 返回 `AnalysisResult`（含 `measurement`）。
3. `Main` 打印 PLAN / ISSUES / SUGGESTIONS / measure，再调 `ReportGenerator.write` 写 Markdown + HTML 到 `docs/reports/`。

### 3.2 其他入口

- `Main bench "SQL"`：只做 `Benchmark`，不跑 AST、规则、建议、报告。
- `Main slowlog file`：只做 `SlowLogParser` + `SlowLogAggregator`，不连数据库。
- `SeedData` / `BaselineRunner`：独立工具，用 `DriverManager` 直连，不经过 `AppConfig` / `Db`；改了环境变量它们不认。

### 3.3 前置顺序

```text
00_init.sql（建库/建账号）→ 01_schema.sql（建表）→ SeedData（造数）→ Main（诊断）
```

`01_schema.sql` 里有 `DROP TABLE`，造数后不要重跑；`00_init.sql` 不能省，否则建表会报 `Unknown database`。

### 3.4 一句话版

```text
Main → AppConfig/Db → DiagnosisService
  → SqlAnalyzer（人写的 SQL）
  → ExplainCollector/ExplainParser（MySQL 的 JSON）
  → remapTableNames → TableMetaLoader
  → QueryContext → RuleEngine / IndexAdvisor
  → Benchmark → AnalysisResult
  → Main 打印 + ReportGenerator
```

`EXPLAIN` 只拿计划，不执行 SQL；真正执行和计时的是 `Benchmark`。

## 4. 关键设计决策

### 4.1 为什么用 JSqlParser，而不是正则

要判断"列被函数包裹""OR 两侧""前导通配""别名归属""IN 列表"，正则不可靠；AST 才有稳定的结构。JSqlParser 纯 Java、AST 模型直观，5.3 对 MySQL 语法覆盖够用。

### 4.2 为什么用 `EXPLAIN FORMAT=JSON`

单表时 `table` 在 `query_block` 下；JOIN 时在 `nested_loop[]`；排序/分组时在 `ordering_operation` / `grouping_operation` 里。表格 EXPLAIN 丢失层级，JSON 才能递归解析出完整结构。

### 4.3 为什么同时看 `Handler_read_*`

`rows` 是优化器估算，可能受统计信息、数据倾斜影响。`Handler_read_*` 是会话级实际计数，执行前后差值能证明"实际读了多少行/索引项"。报告里两个都列，简历里的"扫描行数下降"用后者。

### 4.4 为什么规则引擎用接口 + 独立类

每条规则可单测、可开关、可解释；单条规则抛异常只记日志，不影响整体。`if-else` 会变成一个几百行、无法单测的函数。

### 4.5 为什么只生成 DDL 不执行

DDL 会占元数据锁、影响写入、可能改变其他查询的计划。工具只输出 SQL + 风险提示，人工确认后再执行。

### 4.6 索引建议的列序

1. JOIN 列 + 等值列，按选择性（`Cardinality / TABLE_ROWS`）降序；
2. 范围列最多 1 个，放在等值列之后；
3. 有范围列时不再追加排序列（索引顺序已被范围打断）；
4. SELECT 列可覆盖时追加为覆盖索引（最多补 3 列）；
5. 候选是现有索引前缀 → 跳过；现有索引是候选前缀 → 提示可能冗余。

## 5. 构建过程

### 阶段 1：数据

- `t_user` 10 万行，`city`、`username` 有索引；
- `t_order` 100 万行，`user_id`、`order_no` 有索引；`create_time` 故意不建索引，`status` 低区分度；
- 80% 订单分给 2 万热用户（人均约 40 单），20% 分给 8 万冷用户（人均 2–3 单）。

### 阶段 2：最小闭环

`ExplainCollector` 拿 `EXPLAIN FORMAT=JSON`，`ExplainParser` 递归解析成 `ExplainPlan` / `TableAccess`；先保证"能拿到并解析执行计划"，再谈规则。

### 阶段 3：AST 特征

`SqlAnalyzer` 抽取表与别名、SELECT 列、WHERE 合取项、JOIN ON 列、ORDER/GROUP、函数包裹列、前导通配、OR、笛卡尔积、LIMIT offset、列 vs 字面量类型。

### 阶段 4：规则

10 条规则：全表扫描、索引未命中、函数失效、隐式转换、前导通配、OR 失效、回表、filesort/临时表、深分页、笛卡尔积。

### 阶段 5：索引建议

`TableMetaLoader` 读元数据，`IndexAdvisor` 生成 DDL；`ExplainPlan.remapTableNames` 用 AST 别名映射把 EXPLAIN 里的 `u` / `o` 还原成真实表名。

### 阶段 6：测量与报告

`Benchmark` 预热 2 次、正式 3 次取中位数；`ReportGenerator` 输出 Markdown + HTML，包含 SQL、执行计划、问题、建议、理由/风险、实测、复现命令、已知局限。

### 阶段 7：慢日志

`SlowLogParser` 解析 FILE 格式；`SlowLogAggregator` 把字面量替换成 `?`、折叠 IN 列表、算 SHA-256 指纹，按总耗时排序。

## 6. 实测数据

数据：100 万订单 / 10 万用户；热缓存、单连接、3 次中位数。完整数据见 [`baseline.csv`](baseline.csv)、[`compare.csv`](compare.csv)。

| 场景 | 优化前 | 优化后 | 手段 |
|---|---:|---:|---|
| Q08 排序 + 全表扫描 | 254 ms / 1,000,003 Handler | 0 ms / 11 | 加 `create_time` 索引 |
| Q02 `DATE(create_time)` | 232 ms / 1,000,003 | 8 ms / 2,726 | 改写为范围 + 索引 |
| Q03 `order_no = 数字` | 395 ms / 1,000,003 | 0 ms / 2 | 字面量加引号，走已有索引 |
| Q01 等值 + 排序 | 0 ms / 41 | 0 ms / 20 | `(user_id, create_time)` 消除 filesort |
| Q14 `GROUP BY status` | 206 ms / 2,000,010 | 98 ms / 1,000,002 | `status` 索引消除临时表 |

> `0 ms` 表示小于 1 毫秒。绝对值换机器会变，看数量级和 Handler 差异。

## 7. 已知局限

- 只支持单条 `SELECT` / `PlainSelect`；子查询、UNION、CTE、窗口函数未覆盖；
- `rows` 是估算值，报告同时给 `Handler_read_*` 实测；
- 索引建议基于规则，不保证优化器一定采用；DDL 需人工确认；
- 选择性优先用 `STATISTICS.CARDINALITY`，没有统计信息的列会退化为经验值；
- 慢日志解析按分号切分，字符串/注释里带分号会误判；
- 测量是热缓存、单连接、无并发，生产环境要重新测。

## 8. 复现

```bash
mysql -u root -p < db/00_init.sql
mysql -u sqlquery -p slow_sql_lab < db/01_schema.sql
mvn -q -DskipTests compile exec:java -Dexec.mainClass=com.sqlquery.tools.SeedData
mvn -q -DskipTests compile exec:java -Dexec.mainClass=com.sqlquery.tools.BaselineRunner
mvn test
mvn -q -DskipTests package
java -jar target/slow-sql-doctor-1.0.0.jar
```
