## 0. 先定位：这个项目到底在做什么

### 0.1 一句话

**输入一条 SQL（或一份慢日志），输出"它为什么慢、该加什么索引、加了之后能快多少"的可验证报告。**

注意三个词：

- **为什么慢**：不是"没走索引"这种结论，而是"因为 `WHERE` 列被 `DATE()` 包裹，优化器无法用 `idx_create_time`"这种因果。
- **该加什么**：联合索引列序、覆盖索引、以及"这个列不该单独建索引"的反向建议。
- **可验证**：优化前后各跑 3 次取中位数，附执行计划差异，而不是嘴上说快了。

### 0.3 对你原方案的 5 处修正（重要）

| # | 原方案 | 实际 | 影响 |
|---|---|---|---|
| 1 | `CCJSqlParserUtil.parse(sql)` 后 `select.getSelectBody()` | **JSqlParser 5.x 已删除 `SelectBody`**，`PlainSelect` 直接继承 `Select` | 照抄伪代码会编译不过，见 §5.2 |
| 2 | Java 17 | 你机器是 **JDK 21** | `pom` 里用 `<release>17</release>`，运行在 21 上，兼容 |
| 3 | `rows` 当作扫描行数 | `rows` 是**估算** | 报告必须同时给 `Handler_read_*` 实测，见 §4.4 |
| 4 | 示例 `WHERE user_id=?` 是 `type=ALL` | 你的表 `user_id` **本来就有索引** | 基线要按真实表设计，见 `db/02_typical_slow_sql.sql` |
| 5 | 15 条 SQL 直接开跑 | MySQL 8.0.46 默认 `log_output=FILE`、`long_query_time=10` | 慢日志要手动开，见 §3.5 |

### 0.6 每条命令在哪里执行（第一次做项目，先读这节）

一个完整项目会同时用到 6 个"执行场所"。**先认清自己在哪，再敲命令/点按钮**，能避免 80% 的新手错误。

| 场所 | 长什么样 | 用来做什么 | 怎么打开 |
|---|---|---|---|
| PowerShell | `PS D:\personalobject\Sqlquery>` | 装软件、跑 Maven、Git、启动 jar | `Win + X` → 终端；或在文件夹地址栏输入 `powershell` 回车 |
| Git Bash | `666@PC MINGW64 /d/personalobject/Sqlquery$` | 跑 `mysql < 文件`、git | 在文件夹空白处右键 → `Git Bash Here` |
| DataGrip（推荐可视化） | 左边数据库树、中间 SQL 编辑器、下面结果表格 | 建库建表、跑 SQL、看索引、看执行计划 | 装 DataGrip → 新建 MySQL 数据源，见 §0.7 |
| MySQL 客户端（可选） | `mysql>` | 建库、建表、跑 SQL、EXPLAIN | 先 `mysql -u root -p`，登录后提示符变成 `mysql>` |
| IDEA | 图形界面，底部有 `Run` / `Terminal` | 写 Java、运行类、看报错 | `File → Open` 选项目文件夹 |
| 浏览器 / GitHub | — | 看 HTML 报告、建远程仓库 | — |

**两条路线，选一条即可：**

- **路线 A（推荐，可视化）**：SQL 全在 **DataGrip** 里做；Java 在 IDEA 里写；PowerShell 只负责装 Maven 和 Git。
- **路线 B（纯命令行）**：SQL 在 `mysql>` 里做，其余同上。

两条路线结果完全一样；本文后面同时标了两种做法。

**先认识几个词（后面会一直出现）：**

| 名词 | 白话解释 | 在你项目里对应什么 |
|---|---|---|
| 项目根目录 | 整个项目最外层的文件夹 | `D:\personalobject\Sqlquery` |
| 包（package） | 给类分组的"文件夹"，要和代码里的 `package` 行一致 | `com.sqlquery.rule` |
| 类（class） | 一个 `.java` 文件里的代码单元 | `ExplainParser.java` |
| 依赖（dependency） | 别人写好的库，Maven 自动下载 | JSqlParser、HikariCP |
| 编译（compile） | 把 `.java` 翻译成机器能跑的 `.class` | `mvn compile` |
| 运行（run） | 执行类里的 `main` 方法 | 点绿色 ▶ |
| 终端（terminal） | 敲命令的窗口 | PowerShell / IDEA 底部 Terminal |
| 仓库（repository） | 被 Git 管理的项目目录 | `git init` 之后 |
| 提交（commit） | 给当前代码拍一张快照 | `git commit` |

**三句话记住：**

1. **看清自己在哪。** `PS ...>` 是 Windows 命令行；`mysql>` 是数据库命令行；`$` 是 Git Bash；DataGrip 是图形窗口，没有提示符。
2. **项目根目录 = `D:\personalobject\Sqlquery`。** 现在里面有 `docs`、`db`；做完 §2 会多出 `pom.xml`、`src`。
3. **命令里的 `db/00_init.sql` 是相对路径**，只在项目根目录执行才找得到；不在就先 `cd` 进去。

**进入项目根目录：**

PowerShell：

```powershell
cd D:\personalobject\Sqlquery
Get-Location          # 应输出 D:\personalobject\Sqlquery
```

Git Bash：

```bash
cd /d/personalobject/Sqlquery
pwd                   # 应输出 /d/personalobject/Sqlquery
```

IDEA：底部 `Terminal` 默认就在项目根目录；`Run` 窗口是程序输出，不是命令行。

**三个必踩的坑：**

- **PowerShell 不支持 `<` 重定向。** `mysql ... < db\00_init.sql` 会报 "The '<' operator is reserved for future use"。用 §1.3 的 `source` 写法（推荐），或改用 Git Bash，或 `cmd /c "mysql -u root -p < db\00_init.sql"`。
- **在 `mysql>` 里敲系统命令。** `mvn`、`cd`、`dir` 都不是 SQL，会报语法错误；先输入 `exit` 退出 MySQL 客户端。
- **SQL 忘写分号。** 提示符变成 `->` 就是在等你继续输入；补一个 `;` 回车即可。

**本文的 📍 标记**：每个需要敲命令的地方，前面都会写一行 `📍 在哪执行 · 当前目录`。**没有 📍 的代码块是"要写进文件里的代码"，不是命令。**

**再补一条总规则（记不住 📍 时看这条）：**

- 看到 **SQL**（`SELECT` / `ALTER` / `SHOW` / `EXPLAIN` / `SET`）→ 在 `mysql>` **或 DataGrip 的 console** 里执行（见 §0.7）。
- 看到 **Java** 代码 → 在 IDEA 里新建对应类，粘进去，点绿色 ▶ 运行。
- 看到 `mvn` / `git` / `java -jar` → 在**项目根目录**的 PowerShell / Git Bash / IDEA Terminal 执行。
- 看到改文件（`pom.xml`、`SeedData.java`、`.gitignore`）→ 在 IDEA 里改，别在命令行里 `echo`。

### 0.7 可视化路线：用 DataGrip 代替 mysql 命令行（推荐）

可以，而且第一次做项目用 DataGrip 更友好：能看表结构、看索引、结果表格化、执行计划有面板。**DataGrip 不影响项目代码**，它只是替换"手工跑 SQL"这一环；Java 仍然在 IDEA 里写。

**先解决授权：**

- DataGrip 是收费的，但 **学生可以免费**（JetBrains Student Pack，用学校邮箱申请）。
- 没有学生认证就 30 天试用。
- 已经有 **IDEA Ultimate** 的话，它自带 Database 工具，不用另装 DataGrip。
- 实在不想装：**DBeaver Community** 免费，操作逻辑类似。

#### 1）建连接

1. 打开 DataGrip → 左侧/右侧 `Database` 工具窗 → `+` → `Data Source` → `MySQL`。
2. 填：
   - Host：`localhost`
   - Port：`3306`
   - User：先填 `root`（要执行 `00_init.sql`），密码是安装 MySQL 时设的
   - Database：root 先留空；建库后填 `slow_sql_lab`（`sqlquery` 连接直接填 `slow_sql_lab`，表就在这个库）
3. 第一次会提示 `Download missing driver files`，点下载。
4. 点 `Test Connection`，出现绿色对勾即可。
5. `Apply` → `OK`。

> 连不上时：
> - 报 `Public Key Retrieval is not allowed`：在 `Advanced` 里加 `allowPublicKeyRetrieval=true`。
> - 报时区/`unrecognized time zone`：在 `Advanced` 里加 `connectionTimeZone=Asia/Shanghai`。
> - 报 `Access denied`：用户名/密码错，或账号没有从 `localhost` 连接的权限。

#### 2）执行 SQL 文件（对应 CLI 的 `source`）

1. `File → Open` → 选 `db/00_init.sql`（或把文件拖进窗口）。
2. 编辑器上方选择刚才的数据源（root）。
3. **全选**（`Ctrl + A`）→ `Ctrl + Enter` 执行。
4. 底部 `Services` 窗口会显示每条语句的结果和耗时；有红字就是报错。

> ⚠️ 不要用 `source db/00_init.sql;`——那是 MySQL 命令行客户端自己的命令，DataGrip 不认识（会当普通 SQL 报错）。DataGrip 里就是"打开文件 → 全选 → 执行"。

#### 3）看表结构和索引（对应 `SHOW TABLES` / `SHOW INDEX`）

左侧数据库树展开：`slow_sql_lab` → `tables` → `t_order`。

- 双击表：看数据（分页）。
- 右键表 → `Modify Table`：在 `Indexes` 标签页看/加索引、看列定义。
- 右键表 → `SQL Scripts → Generate DDL to Query Console`：看建表语句。
- 部分版本支持 `Diagrams → Show Visualization` 看表关系图，有就点开。

#### 4）看执行计划（对应 `EXPLAIN`）

1. 在 SQL 编辑器里选中一条 `SELECT`（或把光标放在语句上）。
2. 工具栏点 `Explain Plan`（或右键 → `Explain Plan`）。
3. 下方出现执行计划表格；如果面板顶部有 `Show Visualization`，可以切成图形化计划。
4. 截图可以直接放进 README 的"优化前后对比"。

> `Explain Analyze`（如果菜单里有）会**真的执行** SQL。Q12（笛卡尔积）只能 `Explain Plan`，不要 `Explain Analyze`。

#### 5）执行单条 vs 整个文件

- 光标放在某条语句上 → `Ctrl + Enter`：只执行这一条。
- 选中多条 → `Ctrl + Enter`：执行选中的部分。
- 全选 → `Ctrl + Enter`：执行整个文件。`00_init.sql`、`01_schema.sql` 可以；`02_typical_slow_sql.sql` **不行**，会跑到 Q12。

#### 6）和命令行操作的对应表

| 命令行（`mysql>`） | DataGrip 里 |
|---|---|
| `source db/00_init.sql;` | 打开文件 → 全选 → `Ctrl + Enter` |
| `USE slow_sql_lab;` | 连接的默认库选 `slow_sql_lab`，或执行 `USE` |
| `SHOW TABLES;` | 左侧 schema 树展开 |
| `SHOW INDEX FROM t_order;` | 双击表 → `Indexes` 标签 |
| `EXPLAIN ...` | 选中 SQL → `Explain Plan` |
| `exit` | 关闭 console 标签页 |
| 看耗时 | `Services` 窗口每条语句的耗时 |

**建议**：日常用 DataGrip，但至少亲手在 `mysql>` 里跑一次 `source` 和 `EXPLAIN`——面试问"你平时怎么连库"时，你能说清底层发生了什么，而不是只会点按钮。

## 1. 环境：缺什么、怎么补

### 1.1 体检结果

| 组件 | 状态 | 说明 |
|---|---|---|
| JDK | ✅ 21.0.7 | `C:\Program Files\Java\jdk-21`，但 `JAVA_HOME` 未设置 |
| MySQL | ✅ 8.0.46 | 服务 `MySQL80` 运行中，端口 3306；`mysql.exe` 不在 PATH |
| Maven | ❌ 未安装 | winget 源里没有 `Apache.Maven`，需手动装 |

### 1.2 装 Maven（手动，最稳）

📍 **在哪执行**：PowerShell（普通用户，不需要管理员）· 任意目录（脚本里用的是绝对路径）。

以**普通用户**打开 PowerShell，逐段执行：

```powershell
# 1) 设 JAVA_HOME（当前用户，永久）
[Environment]::SetEnvironmentVariable('JAVA_HOME','C:\Program Files\Java\jdk-21','User')
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'

# 2) 下载并解压 Maven 3.9.16 到 D:\tools
New-Item -ItemType Directory -Force D:\tools | Out-Null
Invoke-WebRequest 'https://dlcdn.apache.org/maven/maven-3/3.9.16/binaries/apache-maven-3.9.16-bin.zip' -OutFile D:\tools\maven.zip
Expand-Archive D:\tools\maven.zip -DestinationPath D:\tools -Force

# 3) 把 Maven 和 MySQL 的 bin 加进用户 PATH（已存在则不重复加）
$add = @('D:\tools\apache-maven-3.9.16\bin','D:\MySQL\MySQL Server 8.0\bin')
$old = [Environment]::GetEnvironmentVariable('Path','User')
foreach ($p in $add) { if ($old -notlike "*$p*") { $old = "$old;$p" } }
[Environment]::SetEnvironmentVariable('Path', $old, 'User')
```

**关掉所有终端，重新开一个**（IDEA 也要重启，否则读不到新的 `PATH`/`JAVA_HOME`），验证：

📍 **在哪执行**：新开的 PowerShell · 任意目录

```bash
mvn -v      # 期望：Apache Maven 3.9.16 / Java version: 21.0.7
mysql --version  # 期望：Ver 8.0.46 for Win64
```

> 如果 `mvn -v` 报 "JAVA_HOME not set"：说明第 1 步没生效，`echo %JAVA_HOME%` 检查，重新开终端。
>
> 如果下载慢：换 `https://mirrors.aliyun.com/apache/maven/maven-3/3.9.16/binaries/apache-maven-3.9.16-bin.zip`。

### 1.3 建库和账号

📍 **在哪执行**：PowerShell 或 Git Bash · **项目根目录** `D:\personalobject\Sqlquery`。

**方法 A（命令行路线，PowerShell 也能用）：先登录，再用 `source` 执行文件。**

```powershell
cd D:\personalobject\Sqlquery
mysql -u root -p
```

输入 root 密码后，提示符会变成 `mysql>`。这时**在 `mysql>` 里**输入：

```sql
source db/00_init.sql;
```

看到 `Query OK` 后输入 `exit` 退出。`source` 是 MySQL 客户端命令，路径用 `/` 或 `\\` 都行。

**方法 B（Git Bash / cmd 专用）：用输入重定向。**

```bash
mysql -u root -p < db/00_init.sql
```

> ⚠️ PowerShell 不支持 `<`，会报 "The '<' operator is reserved"。别在 PowerShell 里用方法 B。

**方法 C（DataGrip，可视化首选）：** 按 §0.7 用 root 建好连接 → `File → Open` 打开 `db/00_init.sql` → 全选 → `Ctrl + Enter`。执行完在左侧树刷新，应该看到 `slow_sql_lab`。

**验证（任意目录，`mysql` 已在 PATH 里；DataGrip 里则在 console 执行同一句）：**

```bash
mysql -u sqlquery -p -e "USE slow_sql_lab; SELECT CURRENT_USER(), DATABASE();"
```

> 连不上时先看服务：PowerShell 里 `Get-Service MySQL80`，状态不是 `Running` 就 `Start-Service MySQL80`（可能需要管理员权限）。

> **为什么不用 root 跑应用**：最小权限原则；Web 版只挂 `sqlquery_ro`。
> 这句话面试可以直接说，是加分项。

表设计（面试会问"为什么这么设计"）：

| 表 | 行数 | 索引 | 故意留的坑 |
|---|---|---|---|
| `t_user` | 10 万 | PK、`idx_city`、`idx_username` | 无 |
| `t_order` | 100 万 | PK、`idx_user_id`、`idx_order_no` | `create_time` 无索引、`status` 低区分度、`user_id` 分布倾斜 |

### 3.2 分布要倾斜，否则测不出"区分度"

目标：**20% 的用户贡献 80% 的订单**。

```java
long userId = (r.nextDouble() < 0.8)
        ? 1 + r.nextInt(20_000)          // 2 万热用户，吃 80% 订单
        : 20_001 + r.nextInt(80_000);    // 8 万冷用户，吃 20% 订单
```

如果均匀分布，`WHERE user_id = ?` 永远只命中 10 行，你根本讲不出"选择性"的故事。

算一下量级：80 万单分给 2 万热用户 ≈ **40 单/人**；20 万单分给 8 万冷用户 ≈ **2.5 单/人**。所以头部用户是 **40–70 单**，不是"几万单"——整体仍是 20% 用户占 80% 订单的温和倾斜。

### 3.3 造数程序（可直接用）

👉 先别急着复制：这个类要建在 `src/main/java/com/sqlquery/tools/SeedData.java`，怎么建、怎么运行，见代码块下方。

```java
package com.sqlquery.tools;

import java.math.BigDecimal;
import java.sql.*;
import java.time.LocalDateTime;
import java.util.Random;

public class SeedData {
    static final String URL = "jdbc:mysql://localhost:3306/slow_sql_lab"
            + "?rewriteBatchedStatements=true"
            + "&connectionTimeZone=Asia/Shanghai"
            + "&characterEncoding=utf8&useSSL=false";
    static final String USER = "sqlquery";
    static final String PASS = "Sqlquery@2026";

    static final String[] CITIES = {"杭州","上海","北京","深圳","成都","武汉","南京","广州","西安","苏州"};
    static final LocalDateTime BASE = LocalDateTime.of(2025, 10, 1, 0, 0);

    public static void main(String[] args) throws Exception {
        Random r = new Random(42);
        try (Connection c = DriverManager.getConnection(URL, USER, PASS)) {
            c.setAutoCommit(false);
            seedUsers(c, r, 100_000);
            seedOrders(c, r, 1_000_000);
            c.commit();
        }
    }

    static void seedUsers(Connection c, Random r, int n) throws SQLException {
        String sql = "INSERT INTO t_user(username, city, age, created_at) VALUES (?,?,?,?)";
        long t0 = System.currentTimeMillis();
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 1; i <= n; i++) {
                ps.setString(1, (i % 3 == 0) ? "张" + i : "user" + i);
                ps.setString(2, CITIES[r.nextInt(CITIES.length)]);
                ps.setInt(3, 18 + r.nextInt(43));
                ps.setTimestamp(4, Timestamp.valueOf(BASE.plusSeconds(r.nextInt(365 * 86400))));
                ps.addBatch();
                if (i % 5_000 == 0) ps.executeBatch();
            }
            ps.executeBatch();
        }
        System.out.println("users done: " + (System.currentTimeMillis() - t0) + " ms");
    }

    static void seedOrders(Connection c, Random r, int n) throws SQLException {
        String sql = "INSERT INTO t_order(user_id, order_no, amount, status, remark, create_time) "
                   + "VALUES (?,?,?,?,?,?)";
        long t0 = System.currentTimeMillis();
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 1; i <= n; i++) {
                long uid = (r.nextDouble() < 0.8)
                        ? 1 + r.nextInt(20_000)
                        : 20_001 + r.nextInt(80_000);
                ps.setLong(1, uid);
                ps.setString(2, "ORD" + (10_000_000L + i));
                ps.setBigDecimal(3, BigDecimal.valueOf(1 + r.nextInt(10_000))
                        .add(BigDecimal.valueOf(r.nextInt(100)).divide(BigDecimal.valueOf(100))));
                ps.setInt(4, r.nextInt(6));
                ps.setString(5, r.nextInt(10) == 0 ? "加急" : null);
                ps.setTimestamp(6, Timestamp.valueOf(BASE.plusSeconds(r.nextInt(365 * 86400))));
                ps.addBatch();
                if (i % 5_000 == 0) {
                    ps.executeBatch();
                    if (i % 100_000 == 0) System.out.println("orders: " + i);
                }
            }
            ps.executeBatch();
        }
        System.out.println("orders done: " + (System.currentTimeMillis() - t0) + " ms");
    }
}
```

**执行顺序（别弄反）：先删索引 → 再跑程序 → 最后加回索引。**

**第 1 步：删二级索引**（让插入快 2~3 倍）
📍 MySQL 客户端 · `sqlquery` 账号 · 任意目录

```sql
ALTER TABLE t_order DROP INDEX idx_user_id, DROP INDEX idx_order_no;
```

**第 2 步：在 IDEA 里运行 `SeedData`**
- 文件路径：`src/main/java/com/sqlquery/tools/SeedData.java`。右键 `com.sqlquery` 包 → `New → Package` → 输入 `tools`；再右键 `tools` → `New → Java Class` → 输入 `SeedData`，把上面的代码粘进去（包名要对）。
- 先确认 `db/01_schema.sql` 已执行（表存在），否则报 `Table 'slow_sql_lab.t_user' doesn't exist`。
- 运行：打开 `SeedData.java`，点 `main` 左边的绿色 ▶ → `Run 'SeedData.main()'`。
- 成功标志：`Run` 窗口出现 `users done: ... ms`、`orders: 100000` …、`orders done: ... ms`，没有红色异常。
- `Communications link failure`：MySQL 没开，或密码/端口不对，回 §1.3 验证。

**第 3 步：把索引加回来（忘了这步，后面所有基线和建议都会错）**

### 3.4 验收数据

📍 **在哪执行**：`mysql>` 里（已 `USE slow_sql_lab;`）· 任意目录；或 DataGrip 的 console。

> DataGrip：把下面四条粘进 console，**逐条** `Ctrl + Enter`，结果直接在表格里看；`COUNT` 的数字就是验收标准。

```sql
SELECT COUNT(*) FROM t_user;                              -- 100000
SELECT COUNT(*) FROM t_order;                             -- 1000000
SELECT COUNT(DISTINCT user_id) / COUNT(*) FROM t_order;   -- ≈ 0.10
SELECT user_id, COUNT(*) c FROM t_order GROUP BY user_id ORDER BY c DESC LIMIT 5;
```

最后一条应看到**头部用户约 40–70 单、冷用户 1–3 单**，整体 `COUNT(DISTINCT user_id)/COUNT(*)` ≈ 0.09–0.10。这是"20% 用户占 80% 订单"的温和倾斜，不是"一个用户几万单"。

### 3.5 开启慢日志

📍 **在哪执行**：`mysql>` 里，先用 **root** 登录（`mysql -u root -p`），再 `USE slow_sql_lab;`；或 DataGrip 里用 **root 连接**的 console。

> DataGrip：在 `Database` 面板再建一个 root 数据源（或把当前连接的用户临时改成 root），执行三条 `SET GLOBAL`；验证时切回 `sqlquery` 连接查 `mysql.slow_log`。

> 这三条要**用 root 执行**（`SYSTEM_VARIABLES_ADMIN`）。`sqlquery` 只拥有 `slow_sql_lab` 的权限，读 `mysql.slow_log` 的 `SELECT` 已在 `00_init.sql` 里单独授权。

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.1;          -- 100ms 以上都记
SET GLOBAL log_output = 'TABLE';           -- 写 mysql.slow_log，好查
```

验证：

```sql
SELECT @@slow_query_log, @@long_query_time, @@log_output;
SELECT start_time, query_time, rows_examined, LEFT(sql_text, 120)
FROM mysql.slow_log ORDER BY start_time DESC LIMIT 10;
```

> 注意：
> - `SET GLOBAL` **重启失效**。要持久化就改 `D:\MySQL\MySQL Server 8.0\my.ini` 的 `[mysqld]` 段：
>   `slow_query_log=1`、`long_query_time=0.1`、`log_output=FILE`、`slow_query_log_file=...`。
> - `mysql.slow_log` 是 **CSV 引擎**表，不支持事务，别在里面 UPDATE。
> - 演示用完记得关掉，否则磁盘会被写满：`SET GLOBAL slow_query_log = OFF;`。

### 3.6 16 条基线 SQL（自动采集，D2）

📍 **在哪执行**：项目根目录 Terminal（PowerShell / IDEA Terminal）。这一步**不需要**在 DataGrip 里手工跑 16 条。

> `db/02_typical_slow_sql.sql` 是 **16 条独立查询的清单**，不是一键执行脚本。打开阅读即可；批量基线用下面的 `BaselineRunner`，不要 `source` 整个文件。

**先说清楚：为什么你做到这里会觉得乱。** 这一段原来把四件事混在一起：

1. `EXPLAIN` 看计划；
2. 同一连接跑 3 次计时；
3. `Handler_read` 前后差值；
4. 把 16 行填进 CSV。

手工做是 16 条 × 5 次 = 80 次执行，第一次做项目必乱。所以改成自动化：项目里已经放了 `BaselineRunner`。

#### 第一步：一条命令生成基线

```bash
mvn -q -DskipTests compile exec:java -Dexec.mainClass=com.sqlquery.tools.BaselineRunner
```

它会：

- 对 16 条 SQL 逐条 `EXPLAIN`，记录 `type / key / rows / Extra`；
- 预热 2 次，正式 3 次，取中位耗时；
- 用 `SHOW SESSION STATUS LIKE 'Handler_read%'` 的前后差值算真实读取量；
- **Q12 只 `EXPLAIN`，绝不执行**；
- 覆盖写入 `docs/baseline.csv`。

看到 16 行输出和 `written: .../docs/baseline.csv` 就成功。

> 末尾可能出现 `mysql-cj-abandoned-connection-cleanup` 的 WARNING，可以忽略，不影响 CSV。
> 改完索引后**不要直接重跑**，否则会覆盖原始基线；先把 `baseline.csv` 复制成 `baseline-before.csv`。

#### 第二步：抽查 3 条，确认你会读

自动跑完不等于看懂。挑 Q01、Q02、Q08：

## 4. 采集层：EXPLAIN + 真实扫描行数

### 4.1 为什么必须用 `FORMAT=JSON`

传统 `EXPLAIN` 是给人看的表格；JSON 是给程序看的树，含：

- `cost_info.query_cost`
- 每个表的 `access_type`、`possible_keys`、`key`、`rows_examined_per_scan`、`filtered`、`used_columns`、`attached_condition`
- `ordering_operation.using_filesort`
- `grouping_operation.using_temporary_table`

单表时结构是 `query_block.table`；**JOIN 时变成 `query_block.nested_loop[].table`**，多表还可能嵌套 `ordering_operation`。所以解析必须**递归**，不能按固定路径取（原方案的示例 JSON 只适合单表）。

### 4.2 采集代码骨架

```java
public final class ExplainCollector {

    public ExplainPlan collect(Connection conn, String sql) throws SQLException {
        ExplainPlan plan;
        try (Statement st = conn.createStatement();
             ResultSet rs = st.executeQuery("EXPLAIN FORMAT=JSON " + sql)) {
            rs.next();
            plan = ExplainParser.parse(rs.getString(1));
        }
        // 8.0 会在这里给出改写后的 SQL（Note 1003），报告里可以展示
        try (Statement st = conn.createStatement();
             ResultSet rs = st.executeQuery("SHOW WARNINGS")) {
            while (rs.next()) {
                if (rs.getInt("Code") == 1003) plan.setRewrittenSql(rs.getString("Message"));
            }
        }
        return plan;
    }
}
```

> **安全**：只对 `SELECT` 调 `EXPLAIN`。`EXPLAIN UPDATE/DELETE` 不执行语句本身，但你的解析链路未必能处理，先拒绝。
> `EXPLAIN ANALYZE` 会**真的执行**，默认不要用；要做也必须加超时。

### 4.3 递归解析 JSON

```java
public final class ExplainParser {
    private static final ObjectMapper M = new ObjectMapper();

    public static ExplainPlan parse(String json) throws JsonProcessingException {
        ExplainPlan plan = new ExplainPlan();
        walk(M.readTree(json), plan);
        return plan;
    }

    private static void walk(JsonNode node, ExplainPlan plan) {
        if (node.isObject()) {
            if (node.has("table")) {
                plan.addTable(toTableAccess(node.get("table")));
            }
            if (node.path("using_filesort").asBoolean(false)) plan.setUsingFilesort(true);
            if (node.path("using_temporary_table").asBoolean(false)) plan.setUsingTemporary(true);
            node.fields().forEachRemaining(e -> walk(e.getValue(), plan));
        } else if (node.isArray()) {
            node.forEach(child -> walk(child, plan));
        }
    }

    private static TableAccess toTableAccess(JsonNode n) {
        TableAccess t = new TableAccess();
        t.setTableName(n.path("table_name").asText());
        t.setAccessType(n.path("access_type").asText());
        t.setKey(n.path("key").isMissingNode() || n.path("key").isNull()
                ? null : n.path("key").asText());
        t.setRowsExamined(n.path("rows_examined_per_scan").asLong(0));
        t.setRowsProduced(n.path("rows_produced_per_join").asLong(0));
        t.setFiltered(n.path("filtered").asDouble(100.0));
        n.path("possible_keys").forEach(k -> t.getPossibleKeys().add(k.asText()));
        n.path("used_columns").forEach(k -> t.getUsedColumns().add(k.asText()));
        t.setAttachedCondition(n.path("attached_condition").asText(null));
        return t;
    }
}
```

**验收**：把 `db/02` 里的 Q01 和 Q11 的 EXPLAIN JSON 存成文件，单测断言：

- Q01：`tables.size() == 1`，`usingFilesort == true`
- Q11：`tables.size() == 2`，第一张是 `t_user`，第二张是 `t_order`

### 4.4 `rows` 是估算：拿 `Handler_read_*` 做实测

```sql
SHOW SESSION STATUS LIKE 'Handler_read%';
```

返回 7 个计数器，**同一条连接**上，执行 SQL 前后各取一次，差值相加 ≈ 实际读了多少行/索引项：

| 变量 | 含义 |
|---|---|
| `Handler_read_first` | 读索引第一项次数 |
| `Handler_read_key` | 按索引键读行次数 |
| `Handler_read_next` | 索引范围扫描的下一行 |
| `Handler_read_prev` | 反向索引扫描 |
| `Handler_read_rnd` | 按固定位置读行（排序后回表常见） |
| `Handler_read_rnd_next` | **全表扫描读下一行**（这个最能说明问题） |

```java
public final class SessionStats {
    public static long handlerReads(Connection c) throws SQLException {
        long sum = 0;
        try (Statement st = c.createStatement();
             ResultSet rs = st.executeQuery("SHOW SESSION STATUS LIKE 'Handler_read%'")) {
            while (rs.next()) sum += rs.getLong(2);
        }
        return sum;
    }
}
```

**报告里写**：

- `EXPLAIN rows` = 优化器估算（per scan）
- `Handler_reads` = 本次执行实际读的行/索引项（含内部操作，不是精确值）

这句话本身就是面试点："估算可能偏差，所以用实际耗时和 Handler 计数做佐证。"

## 5. 解析层：JSqlParser 抽特征

### 5.1 为什么不能正则

`WHERE date(create_time)='...'` 和 `WHERE remark='date(create_time)'` 用正则都会误判；注释、大小写、子查询、同名列、`OR` 嵌套更处理不了。
AST 能告诉你"这个 `Column` 是不是 `Function` 的参数"——这是正则做不到的。

### 5.2 JSqlParser 5.x 的 API 变化（必看）

```java
// 4.x 写法（原方案伪代码，5.x 编译不过）
Select select = (Select) CCJSqlParserUtil.parse(sql);
PlainSelect ps = (PlainSelect) select.getSelectBody();   // ← 5.x 没有 getSelectBody()

// 5.x 写法
Statement stmt = CCJSqlParserUtil.parse(sql);
if (!(stmt instanceof PlainSelect ps)) throw new UnsupportedSqlException("暂不支持");
```

5.x 里 `PlainSelect`、`SetOperationList`、`ParenthesedSelect` 都直接继承 `Select`。
访问器也变成了泛型：`ExpressionVisitorAdapter<T>`，方法签名是 `<S> T visit(Function f, S context)`。

> 面试可以说："我看的是 5.3 的源码，4.x 到 5.x 重构了 Select 体系，网上很多教程还是 4.x 写法。"
> 这句话证明你不是复制粘贴。

### 5.3 特征模型

```java

    private String normalizedSql;
```

### 5.4 抽取逻辑（骨架）

```java
public SqlFeatures analyze(String sql) throws JSQLParserException {
    Statement stmt = CCJSqlParserUtil.parse(sql);
    if (!(stmt instanceof PlainSelect ps)) throw new UnsupportedSqlException("only PlainSelect");
    SqlFeatures f = new SqlFeatures();

    // 1) 表与别名
    addTable(f, ps.getFromItem());
    if (ps.getJoins() != null) for (Join j : ps.getJoins()) addTable(f, j.getRightItem());

    // 2) SELECT 列
    for (SelectItem<?> item : ps.getSelectItems()) {
        Expression e = item.getExpression();
        if (e instanceof AllColumns) f.setSelectStar(true);
        else collectColumns(e, f.getSelectColumns());
    }

    // 3) WHERE：只把"顶层 AND 的合取项"当作可索引条件
    Expression where = ps.getWhere();
    if (where != null) {
        List<Expression> conjuncts = new ArrayList<>();
        flattenAnd(where, conjuncts);          // OR 整体算一个合取项
        for (Expression e : conjuncts) classify(e, f);
    }

    // 4) JOIN ON：只取被驱动表（右表）侧的列
    if (ps.getJoins() != null) {
        for (Join j : ps.getJoins()) {
            if (j.getOnExpressions() == null) { f.setCartesianJoin(true); continue; }
            for (Expression on : j.getOnExpressions()) { addJoinColumns(on, j, f); }
        }
    }

    // 5) ORDER BY / GROUP BY
    if (ps.getOrderByElements() != null)
        for (OrderByElement o : ps.getOrderByElements()) collectColumns(o.getExpression(), f.getOrderColumns());
    if (ps.getGroupBy() != null)
        collectColumns(ps.getGroupBy().getGroupByExpressionList(), f.getGroupColumns());

    // 6) LIMIT
    if (ps.getLimit() != null) f.setLimitRows(number(ps.getLimit().getRowCount()));
    if (ps.getOffset() != null) f.setLimitOffset(number(ps.getOffset().getOffset()));

    f.setNormalizedSql(stmt.toString());
    return f;
}
```

`flattenAnd` 的精髓：

```java
void flattenAnd(Expression e, List<Expression> out) {
    if (e instanceof AndExpression and) { flattenAnd(and.getLeftExpression(), out); flattenAnd(and.getRightExpression(), out); }
    else out.add(e);   // OR、括号、单个比较，都算一个合取项
}
```

`classify` 的思路：

```java
if (e instanceof EqualsTo eq)                 -> eqColumns.add(columnOf(eq.getLeftExpression()))
else if (e instanceof InExpression in)        -> eqColumns.add(columnOf(in.getLeftExpression()))
else if (e instanceof Between b)              -> rangeColumns.add(...)
else if (e instanceof GreaterThan || GreaterThanEquals || MinorThan || MinorThanEquals) -> rangeColumns
else if (e instanceof LikeExpression like)    -> 若右值是 '...%' 开头 → leadingWildcard=true
else if (e instanceof OrExpression)           -> hasOr=true; 两侧分别 visit 收集列
```

### 5.5 函数包裹列怎么判

```java
Set<String> wrapped = new LinkedHashSet<>();
if (ps.getWhere() != null) {
    ps.getWhere().accept(new ExpressionVisitorAdapter<Void>() {
        @Override
        public <S> Void visit(Function fn, S ctx) {
            if (fn.getParameters() != null) {
                for (Expression p : fn.getParameters()) {
                    if (p instanceof Column c) wrapped.add(c.getColumnName());
                }
            }
            return super.visit(fn, ctx);   // 继续递归，别漏嵌套函数
        }
    }, null);
}
```

> 只做了浅层判断（`date(col)` 能抓，`date(ifnull(col,''))` 抓不到）。
> 这个局限写进 README，面试时主动说，比被问出来好。

### 5.6 隐式转换怎么判（要查表元数据）

`WHERE order_no = 202610180001` 里，`order_no` 是 `varchar`，右值是数字 → MySQL 把**列**转成数字比较 → 索引失效。

```sql
SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_SET_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'slow_sql_lab' AND TABLE_NAME = 't_order';
```

规则：`DATA_TYPE` 是字符型，而 AST 右值是 `LongValue/DoubleValue` → 报"隐式转换"。
反向（数字列 = 字符串）在 MySQL 里是转常量，索引通常**不失效**，别误报——这是常见误报点，面试可以讲。

### 5.7 解析失败怎么办

- `catch (JSQLParserException)` → 降级为"只做 EXPLAIN 诊断"，报告里标注"AST 解析失败，仅执行计划可用"。
- 不要直接抛异常终止：慢日志里一定会有怪 SQL（`/* */`、hint、方言）。
- 单测里放 3 条怪 SQL，验证降级路径。

### 6.2 10 条规则的判定与误报点

| ID | 问题 | 判定（AST + 计划） | 典型误报 / 注意 |
|---|---|---|---|
| R01 | 全表扫描 | `access_type=ALL` 且 `rows_examined` 超过阈值 | 小表全扫是合理的；阈值按行数不按时间 |
| R02 | 索引未命中 | `possible_keys` 非空 且 `key` 为空 | `possible_keys` 可能为 null（统计信息缺失） |
| R03 | 函数导致失效 | `functionWrappedColumns` 命中 WHERE 列 | 函数作用在常量上不是问题 |
| R04 | 隐式类型转换 | 字符列 vs 数字字面量 | 数字列 = 字符串**不**失效，别误报 |
| R05 | 前导通配 | `LIKE` 右值以 `%` 开头 | `LIKE 'abc%'` 是合法的范围扫描 |
| R06 | OR 失效 | 顶层 `OR` 且至少一侧列无索引 | MySQL 8 可能用 index merge，需看实际 `key` |
| R07 | 回表 | `access_type in (ref,range)` 且 SELECT 列不在 `key` 的索引列中 | 覆盖索引判断要看 `used_columns` |
| R08 | 临时表/文件排序 | `using_temporary_table` / `using_filesort` | 小结果集 filesort 很快，别一律标 HIGH |
| R09 | 深分页 | `LIMIT offset, n` 且 offset 大 | 阈值（如 > 1 万）写进配置，别硬编码 |
| R10 | 隐式笛卡尔积 | JOIN 无 ON，或 FROM 多表无 WHERE 连接条件 | `CROSS JOIN` 是显式意图，可排除 |

## 7. 索引建议：算法、比对、风险

### 7.1 列序规则（先背结论，再理解）

1. **等值列**（`=`、`IN`）在前；
2. 等值列内部按**区分度从高到低**；
3. **范围列**最多 1 个，放在等值列之后；
4. **排序列**放在最后——但**只要前面有范围列，排序列就基本失效**（不能靠索引消除 filesort）；
5. 总列数 ≤ 5，超过就截断；
6. SELECT 列少且小 → 追加为**覆盖索引**。

### 7.2 算法（30 行版本）

```java
public List<IndexSuggestion> advise(QueryContext ctx) {
    List<IndexSuggestion> out = new ArrayList<>();
    for (TableAccess t : ctx.plan().getTables()) {
        String table = t.getTableName();
        LinkedHashSet<String> cols = new LinkedHashSet<>();

        // 1) JOIN 关联列（被驱动表侧，本质是等值）
        cols.addAll(ctx.features().joinColumnsFor(table));
        // 2) 等值列，按选择性降序
        cols.addAll(sortBySelectivity(ctx.features().eqColumnsFor(table), table, ctx));
        // 3) 范围列，最多 1 个
        List<String> ranges = ctx.features().rangeColumnsFor(table);
        if (!ranges.isEmpty()) cols.add(ranges.get(0));
        // 4) 排序列：只在没有范围列时追加
        if (ranges.isEmpty()) cols.addAll(ctx.features().orderColumnsFor(table));

        if (cols.isEmpty()) continue;
        List<String> candidate = cols.stream().limit(5).toList();

        // 5) 已有索引比对
        ExistingIndex match = existingIndex(table, candidate, ctx);
        if (match == ExistingIndex.COVERED) continue;          // 已有前缀，跳过
        if (match == ExistingIndex.REDUNDANT_OF_EXISTING) continue;

        // 6) 覆盖索引
        boolean covering = canCover(t, candidate, ctx);

        out.add(new IndexSuggestion(table, candidate, covering, reason(...), risk(...)));
    }
    return out;
}
```

### 7.3 选择性怎么算

优先用统计信息（快、不扫表）：

```sql
SELECT TABLE_ROWS FROM information_schema.TABLES
WHERE TABLE_SCHEMA='slow_sql_lab' AND TABLE_NAME='t_order';

SELECT INDEX_NAME, COLUMN_NAME, CARDINALITY
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA='slow_sql_lab' AND TABLE_NAME='t_order';
```

`选择性 ≈ CARDINALITY / TABLE_ROWS`。
`status` 只有 6 个值 → 0.000006 → 单独建索引没意义。

统计信息可能为 `NULL` 或过期，降级方案（采样，别全表）：

```sql
SELECT COUNT(DISTINCT status) / COUNT(*) FROM (SELECT status FROM t_order LIMIT 100000) x;
```

> **面试点**：采样有偏差（前 10 万行可能都是同一批用户），所以优先 `ANALYZE TABLE` 后读 `CARDINALITY`。

### 7.4 已有索引怎么比对

```sql
SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = ? AND TABLE_NAME = ?
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

得到 `Map<索引名, List<列>>`，然后判断：

| 情况 | 结论 |
|---|---|
| 候选是某现有索引的**前缀** | 已覆盖，不建议新建 |
| 现有索引是候选的**前缀** | 候选不冗余，可建；但现有索引变成冗余前缀，**提示可评估删除**（别自动删） |
| 列相同、顺序不同 | 不冗余，顺序决定用途 |
| 现有唯一索引 = 候选 | 完全冗余，跳过 |

### 7.5 输出与风险

```sql
ALTER TABLE `t_order` ADD INDEX `idx_user_id_create_time` (`user_id`, `create_time`);
```

每条建议必须带：

- **理由**：`user_id` 等值在前、`create_time` 排序在后，一次索引扫描即可有序，消除 filesort。
- **风险**：写放大（每次 INSERT 多维护一个索引）、索引占空间、可能改变优化器对其他查询的选择、DDL 期间占用元数据锁。
- **不自动执行**：只生成 SQL，人工确认后再跑（面试官会问"你敢自动改生产库吗"）。

> 生产大表加索引的正确姿势：`pt-online-schema-change` / `gh-ost` / MySQL 8 的 Online DDL（`ALGORITHM=INPLACE, LOCK=NONE`），仍要评估主从延迟。这句话是加分项。

## 8. 对比测量：怎么让数字站得住

### 8.1 协议（写进 README，面试照这个说）

1. 同一连接、同一参数、同一 `sql_mode`；
2. **预热 2 次**（把数据和索引页读进 buffer pool）；
3. 正式跑 **3 次**，取**中位数**；
4. 每次记录：耗时（`System.nanoTime`）、`Handler_read_*` 差值、`EXPLAIN` 的 `type/key/rows/Extra`；
5. 加索引前后用**同一套流程**；
6. 报告里注明"热缓存下测得"，不吹成"生产环境提升 99%"。

### 8.2 代码骨架

```java
public record Sample(long nanos, long handlerReads) {}

public Sample runOnce(Connection c, String sql) throws SQLException {
    long h0 = SessionStats.handlerReads(c);
    long t0 = System.nanoTime();
    long rows = 0;
    try (Statement st = c.createStatement(); ResultSet rs = st.executeQuery(sql)) {
        while (rs.next()) rows++;
    }
    long nanos = System.nanoTime() - t0;
    return new Sample(nanos, SessionStats.handlerReads(c) - h0);
}

public static long median(List<Long> xs) {
    List<Long> s = new ArrayList<>(xs);
    Collections.sort(s);
    return s.get(s.size() / 2);
}
```

### 8.3 数字怎么算才诚实

- 单条 SQL 的提升：`(before - after) / before`，用**中位数**算。
- 16 条汇总：用**几何平均**或直接报"中位数提升"，别用算术平均（一条 100 倍会把均值拉飞）。
- 明确写：`rows` 是估算、`Handler_reads` 是实际计数、耗时是热缓存中位数。
- 如果某条 SQL 优化后反而变慢，**保留在报告里**并解释（比如索引选择变了）。这比全是好消息可信。

## 10. 批量模式：慢日志解析与聚合

### 10.1 FILE 格式长这样

```
# Time: 2026-10-18T10:00:00.123456+08:00
# User@Host: app[app] @ localhost []  Id: 123
# Query_time: 1.834211  Lock_time: 0.000123 Rows_sent: 20  Rows_examined: 998231
SET timestamp=1729216800;
SELECT * FROM t_order WHERE user_id = 10086 ORDER BY create_time DESC LIMIT 20;
```

### 10.2 解析状态机（简化版）

```java
for (String line : lines) {
    if (line.startsWith("# Time:")) { flush(); current = new Entry(); current.time = ...; }
    else if (line.startsWith("# Query_time:")) { parse attrs by regex; }
    else if (line.startsWith("SET timestamp=")) { /* skip */ }
    else {
        current.sql.append(line).append('\n');
        if (line.endsWith(";")) flush();   // 简化：字符串里有分号会误判
    }
}
```

> 局限要主动说：SQL 字符串里含 `;`、注释块、`#` 开头的内容都会干扰；生产级解析要按 `Query_time` 行切分 + 用解析器校验。

### 10.3 归一化与聚合（pt-query-digest 思路）

```
SELECT * FROM t_order WHERE user_id = 10086  →  SELECT * FROM t_order WHERE user_id = ?
SELECT * FROM t_order WHERE user_id IN (1,2,3) →  ... IN (?)
```

- 用 JSqlParser 解析后把字面量替换成 `?`（AST 级替换最稳；退化为正则）；
- `fingerprint = SHA-256(normalizedSql).substring(0, 16)`；
- 按 fingerprint 聚合：`count`、`sum(query_time)`、`avg`、`max`、`sum(rows_examined)`；
- **按总耗时排序**（不是平均），因为一条 0.5s 跑 1 万次比 5s 跑 1 次更值得优化。

### 10.4 另一条路（加分）

MySQL 8 自带 digest：

```sql
SELECT DIGEST_TEXT, COUNT_STAR, SUM_TIMER_WAIT/1e12 AS total_s,
       SUM_ROWS_EXAMINED, AVG_TIMER_WAIT/1e12 AS avg_s
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 20;
```

> `performance_schema` 的表也需要 `SELECT` 权限；没有授权时用 root 跑，或单独 `GRANT SELECT ON performance_schema.*`（生产慎用）。

面试时说"我用慢日志做批处理，也用 `performance_schema` 的 digest 做过对照"，可信度立刻不一样。

## 14. 25 个坑（提前避）

1. `EXPLAIN` 的 `rows` 是**估算**，别当实际扫描行数写简历。
2. `EXPLAIN ANALYZE` 会**真执行** SQL，默认别用。
3. `EXPLAIN FORMAT=JSON` 在 JOIN 时结构是 `nested_loop`，按固定路径取会 NPE。
4. 慢日志默认 `log_output=FILE`、`long_query_time=10`，不开就没有数据。
5. `SET GLOBAL` 重启失效，演示前重新开。
6. 造数均匀分布 → 测不出选择性；必须 20/80 倾斜。
7. 批量插入忘开 `rewriteBatchedStatements=true` → 100 万行跑半小时。
8. 先建索引再插 100 万行 → 慢一倍以上。
9. 时区：中文 Windows 上不配 `connectionTimeZone` 可能报 "unrecognized time zone"。
10. 字符集/排序规则不一致会让 JOIN 走隐式转换，索引失效。
11. `ONLY_FULL_GROUP_BY` 会让你的示例 SQL 直接报错（写 SQL 时注意）。
12. `mysql.slow_log` 是 CSV 引擎，不能事务、不能 UPDATE。
13. `Handler_read_*` 含内部操作，不是精确"扫描行数"，报告里要说明。
14. 加索引后 buffer pool 变热，前后对比不公平；要么都预热，要么注明。
15. 首次连接、类加载、JIT 会污染第一次计时；必须预热。
16. `LIMIT` 不影响 `rows` 估算，深分页的 `rows` 仍然很大。
17. `Using filesort` 不一定慢（结果集小、内存排序）。
18. `Using temporary` 可能是内存临时表，不一定落盘。
19. `type=index` 也是全索引扫描，不等于"用了索引就快"。
20. `possible_keys` 为 `NULL` 不代表没索引，可能是统计信息/条件写法问题。
21. 子查询、UNION 里的表不会出现在顶层 `PlainSelect`，规则会漏。
22. `ORDER BY` 可以用别名/序号，AST 里拿到的不一定是列名。
23. `information_schema` 查询在 8.0 走数据字典，频繁查会拖慢报告。
24. 控制台编码 GBK 会让中文报告乱码；统一 UTF-8。
25. 索引建议**只生成不执行**；自动改生产库是事故。
