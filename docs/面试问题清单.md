## 1. 项目与设计决策（41）

**1.1｜用一分钟说明这个工具解决什么问题、给谁用？**
`关联：项目设计 / 慢查询治理`
**答**：输入一条 SQL 或一份慢日志，输出"它为什么慢、该建什么索引、加完能快多少"的可验证报告。给两类人：没有专职 DBA 的后端/数据开发，以及需要批量治理慢 SQL 的团队。核心价值是把"看 EXPLAIN、凭经验猜、试索引"变成可复用、可解释的闭环。

**1.2｜没有你的工具，DBA 现在怎么排查慢 SQL？你的增量价值是什么？**
`关联：DBA 工作流 / 慢查询治理`
**答**：开慢日志、`pt-query-digest` 排序、逐条 `EXPLAIN`、凭经验加索引、再跑一次验证。痛点是：EXPLAIN 只说"没走索引"，不说"为什么"和"建什么"；批量场景全靠人肉。工具的增量是**归因 + 建议 + 验证**三段都自动化。

**1.3｜从输入一条 SQL 到输出报告，完整链路是什么？**
`关联：系统设计 / 数据流`
**答**：`SQL 文本 → JSqlParser 解析 AST（抽等值/范围/JOIN/排序/函数/通配）→ EXPLAIN FORMAT=JSON + SHOW WARNINGS → Handler_read 差值 → 规则引擎输出问题 → 索引建议（比对 information_schema）→ 前后各 3 次中位数 → Markdown/HTML 报告`。

**1.4｜为什么输入是 SQL 文本 + EXPLAIN，而不是直接接 APM 或监控系统？**
`关联：可观测性 / 系统设计`
**答**：APM 给的是接口级耗时和调用链，拿不到单条 SQL 的 AST 和执行计划，接入成本也高。工具的定位是"给我一条 SQL，我告诉你它为什么慢"，输入越简单越通用；慢日志是批量入口，APM 可以作为未来数据源，但不是第一版。

**1.5｜为什么选 JSqlParser？和 Druid、Calcite、自己写 ANTLR 相比取舍是什么？**
`关联：SQL 解析 / 技术选型`
**答**：JSqlParser 纯 Java、无额外依赖、AST 模型直观、MySQL 语法覆盖够用。Druid 的解析器更强但绑定连接池生态、API 偏重；Calcite 是查询优化器框架，太重；ANTLR 自写文法学习与维护成本高。个人项目选"够用 + 可读 + 能讲清楚"。

**1.6｜为什么用 `EXPLAIN FORMAT=JSON` 而不是传统表格 EXPLAIN？**
`关联：执行计划 / JSON`
**答**：表格是给人看的，字段靠字符串拼接；JSON 是树，能拿到 `cost_info`、`used_columns`、`attached_condition`，JOIN 时还有 `nested_loop` 层级。程序解析稳定，报告里也能保留结构。

**1.7｜JSON 里 `query_block`、`nested_loop`、`ordering_operation`、`grouping_operation` 的嵌套关系是什么？**
`关联：执行计划 / JSON`
**答**：`query_block` 是一个查询块；单表时 `table` 直接挂在下面；JOIN 时变成 `nested_loop` 数组，每个元素里一个 `table`；排序、分组会包一层 `ordering_operation` / `grouping_operation`，`table` 在它里面。所以必须递归遍历，不能按固定路径取。

**1.8｜一张表在 JSON 里可能出现几次？你怎么区分同一张表的不同实例？**
`关联：执行计划 / JOIN`
**答**：自连接、子查询、UNION 分支里会多次出现。每次是一个独立的 `table` 节点，用 `table_name` + `alias` 区分；报告按"节点"聚合，而不是按表名合并。

**1.9｜`rows_examined_per_scan` 和 `rows_produced_per_join` 的区别是什么？**
`关联：优化器 / 成本估算`
**答**：前者是"扫描这张表一次预计读多少行"；后者是"经过这张表的过滤后、参与后续 JOIN 的行数"，约等于前者 × `filtered%`。多表时后者更接近这一层的输出量。

**1.10｜`filtered` 的含义是什么？它和最终行数是什么关系？**
`关联：优化器 / 成本估算`
**答**：表示该表条件过滤后剩余行的百分比；`rows_examined × filtered%` ≈ 传给下一层的行数。它同样是估算值，`filtered=100` 不代表没有过滤，可能只是统计信息不足。

**1.11｜你报告里的"扫描行数"到底怎么算的？和 EXPLAIN 的 `rows` 是一回事吗？**
`关联：执行计划 / 性能度量`
**答**：不是。报告给两个口径：`rows` 是优化器估算（per scan）；"实际扫描"用 `SHOW SESSION STATUS LIKE 'Handler_read%'` 在执行前后的差值求和。简历里的"扫描行数下降"用后者，并注明口径。

**1.12｜为什么报告里要同时给"估算行数"和"实际计数"？**
`关联：统计信息 / 性能度量`
**答**：`rows` 来自统计信息，可能过期、采样偏差；`Handler_read_*` 是本次执行的真实计数。两者并列能看出"优化器以为"和"实际发生"的差距，也能解释"为什么加了索引还是慢"。

**1.13｜规则引擎为什么设计成接口 + 多个实现，而不是一个大的 `if-else` 或 `switch`？**
`关联：设计模式 / 可测试性`
**答**：每条规则独立可测、可开关、可排序；新增规则不改主流程（开闭原则）；单条规则抛异常不影响整体。`if-else` 会变成一个几百行、无法单测、无法解释的函数。

**1.14｜规则之间冲突时（全表扫描 + 未命中索引 + 回表同时出现）你怎么合并？**
`关联：规则引擎 / 去重`
**答**：同一张表、同一组列，只保留 severity 最高的作为主问题，其余折叠成 `related`；索引建议只输出一条，避免给用户多个互斥方案。合并键用 `(表, 列集合)`。

**1.15｜规则的阈值（比如 `rows > 10 万`）怎么定的？换一台机器、换一个库还成立吗？**
`关联：阈值设计 / 统计信息`
**答**：按数据量定，不按时间定；阈值放配置，报告里写明。换环境不一定成立——10 万行在 100 万和 1 亿的表里意义不同，更稳的做法是相对阈值（占表行数的比例），并结合实际耗时。

**1.16｜你怎么控制误报？有没有规则在真实数据上误报过？举一个具体例子。**
`关联：规则质量 / 测试`
**答**：三层：规则只报"AST + 执行计划同时有证据"的；单测覆盖正例/反例/边界；报告标注"建议需人工确认"。真实误报：`数字列 = 字符串` 其实不会失效，我最初按"类型不一致"报，后来区分了转换方向（字符列转数字才失效）。

**1.17｜"识别准确率 ≥ 80%" 的口径是什么？谁来标注"正确"？**
`关联：评估指标`
**答**：16 条 SQL，人工标注每条"应报的问题集合"，工具输出与标注逐条比对；按**问题条目**算准确率/召回，不按 SQL 条数。标注人是我自己，所以报告里写"人工核对"，不吹成标准数据集。

**1.18｜索引建议的输入有哪些？少一个（比如没有列类型）会怎样？**
`关联：索引建议 / 元数据`
**答**：AST 特征（等值/范围/JOIN/排序/SELECT 列）、EXPLAIN（实际用了哪个索引、扫描行数）、表元数据（列类型、字符集、基数）、现有索引（`information_schema.STATISTICS`）。缺列类型判不了隐式转换，缺基数排不了列序。

**1.19｜为什么等值列要按区分度降序排列？反过来会怎样？**
`关联：联合索引 / 选择性`
**答**：联合索引前缀越靠前，过滤后剩余行越少；高区分度列在前能更快缩小范围。反例：低区分度列在前，索引仍要扫大量条目，优化器可能直接放弃这个索引。

**1.20｜范围列为什么最多只放一个？两个范围列会怎样？**
`关联：联合索引 / 范围查询`
**答**：B+ 树只能沿一个方向定位，范围条件之后的索引列无法继续用于定位，第二个范围列只能当过滤条件，放进索引白占空间。所以只保留选择性最好的一个范围列。

**1.21｜排序列什么时候能放进索引？什么时候放了也没用？**
`关联：联合索引 / 排序`
**答**：排序列前面的列都是等值条件、且排序方向一致时，索引本身有序，可以消除 filesort；一旦前面有范围列，索引顺序被打断，排序列放进去也不能用于排序（覆盖场景除外）。

**1.22｜覆盖索引怎么判断？只看 `used_columns` 够吗？**
`关联：覆盖索引`
**答**：SELECT 的列（以及 WHERE 里用到的列）都能在索引列 + 主键里找到，才是覆盖。`used_columns` 是辅助，真正要拿 SELECT 列表和索引定义比对；`SELECT *` 基本不可能覆盖。

**1.23｜已有索引怎么比对？前缀相同但列序不同，算重复吗？**
`关联：索引元数据`
**答**：查 `STATISTICS` 按 `INDEX_NAME, SEQ_IN_INDEX` 还原每个索引的列序。候选是现有索引的前缀 → 已覆盖，跳过；列相同但顺序不同 → 不冗余，顺序决定用途。

**1.24｜现有索引是 `(a)`，你建议 `(a,b)`，那 `(a)` 要不要删？依据是什么？**
`关联：冗余索引 / DDL`
**答**：`(a)` 对 `(a,b)` 是前缀冗余，但**不能自动删**：可能还有只查 `a` 的场景、或 `(a)` 是唯一索引。依据是：查 `performance_schema`/慢日志里是否还有只用 `a` 的查询，以及 `(a)` 是否唯一；报告只提示，不执行。

**1.25｜你生成的 DDL 敢自动执行吗？为什么不敢？设计上怎么兜底？**
`关联：DDL 风险 / 安全`
**答**：不敢。DDL 会占元数据锁、影响写入、可能改变其他查询的计划。工具只生成 SQL + 风险提示，人工确认；生产用 `gh-ost` / `pt-online-schema-change`，并观察主从延迟。

**1.26｜前后对比怎么保证公平？你具体控制了哪些变量？**
`关联：性能测量`
**答**：同一连接、同一参数、同一 `sql_mode`；预热 2 次；正式 3 次取中位数；记录 `Handler_read_*` 差值；加索引前后流程一致；报告注明"热缓存"。

**1.27｜为什么跑 3 次取中位数？如果 3 次差异很大，你会怎么处理？**
`关联：统计 / 测量噪声`
**答**：中位数抗单次抖动（后台任务、GC、缓存）。如果三次差异超过 20%，说明噪声大，加到 5–7 次或换安静环境；报告同时给 min/max，不掩盖波动。

**1.28｜1.8s → 0.12s 是在什么环境下测的？数据量、缓存状态、并发数分别是多少？**
`关联：性能测量 / 缓存`
**答**：本机 MySQL 8.0、100 万订单、10 万用户、单连接无并发、buffer pool 预热后的 3 次中位数。不能吹成生产数据；生产有并发、冷缓存、主从复制和锁竞争。

**1.29｜如果 SQL 是 UPDATE / DELETE / INSERT ... SELECT，你的工具怎么处理？**
`关联：SQL 类型 / 安全`
**答**：当前只处理 SELECT。`EXPLAIN` 能看 DML 的计划，但工具没有执行保护；设计上直接拒绝非 SELECT，Web 端只挂只读账号。要支持的话只做"计划分析"，绝不执行。

**1.30｜子查询、UNION、CTE、窗口函数，你支持到哪一步？不支持时怎么降级？**
`关联：AST / 局限`
**答**：只支持 `PlainSelect`；UNION 是 `SetOperationList`，子查询是 `ParenthesedSelect`，CTE 在 `WithItem`，这些没做。解析失败就降级为"仅 EXPLAIN 诊断"，报告里标注，README 写清局限。

**1.31｜慢日志里同一条 SQL 的常量不同，你怎么归并成一条？**
`关联：SQL 归一化`
**答**：归一化：字面量替换成 `?`、`IN` 列表折叠、去注释、统一空白，算 fingerprint（哈希），按 fingerprint 聚合 `count / sum / avg / max`。

**1.32｜批量诊断怎么排优先级？为什么按总耗时而不是平均耗时？**
`关联：收益模型 / 优先级`
**答**：按总耗时（`sum(query_time)`）排序，因为优化收益 ≈ 单次节省 × 调用次数。一条 50ms 跑 10 万次，比 5s 跑 1 次更值得优化；同时给 avg 和 max 供参考。

**1.33｜工具给出错误建议，最坏会造成什么后果？你怎么在设计上限制影响面？**
`关联：风险控制`
**答**：最坏是建了无用索引（写放大、占空间、优化器选择变差）或 DDL 锁表导致业务抖动。兜底：只生成不执行、风险提示、建议先在影子库验证、报告里给"可回滚"的 DROP 语句。

**1.34｜这个项目最难的技术点是什么？你卡了多久？怎么解决的？**
`关联：项目复盘`
**答**：两件：EXPLAIN JSON 的递归结构（JOIN/排序/分组嵌套，固定路径会 NPE）；"规则不误报"（AST 只能看写法，是否失效还要看类型、字符集、统计信息和实际计划）。前者靠打印树 + fixture 单测，后者靠真实数据跑出错例再改。

**1.35｜哪些代码是 AI 写的？你怎么保证每一行你都能讲清楚？**
`关联：工程实践 / AI`
**答**：骨架、重复样板、报告模板用 AI 提速；规则判定、索引列序、测量口径是我自己定的。验证方式：每个类在真实库跑过、有单测、我能不看代码讲清数据流。面试官指任何一行，我都要能解释。

**1.36｜如果重做一遍，你会砍掉什么、加强什么？**
`关联：项目复盘`
**答**：砍掉过早的 Web UI；加强"规则可解释性"和"真实慢日志回归集"。顺序改成：先 CLI 闭环 → 再规则 → 再建议 → 最后界面，避免界面做完了核心还没跑通。

## 2. Java 语言与 JDK（34）

**2.1｜`HashMap` 的底层结构是什么？JDK 8 相比 7 改了什么？**
`关联：集合 / 哈希表`
**答**：JDK 8 是 `Node[] table` + 链表 + 红黑树；哈希扰动后 `(n-1) & hash` 定位桶；链表长度 ≥ 8 且容量 ≥ 64 转红黑树。JDK 7 是数组 + 链表，扩容时头插法，多线程下可能成环；8 改成尾插 + 红黑树，最坏查询从 O(n) 降到 O(log n)。

**2.2｜`HashMap` 的容量为什么是 2 的幂？扩容时元素怎么迁移？**
`关联：哈希表 / 位运算`
**答**：容量是 2 的幂时，`(n-1) & hash` 等价于取模但更快，且分布均匀。扩容为 2 倍后，每个元素要么留在原位置，要么移到 `原位置 + oldCap`，判断依据是 `hash & oldCap` 是否为 0，不需要重新算哈希。

**2.3｜链表转红黑树的阈值是多少？为什么是 8 和 6 两个值？**
`关联：哈希表 / 复杂度`
**答**：链表长度 ≥ 8 转树；树的节点 ≤ 6 退回链表。用两个阈值形成缓冲，避免在 7/8 之间反复转换（抖动）。另外转树还要求 table 容量 ≥ 64，否则先扩容而不是转树。

**2.4｜`HashMap` 的 key 为什么要重写 `hashCode` 和 `equals`？只重写一个会怎样？**
`关联：对象契约`
**答**：`hashCode` 决定桶位置，`equals` 决定桶内是否相等。只重写 `equals`：相等对象可能落到不同桶，查不到；只重写 `hashCode`：同桶但 `equals` 为 false，永远匹配不上。契约是"equals 相等则 hashCode 必须相等"。

**2.5｜`ConcurrentHashMap` 在 JDK 8 里怎么保证线程安全？和 JDK 7 的分段锁有什么区别？**
`关联：并发 / CAS`
**答**：JDK 8 用 `Node[]`，空桶用 CAS 插入，非空桶对**桶头节点** `synchronized`，扩容多线程协助迁移；size 用 `baseCount + CounterCell[]` 分散计数。JDK 7 是 16 个 `Segment`（继承 `ReentrantLock`），锁粒度是段；8 的锁粒度是单个桶，并发度更高。

**2.6｜`ArrayList` 和 `LinkedList` 的随机访问、插入、内存布局差异是什么？**
`关联：集合 / 数据结构`
**答**：`ArrayList` 底层 `Object[]`，随机访问 O(1)，中间插入要移动元素 O(n)，内存连续、缓存友好；`LinkedList` 双向链表，随机访问 O(n)，已知节点时插入 O(1)，每个节点额外两个引用、内存分散。

**2.7｜`ArrayList` 扩容机制是什么？为什么默认容量是 10？**
`关联：集合 / 扩容`
**答**：默认构造是空数组，第一次 `add` 才扩到 10；之后按 `oldCap + (oldCap >> 1)` 即 1.5 倍扩容，`Arrays.copyOf`。10 是空间与扩容次数的折中，太小频繁扩容，太大浪费内存。

**2.8｜`String` 为什么不可变？字符串常量池和 `intern()` 是什么关系？**
`关联：字符串 / JVM`
**答**：`value` 是 `final byte[]`（Java 9 起压缩字符串），且不暴露修改方法。不可变带来线程安全、hash 可缓存、常量池可复用。`intern()` 把字符串放进常量池并返回池中引用，适合大量重复字符串，但滥用会占满 Metaspace/堆。

**2.9｜`String`、`StringBuilder`、`StringBuffer` 分别适用什么场景？**
`关联：字符串`
**答**：`String` 适合少量、不可变拼接（编译期常量会优化）；`StringBuilder` 单线程可变拼接，最快；`StringBuffer` 方法加了 `synchronized`，线程安全但慢。循环里 `s = s + x` 会反复建对象，应该用 `StringBuilder`。

**2.10｜泛型擦除是什么？`List<String>` 和 `List<Integer>` 在运行时有什么区别？**
`关联：泛型`
**答**：泛型只存在于编译期，编译后类型参数被擦成 `Object` 或上界，运行时 `List<String>` 和 `List<Integer>` 都是 `List`。所以不能 `new T[]`、不能对泛型做 `instanceof`；编译器会生成桥方法保证多态调用正确。

**2.11｜`? extends T` 和 `? super T` 分别适合读还是写？为什么？**
`关联：泛型 / PECS`
**答**：`? extends T` 适合读（生产者），能取出 T，但不能写入（编译器不知道具体子类型）；`? super T` 适合写（消费者），能写入 T 及其子类，但读出来只能当 `Object`。口诀 PECS：Producer Extends, Consumer Super。

**2.12｜Java 异常体系是什么？受检异常和非受检异常怎么选？**
`关联：异常`
**答**：`Throwable` 分 `Error`（JVM 级，不该捕获）和 `Exception`；`Exception` 下 `RuntimeException` 是非受检，其余是受检。受检异常用于"调用方可以恢复/必须处理"的场景；编程错误、参数非法用非受检。不要用异常做流程控制。

**2.13｜`try-with-resources` 的原理是什么？它怎么处理 `close()` 抛异常？**
`关联：异常 / 资源管理`
**答**：资源必须实现 `AutoCloseable`，编译后展开成 `try/finally`，按**声明逆序**关闭。如果 `try` 和 `close()` 都抛异常，`close()` 的异常作为 **suppressed** 挂在主异常上，不覆盖主异常，可通过 `getSuppressed()` 拿到。

**2.14｜`finally` 里写 `return` 会发生什么？为什么不应该这么写？**
`关联：异常 / 控制流`
**答**：`finally` 的 `return` 会覆盖 `try` 里的返回值，甚至吞掉 `try` 里抛出的异常，导致问题被隐藏。除了极少数刻意场景，不应该在 `finally` 里 `return` 或抛异常。

**2.15｜`record` 和普通类有什么区别？它适合替代 Lombok 吗？**
`关联：Java 17 / 语法`
**答**：`record` 是隐式 `final` 的类，自动生成全参构造、访问器、`equals/hashCode/toString`，字段不可变，不能继承其他类，但可以实现接口。它适合 DTO/值对象；不适合需要可变字段、继承或复杂构造的类。Lombok 是编译期改字节码，`record` 是语言特性，面试里 `record` 更稳。

**2.16｜接口的默认方法解决了什么问题？和抽象类怎么选？**
`关联：Java 8 / 接口`
**答**：默认方法让接口在新增方法时不破坏已有实现（二进制兼容），例如 `Collection.stream()`。接口适合"能力/契约 + 多实现"，抽象类适合"共享状态/模板方法 + 单继承"。菱形冲突时实现类必须显式 `override`。

**2.17｜`Stream` 的中间操作和终端操作有什么区别？惰性求值体现在哪？**
`关联：Stream / 函数式`
**答**：中间操作（`map/filter/sorted`）返回新的 Stream，不立即执行；终端操作（`collect/forEach/count`）才触发整个流水线。惰性求值让多个中间操作可以融合成一次遍历，短路操作（`findFirst/anyMatch`）还能提前结束。

**2.18｜并行流 `parallelStream()` 在什么情况下会变慢？它用的是什么线程池？**
`关联：并发 / Stream`
**答**：数据量小、拆分成本高、有 IO/锁、需要保序时都可能更慢。它默认用 `ForkJoinPool.commonPool()`（并行度 = CPU 核数 - 1），被阻塞任务占满会影响全局。IO 密集或需要可控并发时，应该用自定义线程池 + `CompletableFuture`。

**2.19｜`Optional` 解决了什么问题？为什么不适合做字段类型？**
`关联：Java 8 / API 设计`
**答**：用类型显式表达"可能没有值"，减少 `null` 判断和 NPE。它设计成值对象，不可序列化，做字段会增加包装、破坏 JavaBean 约定，也不省内存；更适合方法返回值。取值用 `orElseGet/map/flatMap`，少用 `get()`。

**2.20｜反射的原理是什么？它有什么性能代价？**
`关联：反射 / JVM`
**答**：`Class` 对象持有类元数据，通过 `getDeclaredMethod/Field` 拿到成员并 `invoke/set`，可 `setAccessible(true)` 绕过访问检查。代价：方法查找、参数装箱、访问检查、难以内联，比直接调用慢；框架（Spring/Jackson）靠缓存 `Method` 降低开销。

**2.21｜动态代理有哪两种实现？JDK 代理和 CGLIB 的区别是什么？**
`关联：代理 / 字节码`
**答**：JDK 动态代理基于接口，`Proxy.newProxyInstance` + `InvocationHandler`，生成实现同一接口的类；CGLIB 通过继承生成子类，能代理没有接口的类，但 `final` 类/方法不能代理。Spring Framework 默认有接口用 JDK；Spring Boot 2.x 默认强制 CGLIB（`proxy-target-class=true`）。

**2.22｜JVM 内存区域怎么划分？堆和栈分别放什么？**
`关联：JVM`
**答**：线程共享：堆（对象、数组）、方法区（JDK 8 起是 Metaspace，存类元数据、常量）；线程私有：虚拟机栈（栈帧：局部变量表、操作数栈）、本地方法栈、程序计数器。堆放对象实例，栈放局部变量和方法调用状态。

**2.23｜对象什么时候进入老年代？大对象直接进老年代会有什么问题？**
`关联：GC / 堆`
**答**：年龄达到 `MaxTenuringThreshold`（默认 15）、动态年龄判断（Survivor 中同年龄对象超过一半）、大对象超过 `PretenureSizeThreshold`（仅 Serial/ParNew 生效）、Survivor 放不下时的分配担保。大对象直接进老年代会加速老年代碎片和 Full GC，且失去年轻代回收的机会。

**2.24｜G1 收集器的工作原理是什么？和 CMS 相比解决了什么问题？**
`关联：GC / G1`
**答**：G1 把堆划成等大 Region（逻辑上分 Eden/Survivor/Old/Humongous），按"回收收益"优先回收，用 SATB 处理并发标记，支持 `-XX:MaxGCPauseMillis` 的停顿预测。相比 CMS，它不会产生大量碎片（可整理），停顿更可控，也不用担心 Concurrent Mode Failure。

**2.25｜类加载的双亲委派模型是什么？为什么要这样设计？**
`关联：类加载`
**答**：收到加载请求先交给父加载器（Bootstrap → Platform → App），父加载不了才自己加载。好处：核心类不被篡改（`java.lang.String` 不会被自定义类替换）、避免重复加载。Tomcat 等会打破它做应用隔离。

**2.26｜线程池的核心参数有哪些？任务提交后线程池的处理流程是什么？**
`关联：并发 / 线程池`
**答**：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`handler`。流程：核心线程未满 → 建核心线程；核心满 → 入队列；队列满 → 建非核心线程到 max；再满 → 拒绝策略。注意是**先入队再扩容**，不是核心满了立刻建到 max。

**2.27｜线程池的拒绝策略有哪几种？你项目里会选哪个？**
`关联：线程池`
**答**：`AbortPolicy`（抛异常，默认）、`CallerRunsPolicy`（调用线程执行，天然限流）、`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢最老的）。诊断工具这种"不能丢但可以慢"的场景适合 `CallerRunsPolicy`；对外 API 适合 `AbortPolicy` + 快速失败。

**2.28｜`synchronized` 和 `ReentrantLock` 的区别是什么？**
`关联：并发 / 锁`
**答**：`synchronized` 是 JVM 关键字，自动释放，支持偏向/轻量/重量级升级（偏向锁 JDK 15 后默认关闭）；`ReentrantLock` 是 AQS 实现，可公平/非公平、可 `tryLock`、可中断、可配多个 `Condition`，但必须 `finally` 解锁。简单同步用 `synchronized`，需要超时/中断/公平时用 `ReentrantLock`。

**2.29｜`volatile` 保证什么、不保证什么？`happens-before` 是什么？**
`关联：并发 / 内存模型`
**答**：保证可见性和有序性（禁止重排序），不保证原子性（`i++` 仍不安全）。`happens-before` 是 JMM 定义的偏序：一个操作的结果对另一个操作可见，例如解锁先于加锁、`volatile` 写先于读、线程 `start` 先于线程内操作。

**2.30｜`ThreadLocal` 的原理是什么？为什么会内存泄漏？**
`关联：并发 / ThreadLocal`
**答**：每个 `Thread` 有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 的弱引用，value 是强引用。ThreadLocal 对象被回收后 key 变 null，但 value 还被 Entry 强引用，线程长期存活（线程池）就泄漏。用完必须 `remove()`。

**2.31｜`BigDecimal` 为什么不能直接用 `double` 构造？金额计算要注意什么？**
`关联：数值 / 金额`
**答**：`double` 是二进制浮点，`0.1` 无法精确表示，`new BigDecimal(0.1)` 会得到一长串误差。用 `new BigDecimal("0.1")` 或 `BigDecimal.valueOf(0.1)`。金额用 `DECIMAL`/`BigDecimal`，比较用 `compareTo`（`equals` 会比较 scale），除法必须指定精度和舍入模式。

**2.32｜`LocalDateTime`、`Instant`、`ZonedDateTime` 分别适合什么场景？**
`关联：时间 API`
**答**：`Instant` 是 UTC 时间戳，适合存储/跨时区计算；`LocalDateTime` 不带时区，适合"业务本地时间"（如营业时间）；`ZonedDateTime` 带时区规则，适合跨时区展示和夏令时。数据库 `DATETIME` 对应 `LocalDateTime`，`TIMESTAMP` 对应瞬时时间。

**2.33｜Java 17 有哪些新特性？Java 21 的虚拟线程适合这个项目吗？**
`关联：JDK 版本`
**答**：17：`record`、`sealed`、模式匹配 `instanceof`、文本块、`switch` 预览；21：虚拟线程、`sequenced collections`、`switch` 模式匹配、`record` 模式。这个项目是单机、低并发的诊断工具，虚拟线程收益不大；如果是 Web 版高并发请求，才值得考虑。

**2.34｜字符集和编码的区别是什么？UTF-8 和 GBK 互转会丢什么？**
`关联：字符编码`
**答**：字符集是字符的集合与编号（Unicode），编码是编号到字节的映射（UTF-8/GBK）。UTF-8 变长、兼容 ASCII、支持全 Unicode；GBK 双字节、只覆盖中文等。GBK 转 UTF-8 一般无损，反向遇到 GBK 没有的字符（emoji、生僻字）会变成 `?` 或乱码。

## 3. JDBC 与连接池（22）

**3.1｜`DriverManager.getConnection()` 的完整流程是什么？JDBC 的 SPI 机制起什么作用？**
`关联：JDBC / SPI`
**答**：`DriverManager` 通过 `ServiceLoader` 从 `META-INF/services/java.sql.Driver` 发现驱动实现并注册；`getConnection` 遍历已注册驱动，调用 `driver.connect(url, props)`，第一个能处理的返回 `Connection`。SPI 让 JDBC API 与具体驱动解耦，JDBC 4 之后不需要 `Class.forName`。

**3.2｜`PreparedStatement` 为什么能防 SQL 注入？它的预编译发生在哪一端？**
`关联：JDBC / SQL 注入`
**答**：参数用 `?` 占位，通过 `setXxx` 单独传给驱动，**不会拼进 SQL 文本**，所以参数里的引号/注释不会被当成语法。MySQL Connector/J 默认是**客户端预编译**（本地转义后发送），开启 `useServerPrepStmts=true` 才会发 `COM_STMT_PREPARE` 到服务端；两种方式都安全。

**3.3｜`Statement` 和 `PreparedStatement` 的区别是什么？什么场景只能用 `Statement`？**
`关联：JDBC`
**答**：`Statement` 执行静态 SQL，无参数，有注入风险；`PreparedStatement` 支持参数、可复用执行计划、批量友好。表名、列名、`ORDER BY` 字段这类**标识符不能参数化**，只能用 `Statement` 拼接，但必须用白名单校验。

**3.4｜`execute()`、`executeQuery()`、`executeUpdate()` 分别返回什么？**
`关联：JDBC`
**答**：`execute()` 返回 `boolean`，`true` 表示有 `ResultSet`；`executeQuery()` 返回 `ResultSet`；`executeUpdate()` 返回受影响行数（DDL 返回 0）。不确定语句类型时用 `execute()`。

**3.5｜JDBC 的事务怎么控制？`autoCommit` 默认是什么？**
`关联：JDBC / 事务`
**答**：默认 `autoCommit=true`，每条语句自动提交。手动事务：`setAutoCommit(false)` → 多条 DML → `commit()`；异常时 `rollback()`；最后在 `finally` 恢复 `autoCommit`。连接池会重置状态，但显式恢复更稳。

**3.6｜批处理 `addBatch()` / `executeBatch()` 的原理是什么？**
`关联：JDBC / 批处理`
**答**：`addBatch` 把参数累积到本地列表，`executeBatch` 一次性提交给驱动；驱动可能逐条发送，也可能改写成多值 INSERT。返回 `int[]` 表示每条的影响行数，失败时抛 `BatchUpdateException`，可通过 `getUpdateCounts()` 看哪条成功。

**3.7｜`rewriteBatchedStatements=true` 到底改写了什么？不加会慢多少？**
`关联：JDBC / 批量写入`
**答**：Connector/J 把多条 `INSERT ... VALUES (?,?)` 重写成 `INSERT ... VALUES (...),(...),...`（多值），UPDATE 则可能重写成多条语句（需要 `allowMultiQueries`）。不加时每行一次网络往返，100 万行可能慢 5–10 倍。

**3.8｜为什么需要连接池？每次新建连接的开销在哪里？**
`关联：连接池`
**答**：新建连接要走 TCP 握手、TLS、认证（`caching_sha2_password` 还要 RSA 交换）、会话初始化（字符集、时区、`sql_mode`）、服务端分配线程，通常几毫秒到几十毫秒。连接池复用这些成本，并限制总连接数保护数据库。

**3.9｜HikariCP 的核心参数有哪些？`maximumPoolSize` 怎么定？**
`关联：HikariCP`
**答**：`maximumPoolSize`（默认 10）、`minimumIdle`、`connectionTimeout`（30s）、`idleTimeout`（10min）、`maxLifetime`（30min）、`keepaliveTime`、`leakDetectionThreshold`。池大小从 10 左右起步，按"并发请求数 × 单请求持连接时间 / 目标响应时间"估算，再压测调整；不是越大越好。

**3.10｜连接池越大越好吗？连接数和数据库线程数是什么关系？**
`关联：连接池 / 数据库`
**答**：不是。MySQL 每个连接对应一个服务端线程，连接越多上下文切换、内存、锁竞争越重，吞吐反而下降。经验公式参考 `连接数 ≈ CPU 核数 × 2 + 磁盘数`，实际以压测为准；还要受 `max_connections` 限制。

**3.11｜`connectionTimeout`、`idleTimeout`、`maxLifetime` 分别控制什么？**
`关联：HikariCP`
**答**：`connectionTimeout` 是从池里拿连接的等待上限；`idleTimeout` 是空闲连接被回收的时间；`maxLifetime` 是连接从创建到被强制淘汰的最长寿命（不是空闲时间）。

**3.12｜`maxLifetime` 为什么要比数据库的 `wait_timeout` 小？**
`关联：连接池 / MySQL`
**答**：MySQL 会主动断开超过 `wait_timeout`（默认 8 小时）的空闲连接。如果池里的连接活得比它久，应用可能拿到一个已被服务端关闭的连接，首次使用报错。`maxLifetime` 设小一点（如 30 分钟）可以主动淘汰，避免踩这个时间差。

**3.13｜连接泄漏怎么发现？HikariCP 有哪些相关配置？**
`关联：连接池 / 排障`
**答**：开 `leakDetectionThreshold`（如 10s），连接被借出超时未归还就打印借用栈；同时看池指标 `activeConnections` 是否持续等于上限、请求是否都在等连接。根治靠 `try-with-resources` 和代码 review。

**3.14｜连接失效（被数据库断开）时，连接池怎么检测？`validationQuery` 还要不要配？**
`关联：连接池`
**答**：HikariCP 优先用 JDBC 4 的 `Connection.isValid()` 做保活检测；`connectionTestQuery` 只给不支持 `isValid` 的老驱动用，现代驱动不用配。`keepaliveTime` 可以定期探活。

**3.15｜`ResultSet` 的默认游标是什么？百万行数据怎么流式读取？**
`关联：JDBC / 大数据量`
**答**：默认 `TYPE_FORWARD_ONLY`、`CONCUR_READ_ONLY`，结果集通常一次性拉到客户端。流式读：MySQL 下用 `stmt.setFetchSize(Integer.MIN_VALUE)`（配合 forward-only/read-only）逐行读，或开 `useCursorFetch=true` + 正数 `fetchSize` 走服务端游标。

**3.16｜`fetchSize` 在 MySQL 里为什么默认不生效？要加什么参数？**
`关联：JDBC / MySQL`
**答**：MySQL 默认把整个结果集缓存在客户端，`fetchSize` 被忽略（默认 0）。要生效必须满足：`TYPE_FORWARD_ONLY` + `CONCUR_READ_ONLY`，且用 `Integer.MIN_VALUE` 触发流式，或连接串加 `useCursorFetch=true` 并设正数 `fetchSize`。

**3.17｜`queryTimeout` 和 `socketTimeout` 的区别是什么？**
`关联：JDBC / 超时`
**答**：`Statement.setQueryTimeout(n)` 是 SQL 执行超时，驱动会另开连接发 `KILL QUERY`；`socketTimeout` 是 TCP 读超时，任何一次网络读阻塞超过它就断连，不区分语句。前者业务语义更准，后者防网络挂死，两者都要设。

**3.18｜JDBC 里怎么设置事务隔离级别？和数据库默认值冲突时听谁的？**
`关联：JDBC / 事务`
**答**：`Connection.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ)`，驱动会设置当前会话的隔离级别。显式设置对**这个连接**生效，优先于全局默认；连接池归还后会重置，下一次借用要重新设。

**3.19｜长事务对连接池有什么影响？**
`关联：事务 / 连接池`
**答**：长事务一直占着连接不归还，池里可用连接变少，其他请求排队甚至超时；同时 undo 增长、锁持有时间长、主从延迟变大。要拆小事务、避免事务里做 RPC/IO、设置事务超时。

**3.20｜数据库密码怎么管理？写在代码里、配置文件里、环境变量里分别有什么风险？**
`关联：安全 / 配置`
**答**：写代码里最差（进 Git、反编译可见）；配置文件次之（容易误提交，需 `.gitignore`）；环境变量较好但仍能被同机进程/`ps` 看到。生产用密钥管理（Vault/KMS）或云 IAM，配最小权限账号和定期轮换。

**3.21｜`useSSL`、`allowPublicKeyRetrieval` 这些参数分别解决什么问题？**
`关联：MySQL 连接 / 安全`
**答**：`useSSL=true` 加密链路；`caching_sha2_password` 在非 SSL 连接下需要服务端 RSA 公钥来加密密码，`allowPublicKeyRetrieval=true` 允许客户端主动取公钥，但这可能被中间人替换，生产应优先用 SSL 而不是开它。

**3.22｜时区参数 `connectionTimeZone` / `serverTimezone` 不配会发生什么？**
`关联：时区 / JDBC`
**答**：驱动需要知道服务端时区来转换 `TIMESTAMP`；中文 Windows 上服务端返回"中国标准时间"，驱动可能报 "unrecognized time zone"。显式设 `connectionTimeZone=Asia/Shanghai` 最稳；`DATETIME` 不随时区转换，`TIMESTAMP` 会。

## 4. Maven、Git、工程化（15）

**4.1｜Maven 的生命周期有哪几套？`clean`、`compile`、`test`、`package`、`install` 的顺序是什么？**
`关联：Maven / 构建`
**答**：三套：`clean`、`default`、`site`。`default` 的关键阶段顺序：`validate → compile → test → package → verify → install → deploy`。执行某个阶段会**依次执行它前面的所有阶段**，所以 `mvn install` 会先 compile、test、package。

**4.2｜`phase` 和 `goal` 的区别是什么？插件目标怎么绑定到阶段？**
`关联：Maven`
**答**：`phase` 是生命周期的一个步骤（如 `package`）；`goal` 是插件的一个具体任务（如 `jar:jar`）。绑定方式：打包类型默认绑定，或 `<executions><execution><phase>...</phase><goals><goal>...</goal></goals>` 显式绑定。

**4.3｜依赖冲突时 Maven 的调解规则是什么？"最短路径优先"和"第一声明优先"怎么用？**
`关联：Maven / 依赖`
**答**：先按**最短依赖路径**选版本；路径长度相同时，选 POM 里**先声明**的那个。想强制版本用 `dependencyManagement`（推荐）或 `exclusions` 排除传递依赖。

**4.4｜`dependencyManagement` 和 `dependencies` 的区别是什么？**
`关联：Maven`
**答**：`dependencyManagement` 只声明版本/scope，**不引入依赖**，子模块用到时才生效；`dependencies` 是真正引入。父 POM 用 `dependencyManagement` 统一版本，避免各模块写不同版本。

**4.5｜`scope` 有哪几种？`provided`、`runtime`、`test` 分别什么时候用？**
`关联：Maven`
**答**：`compile`（默认，全阶段）、`provided`（编译需要、运行由容器提供，如 servlet-api）、`runtime`（编译不需要、运行需要，如 JDBC 驱动）、`test`（仅测试）、`system`（本地路径，不推荐）、`import`（仅用于 `dependencyManagement` 导入 BOM）。

**4.6｜怎么排除传递依赖？`exclusions` 写在哪里？**
`关联：Maven`
**答**：写在引入依赖的 `<dependency>` 里：`<exclusions><exclusion><groupId>…</groupId><artifactId>…</artifactId></exclusion></exclusions>`。排除后如果代码真的用到，需要显式再引入正确版本。

**4.7｜SNAPSHOT 版本和 RELEASE 版本的区别是什么？**
`关联：Maven`
**答**：SNAPSHOT 是可变的开发版本，每次发布覆盖，本地/远程会按更新策略重新拉取；RELEASE 不可变，发布后不再改。生产依赖必须用 RELEASE，避免"昨天能编译今天不能"。

**4.8｜多模块项目怎么聚合？父 POM 负责什么？**
`关联：Maven`
**答**：父 POM `packaging=pom`，用 `<modules>` 列子模块；子模块 `<parent>` 指向父。父 POM 统一 `properties`、`dependencyManagement`、`pluginManagement`、仓库和编码，子模块只写自己的依赖与插件。

**4.9｜`maven-shade-plugin` 和 `maven-assembly-plugin` 的区别是什么？打 fat jar 要注意什么？**
`关联：Maven / 打包`
**答**：shade 把依赖解压合并进一个 jar，支持包重定位、合并 `META-INF/services`；assembly 更通用，可以打 zip/目录/自定义布局。fat jar 注意：`META-INF/services` 冲突、重复资源、签名文件（`META-INF/*.SF`）导致校验失败、`module-info` 冲突。

**4.10｜Surefire 和 Failsafe 的分工是什么？**
`关联：Maven / 测试`
**答**：Surefire 跑单元测试（`test` 阶段，默认匹配 `*Test`/`Test*`）；Failsafe 跑集成测试（`integration-test`/`verify` 阶段，匹配 `*IT`），它在测试失败后仍执行 `post-integration-test` 做清理，最后在 `verify` 报失败。

**4.11｜本地仓库、私服、中央仓库的关系是什么？依赖下载流程是怎样的？**
`关联：Maven / 仓库`
**答**：先查本地 `~/.m2/repository`；没有再按 `settings.xml` 的 mirror 去私服（Nexus/Artifactory）；私服没有就代理到中央仓库并缓存。私服的作用是加速、审计、隔离外网和存内部构件。

**4.12｜`.gitignore` 里为什么必须有 `target/`？还有哪些容易误提交的文件？**
`关联：Git / 工程化`
**答**：`target/` 是构建产物，二进制、体积大、每次构建都变，提交会污染历史和冲突。还容易误提交：`.idea/`、`*.iml`、日志、生成的报告、本地配置（含密码）、`.DS_Store`。

**4.13｜`git merge` 和 `git rebase` 的区别是什么？什么时候不该 rebase？**
`关联：Git`
**答**：merge 保留分支历史，生成合并提交；rebase 把当前分支的提交"重放"到新基线上，历史线性但**改写 commit hash**。不要对已经推送、别人在用的公共分支 rebase，否则别人拉取会冲突。

**4.14｜`git reset --soft`、`--mixed`、`--hard` 的区别是什么？**
`关联：Git`
**答**：`--soft` 只移动 HEAD，索引和工作区保留（改动仍在暂存区）；`--mixed`（默认）移动 HEAD 并重置索引，工作区保留；`--hard` 三者全重置，**丢弃未提交改动**，危险。

**4.15｜怎么保证别人 `git clone` 之后一条命令就能跑起来？**
`关联：Git / 交付`
**答**：提供 Maven Wrapper（`mvnw`），README 写清 JDK 版本、初始化数据库的脚本、配置项，默认配置能连本地库；`./mvnw package` 之后 `java -jar` 即可。更彻底的是 `docker-compose up` 一键起库和应用。

## 5. 测试与质量（13）

**5.1｜单元测试和集成测试的边界怎么划？你的项目里哪些是单测、哪些是集成测试？**
`关联：测试`
**答**：单测隔离外部依赖（不连库、不联网），毫秒级；集成测试跨边界（真实 DB、HTTP）。项目里：规则、AST 特征、EXPLAIN 解析、索引建议、报告模板是单测（JSON fixture）；`ExplainCollector`、`Benchmark`、慢日志导入是集成测试（连真实 MySQL）。

**5.2｜JUnit 5 的 `@BeforeEach`、`@BeforeAll`、`@AfterEach` 执行顺序是什么？**
`关联：JUnit 5`
**答**：每个测试类实例：`@BeforeAll`（静态，一次）→ 每个测试方法 `@BeforeEach` → 测试 → `@AfterEach` → 全部结束 `@AfterAll`（静态）。默认每个测试方法新建一个测试类实例，所以实例字段不会互相污染。

**5.3｜`@ParameterizedTest` 怎么用？它比写多个 `@Test` 好在哪？**
`关联：JUnit 5`
**答**：`@ParameterizedTest` + `@ValueSource`/`@CsvSource`/`@MethodSource` 提供参数，一个方法跑多组数据。好处：减少重复代码、失败时能定位到具体参数、用例表一目了然；规则引擎的 20+ 用例很适合这样写。

**5.4｜怎么断言一个方法一定抛异常？怎么断言异常消息？**
`关联：JUnit 5`
**答**：`assertThrows(IllegalArgumentException.class, () -> ...)` 返回异常对象，再 `assertEquals("msg", ex.getMessage())`。不要用 `try/catch + fail()` 的老写法，容易漏断言。

**5.5｜什么是测试夹具（fixture）？为什么你的规则测试用 JSON 文件而不是连数据库？**
`关联：测试 / fixture`
**答**：fixture 是测试前准备好的固定输入与环境。规则测试用 `src/test/resources/plans/*.json`：不依赖数据库、速度快、结果稳定、能版本化；而且这些 JSON 是从真实 EXPLAIN 复制的，能覆盖真实结构。

**5.6｜Mockito 适合 mock 什么？什么情况下不该用 mock？**
`关联：测试 / Mockito`
**答**：适合 mock 外部协作者：数据库、HTTP、时钟、消息队列。不该 mock 值对象/DTO、被测类自身的逻辑、简单纯函数；过度 mock 会让测试"通过但没验证真实行为"，也会和实现耦合。

**5.7｜测试金字塔是什么？为什么集成测试多了会拖慢反馈？**
`关联：测试策略`
**答**：底层大量单测、中层少量服务/集成测试、顶层极少量 E2E。集成测试要起数据库/网络、准备数据、清理环境，慢且易 flaky；单测毫秒级，能在每次保存时跑。反馈越慢，开发者越不愿意跑。

**5.8｜代码覆盖率 80% 能说明质量好吗？覆盖率的陷阱是什么？**
`关联：测试质量`
**答**：不能。覆盖率只说明代码被执行过，不说明断言有效；`assertEquals(true, true)` 也能刷覆盖率。分支覆盖比行覆盖更有意义；关键路径、边界、异常分支比数字重要。

**5.9｜规则引擎怎么测"不误报"？你会设计哪些反例？**
`关联：规则引擎 / 测试`
**答**：每条规则至少：正例（应报）、反例（相似但合法，如 `LIKE 'abc%'`、数字列 = 字符串）、边界（`rows` 恰等于阈值）、畸形输入（解析失败降级）。反例来自真实慢日志和"曾经误报过的 SQL"，断言 `severity` 和建议内容。

**5.10｜什么是 golden file 测试？报告生成适合用它吗？**
`关联：测试 / 报告`
**答**：把期望输出存成文件，测试时生成结果与文件逐字/逐结构比对。报告适合：结构稳定、字段多，逐字段断言太啰嗦；但时间戳、绝对路径要参数化，更新 golden 文件必须走 code review，避免"改到通过"。

**5.11｜测试数据怎么管理？随机数据和固定数据各有什么问题？**
`关联：测试数据`
**答**：随机数据能覆盖边界但不可复现，失败难排查；固定数据可复现但可能漏场景。折中：固定种子 + 测试数据构造器（builder），只对关键字段随机；共享 fixture 要只读，避免测试间互相污染。

**5.12｜数据库相关的测试怎么做才可重复？（事务回滚 / 独立 schema / Testcontainers）**
`关联：测试 / 数据库`
**答**：三层：每个测试用事务包裹并回滚（快，但测不了 DDL/多连接）；独立 schema 或每次重建（能测 DDL）；Testcontainers 起临时 MySQL（最真实，需要 Docker）。别在共享开发库上跑会改数据的测试。

**5.13｜CI 里应该跑哪些步骤？`mvn test` 失败时怎么定位？**
`关联：CI / 排障`
**答**：checkout → 装 JDK → 缓存 `~/.m2` → `mvn -B verify` → 上传 surefire 报告/构建产物。失败时先看 `target/surefire-reports/*.txt` 的堆栈，本地用 `mvn -Dtest=类名#方法 test` 复现；环境相关失败看 JDK 版本和字符集。

## 6. SQL 解析与 AST（14）

**6.1｜什么是 AST？它和词法分析、语法分析是什么关系？**
`关联：编译原理 / SQL 解析`
**答**：AST（抽象语法树）是用树表示程序/语句的结构，节点是 `Select`、`Column`、`Function` 这类语义单元。流程是：字符流 → 词法分析（token）→ 语法分析（按文法建树）→ AST。AST 去掉了括号、空白等细节，只保留结构，所以适合做规则判断。

**6.2｜递归下降解析和运算符优先解析的区别是什么？**
`关联：编译原理`
**答**：递归下降是自顶向下，每个非终结符写一个函数，直观但表达式优先级要分层（`expr → term → factor`）；运算符优先（Pratt/precedence climbing）用一个循环 + 优先级表处理二元运算符，代码更紧凑，适合表达式多的语言。SQL 解析器通常用生成的 LL/LALR 解析器。

**6.3｜JSqlParser 是怎么把 SQL 变成 Java 对象的？它用的是哪种解析技术？**
`关联：JSqlParser`
**答**：它用 **JavaCC** 根据文法生成解析器，解析时直接构造自己的 Java 对象模型（`PlainSelect`、`Column`、`Function`…），`CCJSqlParserUtil.parse()` 返回 `Statement`。不是手写递归下降，也不是 ANTLR。

**6.4｜JSqlParser 5.x 相比 4.x 有哪些不兼容变化？`SelectBody` 去哪了？**
`关联：JSqlParser / API`
**答**：5.x 删除了 `SelectBody`，`Select` 成为基类，`PlainSelect`、`SetOperationList`、`ParenthesedSelect` 直接继承它；`SelectItem` 变成泛型 `SelectItem<?>`；访问器变成泛型 `<S> T visit(X node, S context)`。所以 4.x 的 `select.getSelectBody()` 在 5.x 编译不过，直接 `instanceof PlainSelect`。

**6.5｜为什么 SQL 解析比 JSON 解析难？方言带来的麻烦有哪些？**
`关联：SQL 方言`
**答**：SQL 关键字多、可作标识符、语法有歧义（`JOIN` 隐式/显式）、函数和类型千变万化、各厂商扩展不同（`LIMIT`/`TOP`/`FETCH`、`::`、hint、`ON DUPLICATE KEY`）。JSON 文法小且统一。方言处理不好就会解析失败或误判。

**6.6｜怎么从 AST 里判断"列被函数包裹"？深层嵌套函数怎么办？**
`关联：AST / 规则`
**答**：用 `ExpressionVisitorAdapter` 重写 `visit(Function, ctx)`，检查 `getParameters()` 里是否有 `Column`；再 `super.visit()` 递归进参数，处理 `date(ifnull(col,''))` 这种嵌套。注意只看 WHERE/HAVING 里的函数，SELECT 里的函数不影响索引选择。

**6.7｜怎么判断 `LIKE '%x'`？`LIKE 'x%'` 和 `LIKE '%x%'` 在 AST 里有什么区别？**
`关联：AST / 索引失效`
**答**：`LikeExpression.getRightExpression()` 是 `StringValue`，看字符串是否以 `%` 开头：`'%x'`/`'%x%'` 是前导通配（索引失效），`'x%'` 是前缀匹配（可走范围扫描）。还要处理转义 `\%` 和参数化 `LIKE ?`（运行时才知道值）。

**6.8｜怎么判断 OR 的两侧是否都有索引？只靠 AST 够吗？**
`关联：AST / 索引`
**答**：不够。AST 只能看出 `OrExpression` 两侧的列；是否有索引要查 `information_schema.STATISTICS` 或看 EXPLAIN 的 `possible_keys`/`key`。MySQL 还可能用 index merge，所以最终以执行计划为准，AST 只做初筛。

**6.9｜有表别名时，怎么把 `o.user_id` 解析回 `t_order.user_id`？**
`关联：AST / 语义分析`
**答**：遍历 `FromItem` 和 `Join`，建立"别名/表名 → 真实表名"的映射；`Column.getTable().getName()` 拿到限定名后查映射。无别名的列在单表时直接归属该表，多表时标记为"未知"，不要猜。

**6.10｜子查询里的表怎么遍历？`PlainSelect` 和 `ParenthesedSelect` 怎么区分？**
`关联：AST / 子查询`
**答**：子查询在 `FromItem`、`IN/EXISTS` 的右表达式里，类型是 `ParenthesedSelect`（包一层 `Select`）。用 `FromItemVisitor`/`ExpressionVisitor` 递归下去，遇到 `ParenthesedSelect` 取内层 `Select` 再判断 `PlainSelect`。当前版本只处理顶层，子查询标注为"未覆盖"。

**6.11｜`UNION` 在 AST 里是什么结构？两个分支怎么分别诊断？**
`关联：AST / UNION`
**答**：`SetOperationList`，`getSelects()` 是各分支（通常是 `PlainSelect`），`getOperations()` 是 `UNION`/`UNION ALL`。分别对每个分支跑特征抽取和规则，报告里按分支展示；`ORDER BY`/`LIMIT` 作用于整体。

**6.12｜SQL 归一化（fingerprint）怎么做？为什么不能简单地把数字替换成 `?`？**
`关联：SQL 归一化`
**答**：目标是"结构相同、常量不同"的 SQL 得到同一指纹。简单正则替换会误伤：字符串里的数字、标识符里的数字（`col1`）、注释、`IN` 列表长度、大小写、空白。更稳的是 AST 级替换字面量为 `?`，再序列化；至少也要先去掉注释、区分字符串/标识符。

**6.13｜SQL 解析失败时怎么降级？为什么不能直接抛异常退出？**
`关联：健壮性`
**答**：`catch (JSQLParserException)` 后仍执行 EXPLAIN，只是关闭依赖 AST 的规则，报告标注"AST 解析失败，仅执行计划可用"。慢日志里一定有怪 SQL（hint、方言、多语句），一条失败不能让整批诊断退出。

**6.14｜用 SQL 解析器做"只允许 SELECT"的白名单，比字符串前缀判断好在哪？**
`关联：安全 / AST`
**答**：`startsWith("select")` 能被注释、`WITH`、大小写、前导空白绕过，也挡不住 `SELECT ... INTO OUTFILE`。解析后判断 `Statement` 类型、拒绝多语句、拒绝 `INTO OUTFILE/DUMPFILE`，再配合只读账号和 `max_execution_time`，才是多层防御。

## 7. MySQL 架构与 InnoDB（24）

**7.1｜一条 SQL 从客户端到返回结果，完整经过了哪些组件？**
`关联：MySQL 架构`
**答**：客户端 → 连接器（认证、分配线程）→ 解析器（词法/语法，生成 AST）→ 预处理器（语义检查、权限）→ 优化器（改写、选索引、定 JOIN 顺序、算成本）→ 执行器（按计划调用引擎接口）→ InnoDB（buffer pool、索引、事务、锁）→ 返回结果。

**7.2｜Server 层和存储引擎层分别负责什么？**
`关联：MySQL 架构`
**答**：Server 层负责连接、SQL 解析、优化、执行、binlog、权限、函数；引擎层负责数据的物理存储、索引、事务、锁、redo/undo、buffer pool。Server 层通过 handler API 调用引擎，所以同一套 SQL 可以跑在不同引擎上。

**7.3｜连接器、解析器、优化器、执行器各自做什么？**
`关联：MySQL 架构`
**答**：连接器：TCP/TLS、认证、权限、连接线程；解析器：词法语法分析、生成 AST；优化器：逻辑改写、基于成本选索引和 JOIN 顺序；执行器：按执行计划调用引擎、过滤、组装结果、写 binlog。

**7.4｜MySQL 的连接模型是什么？为什么连接数不能无限加？**
`关联：连接管理`
**答**：一个连接对应一个服务端线程（线程池版除外），连接数受 `max_connections` 限制。每个线程有栈和内存，连接多了上下文切换、锁竞争、内存压力都上升，吞吐反而下降；应用侧要用连接池限流。

**7.5｜redo log、undo log、binlog 的作用和区别是什么？**
`关联：日志 / InnoDB`
**答**：redo 是 InnoDB 的物理日志（页修改），WAL 保证崩溃恢复；undo 是逻辑日志，保存旧版本，用于回滚和 MVCC；binlog 是 Server 层的逻辑日志，用于主从复制和按时间点恢复。redo 循环写，binlog 追加写。

**7.6｜什么是两阶段提交？为什么需要它？**
`关联：事务 / 日志`
**答**：为了保证 redo（引擎层）和 binlog（Server 层）一致：先写 redo 并置 prepare → 写 binlog → 提交 redo（commit）。崩溃恢复时，若 binlog 完整则提交，否则回滚。没有 2PC，可能出现"引擎提交了但 binlog 没写"（主从丢数据）或反之。

**7.7｜Buffer Pool 的作用是什么？脏页什么时候刷？**
`关联：InnoDB / 内存`
**答**：缓存数据页和索引页，读写都先经过它，减少磁盘 IO；内部用改进的 LRU（young/old 分区）防止全表扫描污染。脏页由后台线程按 checkpoint、LRU 淘汰、redo 空间压力、空闲时刷盘。

**7.8｜change buffer 解决什么问题？什么索引用不上它？**
`关联：InnoDB / 写优化`
**答**：对**非唯一二级索引**的插入/更新，如果目标页不在 buffer pool，先把变更记在 change buffer，等页被读入时再 merge，减少随机读。唯一索引必须读页检查唯一性，所以用不上；主键也用不上。

**7.9｜log buffer 什么时候刷盘？`innodb_flush_log_at_trx_commit` 的三个值分别是什么？**
`关联：redo / 持久性`
**答**：`0`：每秒写并刷一次，崩溃可能丢 1 秒；`1`：每次提交都 `fsync`，最安全（默认）；`2`：每次提交写到 OS cache，由 OS 每秒刷，MySQL 崩溃不丢、主机断电可能丢。还有 `innodb_flush_log_at_timeout` 控制周期。

**7.10｜InnoDB 的页、区、段、表空间是什么关系？一页多大？**
`关联：InnoDB / 存储`
**答**：页（page）是 IO 基本单位，默认 16KB；区（extent）默认 1MB = 64 个连续页；段（segment）由多个区组成，分叶子段/非叶子段；表空间（tablespace）是文件的逻辑容器，`.ibd` 存表数据与索引。

**7.11｜行格式有哪些？`DYNAMIC` 和 `COMPACT` 的区别是什么？**
`关联：InnoDB / 行格式`
**答**：`REDUNDANT`、`COMPACT`、`DYNAMIC`（8.0 默认）、`COMPRESSED`。`DYNAMIC` 对长 `VARCHAR/BLOB` 采用**完全溢出页**，行内只留 20 字节指针；`COMPACT` 会在行内保留 768 字节前缀，长字段多时主键页更臃肿。

**7.12｜聚簇索引和二级索引在物理结构上有什么区别？**
`关联：索引 / InnoDB`
**答**：聚簇索引（主键）的叶子节点存**整行数据**；二级索引的叶子节点存**索引列 + 主键值**。所以二级索引查非索引列要拿主键回聚簇索引再查一次（回表）。

**7.13｜为什么推荐自增主键？用 UUID 会有什么问题？**
`关联：主键 / B+ 树`
**答**：自增主键单调递增，插入总在 B+ 树最右侧，页分裂少、页填充率高、二级索引存的主键也小。UUID 随机，插入会打到中间页，频繁页分裂、缓存命中低，且 36 字节比 8 字节大，二级索引膨胀。

**7.14｜什么是页分裂？什么时候会发生？怎么减少？**
`关联：B+ 树 / 插入`
**答**：向已满的页插入时，InnoDB 把页拆成两半并重新分配记录，同时更新前后页指针。随机主键、无序插入、大量更新导致行变长都会触发。减少：自增/有序主键、控制行大小、批量按主键顺序写。

**7.15｜什么是页合并？**
`关联：B+ 树 / 删除`
**答**：删除大量记录后，相邻页利用率很低，InnoDB 会把两个页合并成一个并释放空间。它是后台异步发生的，不是删除即刻触发，所以删数据后磁盘空间不一定马上降。

**7.16｜自适应哈希索引是什么？它对范围查询有用吗？**
`关联：InnoDB / 哈希`
**答**：InnoDB 在内存里为频繁访问的索引页自动建哈希索引，把等值查找变成 O(1)。它只支持等值，不支持范围、排序、最左前缀；可以通过 `innodb_adaptive_hash_index` 关闭，高并发下有时反而是瓶颈。

**7.17｜双写缓冲（doublewrite）解决什么问题？**
`关联：InnoDB / 崩溃恢复`
**答**：解决**部分页写（torn page）**：刷脏页前先顺序写到 doublewrite 区域，再写数据文件；崩溃后如果数据页损坏，可以用 doublewrite 里的副本恢复。代价是多一次写，SSD 上可以用 `innodb_doublewrite=OFF` 换性能，但断电风险变高。

**7.18｜checkpoint 的作用是什么？和崩溃恢复有什么关系？**
`关联：redo / 恢复`
**答**：checkpoint 把内存里的脏页刷到磁盘，并推进 redo 的检查点 LSN，使之前的 redo 可以复用。崩溃恢复只需从最近一次 checkpoint 开始重放 redo，checkpoint 越新，恢复越快。

**7.19｜崩溃恢复时 redo 和 undo 分别做什么？**
`关联：崩溃恢复`
**答**：redo 做**前滚**：从 checkpoint 开始重放已提交但可能未落盘的修改；undo 做**回滚**：把崩溃时未提交的事务撤销。结合 binlog 的两阶段状态决定提交还是回滚。

**7.20｜binlog 的三种格式分别是什么？`ROW` 格式的优缺点是什么？**
`关联：binlog / 复制`
**答**：`STATEMENT`（记 SQL）、`ROW`（记行变更，8.0 默认）、`MIXED`（按语句自动选）。ROW 的优点：确定性强、主从一致、能处理非确定性函数；缺点：日志量大（批量更新）、可读性差、DDL 仍记语句。

**7.21｜redo log 太小会怎样？太大会怎样？**
`关联：redo / 性能`
**答**：太小会频繁 checkpoint、刷脏页跟不上，出现"log file full"等待，写入抖动；太大会增加崩溃恢复时间、占磁盘。一般按写入量设几百 MB 到几 GB，兼顾恢复时间和写性能。

**7.22｜大事务为什么危险？它会带来哪些连锁反应？**
`关联：事务 / 运维`
**答**：undo 暴涨、history list 变长、purge 跟不上；锁持有久、阻塞其他事务；binlog 巨大、主从延迟；回滚可能要很久；buffer pool 被污染。要拆批、控制单事务行数、避免事务里做远程调用。

**7.23｜临时表在内存还是磁盘？什么参数控制？**
`关联：临时表`
**答**：先内存（`TempTable` 引擎，8.0.13+ 默认；旧版是 MEMORY），超过 `tmp_table_size`/`max_heap_table_size` 后转磁盘（InnoDB 临时表空间）。`GROUP BY`、`DISTINCT`、`UNION`、派生表都可能用到。

**7.24｜分区表适合什么场景？为什么很多公司不用它？**
`关联：分区`
**答**：适合按时间/范围做**分区裁剪**和快速删历史数据（`DROP PARTITION`）。限制多：分区键必须在唯一键里、不支持外键、跨分区查询/更新可能更慢、运维和分库分表工具支持差，所以 OLTP 核心表很少用。

## 8. 索引与 B+ 树（34）

**8.1｜为什么 InnoDB 用 B+ 树做索引，而不是 B 树、哈希表、跳表或红黑树？**
`关联：B+ 树 / 数据结构`
**答**：B+ 树扇出大、树矮，磁盘 IO 少；数据全在叶子且叶子有序相连，范围查询和排序友好。B 树非叶子也存数据，扇出小、范围遍历麻烦；哈希只支持等值、不支持范围和排序；跳表是内存结构、没有页局部性；红黑树是二叉树，几百万行高度约 20+ 层，IO 次数不可接受。

**8.2｜B+ 树的非叶子节点存什么？叶子节点存什么？叶子之间怎么连？**
`关联：B+ 树`
**答**：非叶子只存**键 + 子页指针**，不存数据；叶子存数据（聚簇索引存整行，二级索引存索引列 + 主键），叶子之间用**双向链表**连接，支持范围扫描和反向扫描。

**8.3｜一棵三层 B+ 树大概能存多少行？怎么估算的？**
`关联：B+ 树 / 容量`
**答**：按 16KB 页、非叶子每项约 14 字节（8 字节 key + 6 字节指针），一页约 1170 项；叶子按每行 1KB 算约 16 行。三层约 `1170 × 1170 × 16 ≈ 2190 万` 行；行越小存得越多。面试说清假设，不要背一个绝对数字。

**8.4｜页大小 16KB 时，一个节点能放多少个索引项？扇出怎么算？**
`关联：B+ 树 / 页`
**答**：扇出 ≈ 页大小 / 单个索引项大小。BIGINT 主键：8 字节 key + 6 字节页指针 ≈ 14 字节，`16384 / 14 ≈ 1170`。所以非叶子一层能指向约 1170 个子页。

**8.5｜聚簇索引的叶子节点存的是什么？二级索引的叶子节点存的又是什么？**
`关联：聚簇索引 / 二级索引`
**答**：聚簇索引（主键）叶子存**完整行数据**；二级索引叶子存**索引列的值 + 主键值**。所以二级索引本身不含整行，查其他列要拿主键回聚簇索引。

**8.6｜什么是回表？什么情况下不用回表？**
`关联：回表 / 覆盖索引`
**答**：二级索引拿到主键后，再回聚簇索引取整行，叫回表。查询需要的列全在二级索引里（含主键）时不用回表，即覆盖索引；`Using index` 就是这个信号。

**8.7｜覆盖索引一定更好吗？它的代价是什么？**
`关联：覆盖索引`
**答**：不一定。覆盖索引更宽，占更多空间、写放大更严重、buffer pool 能缓存的页更少；优化器也可能因为成本不选它。只在"查询频率高 + 列少 + 收益明确"时做覆盖。

**8.8｜最左前缀原则是什么？`(a,b,c)` 能支持哪些查询组合？**
`关联：联合索引`
**答**：联合索引按 `a,b,c` 排序，查询必须从最左列开始连续使用。支持：`a`、`a,b`、`a,b,c`、`a` + `b` 范围、`a` + `ORDER BY b`、`a,b` + `ORDER BY c`；不支持：只查 `b`、只查 `c`、`b,c`。

**8.9｜联合索引 `(a,b,c)` 下，`WHERE b=1 AND c=2` 能用吗？`WHERE a=1 AND c=2` 呢？**
`关联：联合索引`
**答**：`b=1 AND c=2` 完全用不上（跳过最左列 a）；`a=1 AND c=2` 能用 a 定位，c 只能做过滤（可能走 ICP，但索引里 c 的有序性用不上），不能用来减少扫描范围。

**8.10｜范围查询之后的列为什么用不上索引？`a>1 AND b=2` 在 `(a,b)` 上是什么情况？**
`关联：联合索引 / 范围`
**答**：索引先按 a 排、a 相同再按 b 排；`a>1` 取到的是多个不连续的 a 区间，每个区间内 b 有序但整体无序，所以 b 不能继续用于定位，只能过滤。`(a,b)` 上 `a>1 AND b=2` 用 a 做范围扫描，b 在回表前用 ICP 过滤。

**8.11｜`ORDER BY` 什么时候能利用索引避免排序？什么时候不能？**
`关联：索引 / 排序`
**答**：当 `ORDER BY` 的列正好是索引中"等值条件之后"的连续列，且方向一致（或 8.0 降序索引匹配）时，索引本身有序，可避免 filesort。前面有范围列、排序列不在索引中、或方向混用（无降序索引）时不能。

**8.12｜`GROUP BY` 怎么利用索引？**
`关联：索引 / 分组`
**答**：如果 `GROUP BY` 的列与索引顺序一致（前面可有等值条件），可以顺着索引扫描完成分组，避免临时表和排序；否则会 `Using temporary; Using filesort`。低区分度列分组收益有限，可能仍要扫很多行。

**8.13｜什么是索引下推（ICP）？它减少了什么？**
`关联：索引下推`
**答**：把 WHERE 中"能用索引列判断、但不用于定位"的条件下推到存储引擎层，在回表前过滤，减少回表次数。EXPLAIN 显示 `Using index condition`；只对二级索引有效，且条件列必须在索引里。

**8.14｜`Using index` 和 `Using index condition` 的区别是什么？**
`关联：执行计划`
**答**：`Using index` 是覆盖索引，查询所需列都在索引里，**不回表**；`Using index condition` 是 ICP，索引列条件在引擎层过滤，但查非索引列**仍要回表**。

**8.15｜索引区分度（选择性）怎么算？多高才算"值得建索引"？**
`关联：选择性 / 统计`
**答**：`COUNT(DISTINCT col) / COUNT(*)`，越接近 1 越好。经验上等值查询区分度 > 10%–30% 才值得单独建；范围查询可以更低。但最终要看优化器成本，低区分度列放进联合索引往往更合适。

**8.16｜为什么 `status` 这种只有几个值的列不适合单独建索引？**
`关联：选择性`
**答**：只有 6 个值，选择性约 1/6，走索引要扫大量索引项再回表，成本可能高于全表扫描，优化器多半直接放弃；而且维护索引还有写放大。除非查询只取少量状态且能覆盖，或做成 `(status, create_time)` 这类联合索引。

**8.17｜前缀索引是什么？怎么选前缀长度？它有什么限制？**
`关联：前缀索引`
**答**：`INDEX idx_name (name(10))` 只索引前 10 个字符，节省空间。长度用 `COUNT(DISTINCT LEFT(name,n)) / COUNT(*)` 逼近全列区分度来选。限制：不能覆盖查询（要回表取完整值）、不能用于 `ORDER BY`/`GROUP BY` 完整值、区分度可能不足。

**8.18｜什么是最左前缀匹配失效？举三个真实写法。**
`关联：联合索引`
**答**：① `WHERE b=1`（跳过 a）；② `WHERE b=1 AND c=2`（跳过 a）；③ `WHERE a=1 AND c=2`（a 能用，c 只能过滤）；另外 `a` 上做函数/隐式转换、`a LIKE '%x'` 也会让整个索引失效。

**8.19｜`LIKE '%abc'` 为什么失效？`LIKE 'abc%'` 为什么不一定失效？**
`关联：索引 / LIKE`
**答**：B+ 树按字符串前缀排序，`%abc` 不知道从哪开始，只能全扫；`abc%` 有确定前缀，可以转成范围 `[abc, abd)` 扫描。但 `abc%` 是否走索引还取决于选择性、是否覆盖、优化器成本。

**8.20｜隐式类型转换为什么会导致索引失效？哪种方向会、哪种方向不会？**
`关联：隐式转换`
**答**：字符串列与数字比较时，MySQL 把**列**转成数字再比，列上无法用索引（每行都要转换）；反过来数字列与字符串比较，转的是**常量**，索引仍可用。所以 `varchar_col = 123` 失效，`int_col = '123'` 通常不失效。

**8.21｜字符集不一致为什么会导致 JOIN 索引失效？**
`关联：字符集 / JOIN`
**答**：两列字符集/排序规则不同时，MySQL 要先统一（通常是转换其中一列），被转换列的索引无法使用，JOIN 退化成全表扫描。建表时统一 `utf8mb4` + 同一 collation，JOIN 列类型也保持一致。

**8.22｜OR 为什么容易导致索引失效？什么情况下 MySQL 会用 index merge？**
`关联：OR / index merge`
**答**：OR 要求两侧都高效，任一侧无索引就可能退化成全表扫描。当两侧都有索引时，优化器可能用 index merge（union 合并两个索引结果，或 intersection）；是否用取决于成本，`optimizer_switch` 可控制。

**8.23｜函数索引（8.0.13+）怎么建？它和"改写 SQL"相比有什么取舍？**
`关联：函数索引`
**答**：`ALTER TABLE t ADD INDEX idx_d ((CAST(create_time AS DATE)))` 或 `((DATE(create_time)))`，查询必须用完全相同的表达式才能命中。好处是不用改 SQL；代价是额外存储/写放大、表达式必须确定性、对使用者有"隐形约定"。

**8.24｜降序索引（8.0）解决什么问题？**
`关联：降序索引`
**答**：解决混合排序（`ORDER BY a ASC, b DESC`）无法用索引顺序的问题。8.0 之前索引只能全升序，混合方向要 filesort；8.0 支持 `INDEX (a ASC, b DESC)`，按定义方向存储。

**8.25｜哈希索引在 InnoDB 里怎么存在？为什么它不支持范围查询？**
`关联：哈希索引`
**答**：InnoDB 只有内存中的自适应哈希索引（AHI），由引擎自动为热点页建，不是用户可建的持久索引；MEMORY 引擎支持显式哈希索引。哈希按 key 的哈希值散列，天然无序，所以不支持范围、排序、最左前缀。

**8.26｜全文索引适合什么场景？和 `LIKE '%x%'` 的本质区别是什么？**
`关联：全文索引`
**答**：适合文章/评论的关键词检索，`MATCH ... AGAINST`，倒排索引 + 分词（中文用 ngram），支持相关度排序。`LIKE '%x%'` 是逐行字符串匹配，无法用索引、无法分词、无法排序，数据量大时不可用。

**8.27｜唯一索引和普通索引在写入性能上有什么区别？为什么？**
`关联：唯一索引 / change buffer`
**答**：普通索引的插入/更新可以用 change buffer 延迟合并，减少随机读；唯一索引必须读页检查唯一性，用不上 change buffer，写入更慢一些。但唯一索引能提供约束，且等值查询可能更快（找到即停）。

**8.28｜索引的长度限制是多少？超了怎么办？**
`关联：索引 / 限制`
**答**：InnoDB `DYNAMIC/COMPRESSED` 行格式单列索引上限 3072 字节，`REDUNDANT/COMPACT` 是 767 字节；`utf8mb4` 每字符最多 4 字节。超了用前缀索引、缩短列、或改用哈希列/生成列。

**8.29｜索引提示 `FORCE INDEX` / `USE INDEX` 什么时候用？有什么风险？**
`关联：索引提示`
**答**：只在统计信息失真、优化器明显选错、且无法立刻 `ANALYZE` 时临时用。风险：数据分布变化后提示仍然生效，可能更慢；索引改名/删除会直接报错；掩盖了统计信息问题。优先修统计信息或改写 SQL。

**8.30｜索引越多越好吗？多一个索引会带来哪些代价？**
`关联：索引成本`
**答**：不是。每个索引都要在 INSERT/UPDATE/DELETE 时维护（写放大）、占磁盘和 buffer pool、增加优化器选择成本、DDL 更慢、可能被选错。一般单表控制在 5 个以内，按真实查询建。

**8.31｜什么是冗余索引和重复索引？怎么检测？**
`关联：冗余索引`
**答**：重复：列和顺序完全相同（如 `(a)` 和 `(a)`）；冗余：一个索引是另一个的前缀（`(a)` 是 `(a,b)` 的前缀）。查 `information_schema.STATISTICS` 按列序比对，或用 `pt-duplicate-key-checker`。删之前确认没有查询只依赖前缀索引。

**8.32｜索引和锁有什么关系？没有索引的 UPDATE 会锁多少行？**
`关联：索引 / 锁`
**答**：InnoDB 锁的是索引记录（和间隙），扫描到哪些就锁哪些。没有索引的 UPDATE 会全表扫描，RR 下把扫描到的所有行和间隙都锁住，近似锁表，并发直接崩。所以 UPDATE/DELETE 的 WHERE 列必须有合适索引。

**8.33｜统计信息里的 Cardinality 是什么？它不准会怎样？**
`关联：统计信息`
**答**：优化器估算的索引列**不同值个数**，来自对索引页的采样，存在 `STATISTICS.CARDINALITY`。它不准会导致行数估算偏差，进而选错索引/JOIN 顺序；`ANALYZE TABLE` 可刷新，8.0 还支持直方图。

**8.34｜为什么加了索引，优化器还是不走？**
`关联：优化器 / 索引失效`
**答**：常见原因：列上有函数/隐式转换、前导通配、OR 一侧无索引、跳过最左列、区分度太低、统计信息过期、回表成本太高（不如全扫）、已有更合适的索引、`FORCE INDEX` 了别的索引。用 `EXPLAIN` + `optimizer_trace` 看它为什么选另一条路。

## 9. 优化器与执行计划（30）

**9.1｜MySQL 优化器是怎么选索引的？成本模型里包含哪些成本？**
`关联：优化器 / 成本模型`
**答**：对每个候选索引估算"读多少页 + 处理多少行"，比较总成本取最小。成本分 IO（`read_cost`，读页）和 CPU（`eval_cost`，比较/计算行）；范围查询用 index dive 估算行数，等值/全表用统计信息。它还考虑回表成本、排序成本、JOIN 顺序。

**9.2｜`cost_info` 里的 `read_cost`、`eval_cost`、`query_cost` 分别是什么？**
`关联：执行计划 / 成本`
**答**：`read_cost` 是读数据/索引页的 IO 成本；`eval_cost` 是评估 WHERE 条件的 CPU 成本；`query_cost` 是两者之和（多表时还有前缀成本）。单位是内部成本单位，不是毫秒。

**9.3｜`EXPLAIN` 的 `type` 有哪些取值？从好到差怎么排？**
`关联：执行计划 / 访问类型`
**答**：`system > const > eq_ref > ref > fulltext > ref_or_null > index_merge > unique_subquery > index_subquery > range > index > ALL`。越靠前越快；`index` 是全索引扫描，`ALL` 是全表扫描，线上要尽量避免这两个。

**9.4｜`system`、`const`、`eq_ref`、`ref`、`range`、`index`、`ALL` 分别是什么场景？**
`关联：执行计划`
**答**：`system`：表只有一行；`const`：主键/唯一索引等值，最多一行；`eq_ref`：JOIN 中被驱动表用主键/唯一索引等值匹配，每行一条；`ref`：普通索引等值，可能多行；`range`：索引范围扫描；`index`：扫整棵索引树；`ALL`：全表扫描。

**9.5｜`possible_keys`、`key`、`key_len`、`ref`、`rows`、`filtered`、`Extra` 各是什么含义？**
`关联：执行计划`
**答**：`possible_keys` 是可能可用的索引；`key` 是实际选的；`key_len` 是用了索引的多少字节；`ref` 是与索引比较的列/常量；`rows` 是预计扫描行数；`filtered` 是过滤后剩余百分比；`Extra` 是额外信息（覆盖、排序、临时表等）。

**9.6｜`key_len` 怎么算？它能说明联合索引用到了哪几列吗？**
`关联：执行计划 / 联合索引`
**答**：定长列按字节数；`VARCHAR(n)` 加 1–2 字节长度；可空列再加 1 字节；`utf8mb4` 每字符最多 4 字节。把 `key_len` 和各列定义对上，就能推断联合索引用到了前几列；但函数/前缀索引会让计算变复杂。

**9.7｜`Extra` 里常见的值有哪些？`Using where` 和 `Using index` 能同时出现吗？**
`关联：执行计划 / Extra`
**答**：`Using index`（覆盖）、`Using where`（回表后过滤）、`Using index condition`（ICP）、`Using temporary`、`Using filesort`、`Using join buffer`、`Using MRR`、`Select tables optimized away`。可以同时出现：覆盖索引 + 索引列之外的条件过滤。

**9.8｜`Using filesort` 一定慢吗？它用的算法是什么？**
`关联：排序`
**答**：不一定。结果集小、`sort_buffer_size` 足够时是内存快排，很快；数据量大才退化为磁盘归并排序。它只表示"不能靠索引顺序，需要额外排序"，是否慢要结合行数和耗时判断。

**9.9｜单路排序和双路排序的区别是什么？`max_length_for_sort_data` 影响什么？**
`关联：排序`
**答**：单路（全字段）把 SELECT 的所有列都放进 sort buffer，排完直接返回，只读一次表；双路只放排序键 + 行指针，排完再按指针回表取列，读两次。8.0.20 之前用 `max_length_for_sort_data` 控制选择；新版本优化器按行宽和 `sort_buffer_size` 自动选，该参数已废弃，别再拿它调优。

**9.10｜`Using temporary` 什么时候出现？内存临时表和磁盘临时表怎么区分？**
`关联：临时表`
**答**：`GROUP BY`/`DISTINCT`/`UNION`/派生表/某些 `ORDER BY` 需要中间结果时出现。先建内存临时表（TempTable），超过 `tmp_table_size`/`max_heap_table_size` 转磁盘。看 `Created_tmp_disk_tables` 或 `performance_schema` 的临时表统计区分。

**9.11｜MySQL 的 JOIN 算法有哪几种？NLJ、BNL、哈希连接分别适合什么？**
`关联：JOIN 算法`
**答**：NLJ（嵌套循环，被驱动表有索引，逐行查）、BNL（被驱动表无索引，用 join buffer 分块匹配）、哈希连接（8.0.18+，等值连接，建哈希表探测）、BKA（批量 key 访问 + MRR）。有索引优先 NLJ，无索引大表用哈希连接。

**9.12｜8.0.18 之后的哈希连接解决了什么问题？**
`关联：JOIN / 哈希连接`
**答**：解决"被驱动表没有索引时 BNL 太慢"的问题：把小的那一侧建哈希表，另一侧扫描探测，复杂度接近 O(N+M)，不需要索引。只支持等值连接，内存不够会落盘。

**9.13｜`join_buffer_size` 影响什么？**
`关联：JOIN / 内存`
**答**：BNL 和哈希连接用的内存大小。太小会分多块、多次扫描被驱动表；太大会占内存、影响并发。按 join 规模调，不要无脑设很大。

**9.14｜驱动表是怎么选的？为什么"小表驱动大表"？**
`关联：JOIN / 优化器`
**答**：优化器按过滤后的行数和成本选驱动表（外层循环）；`LEFT JOIN` 的驱动表通常固定为左表。小结果集驱动，外层循环次数少，被驱动表走索引时总 IO 更小；但"小"指过滤后的行数，不是表总行数。

**9.15｜`STRAIGHT_JOIN` 什么时候用？**
`关联：JOIN / 优化器`
**答**：当优化器选错驱动顺序、且你确认另一个顺序明显更好时，用它强制按书写顺序 JOIN。风险：数据分布变化后可能更差、可读性差；优先尝试 `ANALYZE TABLE` 或改写 SQL。

**9.16｜`EXPLAIN ANALYZE` 和 `EXPLAIN` 的本质区别是什么？什么时候该用？**
`关联：执行计划 / 实测`
**答**：`EXPLAIN` 只生成计划、不执行；`EXPLAIN ANALYZE` **真的执行**并返回每步的实际耗时、实际行数、循环次数。适合在测试环境定位"估算与实际的偏差"，不要在生产对重查询随便用。

**9.17｜`EXPLAIN FORMAT=TREE` 比 JSON 好在哪里？**
`关联：执行计划 / 格式`
**答**：TREE 是缩进文本，人读起来直观，能看到 JOIN 顺序和每步成本；`EXPLAIN ANALYZE` 的 TREE 还会带实际时间/行数。JSON 结构更适合程序解析。两者可以配合：人看 TREE，程序读 JSON。

**9.18｜`optimizer_trace` 怎么看？它能回答什么问题？**
`关联：优化器 / 诊断`
**答**：`SET optimizer_trace='enabled=on'`，执行 SQL，然后查 `information_schema.OPTIMIZER_TRACE` 的 `TRACE` 字段。它记录候选索引、每个方案的成本、为什么选这个，能回答"为什么没走索引/为什么选错索引"。

**9.19｜统计信息是怎么收集的？`ANALYZE TABLE` 做了什么？**
`关联：统计信息`
**答**：InnoDB 默认随机采样少量索引页（`innodb_stats_persistent_sample_pages`，默认 20）估算行数和基数，持久化到磁盘。`ANALYZE TABLE` 重新采样并更新 `STATISTICS` 的 `CARDINALITY`，让优化器拿到更新的分布。

**9.20｜统计信息持久化（`innodb_stats_persistent`）解决什么问题？**
`关联：统计信息`
**答**：非持久化时统计信息在重启/某些操作后重新采样，可能导致执行计划"飘"。持久化把统计信息存到磁盘，重启后稳定，减少计划突变；代价是数据变化后要手动/定时 `ANALYZE`。

**9.21｜直方图（histogram）解决什么问题？怎么建？**
`关联：统计信息 / 直方图`
**答**：解决"列上没有索引、但 WHERE 用它过滤"时优化器不知道数据分布的问题，尤其数据倾斜。`ANALYZE TABLE t UPDATE HISTOGRAM ON col WITH 100 BUCKETS;`，之后 `information_schema.COLUMN_STATISTICS` 可查。

**9.22｜为什么 `rows` 会估不准？举三个原因。**
`关联：统计信息 / 估算`
**答**：① 采样页少、数据倾斜（如 20% 用户 80% 订单）；② 多列相关性，优化器按独立假设相乘；③ 统计信息过期；另外函数/表达式、`LIKE`、`IN` 长列表的选择性也很难估。

**9.23｜绑定变量和"参数化查询"会影响执行计划吗？**
`关联：优化器 / 参数`
**答**：会。服务端预编译可能复用第一次的计划，常量不同（比如 `status=1` 和 `status=3` 命中行数差很多）会导致计划不适合；Connector/J 默认客户端预编译，每次执行都重新优化，反而按实际常量选计划。

**9.24｜MySQL 8 有没有执行计划缓存？Oracle 的游标共享和它有什么区别？**
`关联：优化器 / 缓存`
**答**：MySQL 8 没有 Oracle 那种全局执行计划缓存（查询缓存也在 8.0 移除）；预编译语句在会话内有句柄，但计划仍可能因统计/常量变化。Oracle 的游标共享会复用计划并做绑定变量窥探，机制不同。

**9.25｜条件下推（condition pushdown）是什么？**
`关联：优化器 / 下推`
**答**：把外层的 WHERE 条件下推到派生表、UNION 分支、外连接的内层，尽早过滤减少行数。8.0.22 有 `derived_condition_pushdown`；索引条件下推（ICP）是另一回事，发生在引擎层。

**9.26｜子查询物化是什么？什么时候会物化？**
`关联：子查询 / 物化`
**答**：把子查询结果算出来存进临时表（可带索引），避免对外层每一行重复执行。`IN`/`EXISTS` 无法转半连接、或子查询结果需要复用时，优化器会选择物化；`EXPLAIN` 里能看到 `materialized`。

**9.27｜半连接（semi-join）有哪些执行策略？**
`关联：子查询 / 半连接`
**答**：`FirstMatch`（找到第一条就停）、`LooseScan`（利用索引去重扫描）、`Materialization`（物化后 join）、`DuplicateWeedout`（用临时表去重）。用于 `IN`/`EXISTS` 这类"只关心是否存在"的子查询。

**9.28｜派生表合并（derived merge）是什么？什么时候不能合并？**
`关联：派生表`
**答**：把 `FROM (SELECT ...) t` 的派生表展开合并进外层查询，避免物化。含 `GROUP BY`、`DISTINCT`、`LIMIT`、`UNION`、窗口函数等无法简单合并时，会物化成临时表。

**9.29｜`LIMIT` 对优化器的选择有什么影响？**
`关联：LIMIT / 优化器`
**答**：有 `LIMIT` 时优化器知道只需少量行，可能优先选能提供顺序的索引、提前终止扫描；但 `LIMIT offset, n` 仍要扫描并丢弃 offset 行，offset 很大时成本依然高。

**9.30｜为什么"加了索引还是慢"？列出至少五种可能。**
`关联：索引 / 性能`
**答**：① 索引没被选中（函数、隐式转换、区分度低、统计过期）；② 回表太多（选择性差或 `SELECT *`）；③ 仍有 filesort/临时表；④ 锁等待或并发争用；⑤ 数据量/网络/应用层瓶颈；⑥ 索引选错，扫描量反而更大。

## 10. 慢查询与监控（12）

**10.1｜慢查询日志有哪些关键参数？`long_query_time` 修改后需要重启吗？**
`关联：慢查询日志`
**答**：`slow_query_log`、`slow_query_log_file`、`long_query_time`、`log_output`、`log_queries_not_using_indexes`、`min_examined_row_limit`、`log_slow_admin_statements`。`long_query_time` 是全局+会话动态参数，`SET GLOBAL` 立即生效，不需要重启（但重启后恢复配置文件值）。

**10.2｜`log_output` 的 `FILE` 和 `TABLE` 各有什么优缺点？**
`关联：慢查询日志`
**答**：`FILE` 开销小、可轮转、适合长期保留，但要登录机器解析；`TABLE` 直接 SQL 查、方便，但写表有额外开销、`mysql.slow_log` 是 CSV 引擎、没有索引，量大时查询慢。

**10.3｜`mysql.slow_log` 表用的是什么存储引擎？有什么使用限制？**
`关联：慢日志表`
**答**：CSV 引擎。没有索引、不支持事务、不能 UPDATE/DELETE 单行（只能整表操作/`TRUNCATE`），并发写入性能差。适合临时排查，不适合长期大量保留。

**10.4｜`log_queries_not_using_indexes` 开启后有什么副作用？**
`关联：慢日志`
**答**：所有没走索引的查询都会记录，**不管多快**，小表/高频简单查询会把日志刷爆，增加 IO 和磁盘占用。通常配合 `min_examined_row_limit` 限制，或只在短时间排查时开。

**10.5｜`pt-query-digest` 的聚合原理是什么？它怎么给 SQL 做指纹？**
`关联：SQL 归一化 / 慢日志`
**答**：解析慢日志，把字面量、`IN` 列表、空白归一化成占位符，生成 fingerprint，按 fingerprint 分组；每组统计 count、总耗时、平均、max、p95、扫描行数，并按总耗时排序输出 profile。

**10.6｜`performance_schema` 的 digest 表和慢日志是什么关系？**
`关联：performance_schema`
**答**：digest 表是服务端**实时聚合**的统计（按归一化 SQL 分组），不需要开慢日志、不受 `long_query_time` 限制；慢日志是逐条记录。两者指纹算法类似，digest 更适合看"当前最耗资源的 SQL"，慢日志适合留证和离线分析。

**10.7｜慢日志对数据库性能有影响吗？生产上怎么权衡？**
`关联：慢日志 / 性能`
**答**：有。写文件/表、格式化 SQL、锁（TABLE 模式）都有开销。生产上设合理阈值（如 0.5–1s）、用 FILE + 轮转、避免 `log_queries_not_using_indexes` 长期开启；高负载时优先用 `performance_schema`。

**10.8｜线上突然出现大量慢查询，你的排查顺序是什么？**
`关联：排障`
**答**：① 看监控（QPS、连接数、CPU/IO、主从延迟）确认范围；② `SHOW PROCESSLIST` 看阻塞/长事务/锁等待；③ 慢日志/digest 找 Top SQL；④ 对比近期变更（发布、DDL、数据量、参数）；⑤ 对 Top SQL `EXPLAIN`；⑥ 止血（限流、kill、加索引/回滚）再定位根因。

**10.9｜监控 MySQL 应该看哪些指标？QPS、TPS、连接数、`Innodb_rows_read` 分别说明什么？**
`关联：监控`
**答**：QPS：查询吞吐；TPS：事务吞吐；连接数（`Threads_connected/running`）：并发压力；`Innodb_rows_read`：实际扫描行数，能看出"查询变重"；再加 buffer pool 命中率、磁盘 IO、锁等待、主从延迟。

**10.10｜`SHOW PROCESSLIST` 和 `information_schema.PROCESSLIST` 能看出什么？**
`关联：排障`
**答**：当前连接、用户、来源、执行的 SQL、状态（`Sending data`、`Locked`、`Waiting for table metadata lock`）、已执行时间。能快速发现长事务、锁等待、全表扫描；普通用户只能看自己的线程，需要 `PROCESS` 权限看全部。

**10.11｜主从延迟怎么监控？延迟的常见原因有哪些？**
`关联：复制 / 监控`
**答**：`SHOW REPLICA STATUS` 的 `Seconds_Behind_Source`，更准的是 `pt-heartbeat` 写时间戳。原因：大事务、大表 DDL、单线程回放、无主键导致 ROW 回放慢、网络、从库负载高、锁冲突。

**10.12｜告警阈值怎么定？定得太低会怎样？**
`关联：监控 / 告警`
**答**：基于历史基线 + 分位数（P95/P99），而不是拍脑袋；区分"症状指标"（延迟、错误率）和"资源指标"（CPU）。太低会告警疲劳，最后没人看；太高会漏掉真实故障。定期回顾阈值。

## 11. 事务、锁、MVCC（20）

**11.1｜ACID 分别是什么？InnoDB 靠什么保证每一项？**
`关联：事务`
**答**：A 原子性靠 undo（回滚）；C 一致性靠约束 + 应用逻辑 + 事务机制共同保证；I 隔离性靠锁 + MVCC；D 持久性靠 redo log + 刷盘（`innodb_flush_log_at_trx_commit=1`）。

**11.2｜四种隔离级别分别解决了什么问题？MySQL 默认是哪一级？**
`关联：隔离级别`
**答**：读未提交（啥都不解决）、读已提交（解决脏读）、可重复读（解决脏读 + 不可重复读，MySQL 默认）、串行化（再解决幻读，但并发最差）。RR 下快照读靠 MVCC，当前读靠间隙锁。

**11.3｜脏读、不可重复读、幻读的区别是什么？**
`关联：隔离级别`
**答**：脏读：读到别的事务未提交的数据；不可重复读：同一行两次读值不同（别人改了并提交）；幻读：同一范围两次读，行数变了（别人插入/删除了满足条件的行）。

**11.4｜MVCC 的实现原理是什么？ReadView 里有哪些字段？**
`关联：MVCC`
**答**：每行有隐藏的 `trx_id`（最后修改它的事务）和 `roll_pointer`（指向 undo 旧版本）。ReadView 记录：`m_ids`（活跃事务 id 列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。判断可见性：trx_id < min 可见；≥ max 不可见；在 m_ids 中不可见；否则可见，不可见就沿 undo 链找旧版本。RR 在事务第一次快照读时创建 ReadView 并复用，RC 每条语句重建。

**11.5｜`undo` 版本链是怎么串起来的？**
`关联：MVCC / undo`
**答**：每次 UPDATE 把旧值写进 undo 记录，当前行的 `roll_pointer` 指向它；多条 undo 记录通过 `roll_pointer` 串成链表。ReadView 判断当前版本不可见时，就顺着链找到可见的旧版本；没有事务再需要时由 purge 线程清理。

**11.6｜快照读和当前读的区别是什么？哪些语句是当前读？**
`关联：MVCC / 锁`
**答**：快照读读 ReadView 对应的历史版本，不加锁（普通 `SELECT`）；当前读读最新已提交版本并加锁：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT`。

**11.7｜RR 级别下幻读被完全解决了吗？间隙锁起什么作用？**
`关联：RR / 间隙锁`
**答**：快照读下不会幻读（一直看同一个 ReadView）；当前读下靠 next-key lock 锁住范围间隙，阻止其他事务在区间内插入，从而避免幻读。但如果没有索引、条件复杂，锁的范围可能很大；特殊场景仍可能看到"幻影"。

**11.8｜记录锁、间隙锁、临键锁（next-key lock）分别锁什么？**
`关联：InnoDB 锁`
**答**：记录锁锁一条索引记录；间隙锁锁两个索引记录之间的"缝"，防止插入；临键锁 = 记录锁 + 前面的间隙锁，是 RR 下范围扫描的默认加锁方式。

**11.9｜插入意向锁是什么？它和间隙锁会冲突吗？**
`关联：InnoDB 锁`
**答**：插入前在目标间隙上加的一种意向锁，表示"我要在这个间隙插入"。多个插入意向锁之间不冲突（不同位置可并发插入），但它会和别人持有的间隙锁冲突，从而被阻塞。

**11.10｜没有索引的 `UPDATE` 会锁多少行？为什么？**
`关联：锁 / 索引`
**答**：InnoDB 锁的是扫描到的索引记录。没有可用索引时只能全表扫描，RR 下会把扫描到的所有记录和间隙都锁住，近似锁表，其他事务的写入/更新基本被阻塞。所以 UPDATE/DELETE 的 WHERE 列必须有索引。

**11.11｜意向锁的作用是什么？**
`关联：InnoDB 锁`
**答**：表级锁，表示"这个事务准备在表里加行锁"（IS 共享意向、IX 排他意向）。它让表级锁（如 `LOCK TABLES`、DDL）不必逐行检查就能判断是否冲突；意向锁之间互相兼容。

**11.12｜死锁是怎么产生的？InnoDB 怎么检测？`innodb_deadlock_detect` 关掉会怎样？**
`关联：死锁`
**答**：两个事务互相等待对方持有的锁，形成环。InnoDB 用 wait-for graph 检测，发现环就回滚"代价小"的事务（undo 量少）。关掉检测后不会立刻报死锁，只能等 `innodb_lock_wait_timeout` 超时，响应变慢。

**11.13｜锁等待超时后事务是什么状态？**
`关联：锁 / 事务`
**答**：默认只回滚**当前语句**，事务仍然开着，需要应用显式 `ROLLBACK` 或 `COMMIT`；如果 `innodb_rollback_on_timeout=ON`，会回滚整个事务。连接池场景一定要注意别把半开事务还回去。

**11.14｜乐观锁和悲观锁分别怎么实现？各自适合什么场景？**
`关联：并发控制`
**答**：乐观锁用版本号/时间戳：`UPDATE ... SET version=version+1 WHERE id=? AND version=?`，失败重试，适合读多写少、冲突少；悲观锁用 `SELECT ... FOR UPDATE` 占住行，适合冲突频繁、重试代价高的场景。

**11.15｜大事务会带来哪些问题？怎么拆分？**
`关联：事务 / 运维`
**答**：undo 膨胀、history list 变长、锁持有久、binlog 大、主从延迟、回滚慢、buffer pool 污染。拆分：按主键分批提交、事务里不做 RPC/文件 IO、控制单事务行数、用异步/补偿替代长事务。

**11.16｜RR 和 RC 在 binlog 格式上有什么要求？为什么？**
`关联：事务 / binlog`
**答**：RC 下用 STATEMENT 格式可能主从不一致（语句执行顺序/可见性不同），所以要用 ROW；RR 下 STATEMENT 相对安全但仍不推荐。MySQL 默认 ROW，正是为了确定性和一致性。

**11.17｜什么是"一致性读"？它和锁冲突吗？**
`关联：MVCC`
**答**：一致性读（快照读）基于 ReadView 读历史版本，不加锁，所以不会和写锁冲突；它保证同一事务内看到一致的快照，但不保证读到最新数据。

**11.18｜`SELECT ... FOR UPDATE` 和 `LOCK IN SHARE MODE` 的区别是什么？**
`关联：锁`
**答**：`FOR UPDATE` 加排他锁（X），其他事务不能改也不能加共享锁；`LOCK IN SHARE MODE`（8.0 的 `FOR SHARE`）加共享锁（S），别人可以读但不能改。两者都是当前读。

**11.19｜分布式事务有哪些方案？2PC、TCC、Saga、本地消息表分别适合什么？**
`关联：分布式事务`
**答**：2PC/XA：强一致、性能差、协调者单点；TCC：业务补偿、侵入大、适合支付类；Saga：长事务、最终一致、要处理补偿；本地消息表/Outbox：最终一致、实现简单、适合跨服务通知。多数互联网场景选最终一致。

**11.20｜跨库 JOIN 怎么做？为什么大多数公司禁止？**
`关联：分库分表`
**答**：应用层分别查再拼、冗余字段、宽表/ES、或中间件做联邦查询。禁止的原因：跨网络放大延迟、无法用索引、事务一致性难保证、扩缩容困难；通常用冗余和异步同步替代。

## 12. JOIN、分页、子查询（14）

**12.1｜NLJ 的时间复杂度是多少？为什么被驱动表的关联列必须有索引？**
`关联：JOIN / 索引`
**答**：无索引时 NLJ 是 O(N×M)，外层每行都要全扫内层；被驱动表关联列有索引时，内层变成索引查找，复杂度接近 O(N×log M)。所以 JOIN 的索引建在**被驱动表**的关联列上。

**12.2｜小表驱动大表的原则在什么情况下会失效？**
`关联：JOIN / 优化器`
**答**：当"小表"过滤后并不小、被驱动表没有索引、或 `LEFT JOIN` 固定了驱动顺序时；另外如果驱动表过滤性差，外层循环次数仍然很多。优化器按成本选，不只看表总行数。

**12.3｜JOIN 字段类型不一致会发生什么？字符集不一致呢？**
`关联：JOIN / 隐式转换`
**答**：类型不一致会触发隐式转换，可能导致索引失效、结果不符合预期（如字符串比较的排序规则）；字符集/排序规则不一致时，被转换列的索引失效，JOIN 退化为全表扫描。建表时统一类型和字符集。

**12.4｜多表 JOIN 时，索引应该建在哪张表上？**
`关联：JOIN / 索引`
**答**：建在**被驱动表**（内层循环）的关联列上；驱动表通常按 WHERE 条件建索引。`LEFT JOIN` 时右表是被驱动表，索引建在右表关联列；同时考虑 WHERE 里对右表的过滤条件。

**12.5｜深分页为什么慢？`LIMIT 1000000, 20` 到底执行了什么？**
`关联：分页`
**答**：MySQL 要先扫描并丢弃前 100 万行，再取 20 行；如果还有排序，成本更高。扫描的行多、回表多、随机 IO 多，所以越翻越慢。

**12.6｜延迟关联怎么优化深分页？它的原理是什么？**
`关联：分页 / 覆盖索引`
**答**：先用覆盖索引只查主键：`SELECT id FROM t ORDER BY ... LIMIT 1000000, 20`，再 `JOIN` 回表取整行。这样前 100 万行只走索引（不回表），只有最后 20 行回表，IO 大幅下降。

**12.7｜游标分页（`WHERE id > last_id`）有什么限制？**
`关联：分页`
**答**：要求排序键唯一且单调（通常是自增主键），只能"下一页"，不能随机跳页；如果有复杂排序/多列排序，游标条件会变复杂。优点是 O(1) 定位，不随页码变慢。

**12.8｜`COUNT(*)`、`COUNT(1)`、`COUNT(col)` 的区别是什么？**
`关联：聚合`
**答**：`COUNT(*)` 和 `COUNT(1)` 都统计行数，InnoDB 会选最小的二级索引扫描；`COUNT(col)` 只统计 `col IS NOT NULL` 的行，结果可能更小，且要读该列。

**12.9｜大表 `COUNT(*)` 怎么优化？近似值可以接受吗？**
`关联：聚合 / 架构`
**答**：用最小的二级索引、汇总表/计数表、`SHOW TABLE STATUS` 的近似值、或把统计放到 OLAP/缓存。是否接受近似值取决于业务（列表总数可以近似，财务对账不行）。

**12.10｜`IN` 和 `EXISTS` 怎么选？子查询会不会被改写成 JOIN？**
`关联：子查询`
**答**：取决于优化器：`IN` 可能转半连接/物化，`EXISTS` 可能走 FirstMatch；一般小结果集用 `IN`，相关子查询用 `EXISTS`。MySQL 8 会做半连接转换，最终看 `EXPLAIN`，不要死记规则。

**12.11｜`UNION` 和 `UNION ALL` 的区别是什么？去重的代价在哪？**
`关联：集合运算`
**答**：`UNION` 会去重，需要排序或临时表，代价高；`UNION ALL` 直接拼接，快。确定没有重复或业务能接受重复时，优先 `UNION ALL`。

**12.12｜`GROUP BY` 怎么优化？什么时候需要临时表？**
`关联：分组`
**答**：让 `GROUP BY` 列与索引顺序一致（前面可带等值条件），避免临时表和排序；无法利用索引、或分组列顺序不匹配时，会建临时表。减少分组前的行数（先过滤）也很关键。

**12.13｜`DISTINCT` 的性能问题是什么？能用 `GROUP BY` 替代吗？**
`关联：去重`
**答**：`DISTINCT` 可能走临时表/排序；如果去重列有索引且能覆盖，可以只扫索引。`GROUP BY` 和 `DISTINCT` 在优化器里经常等价，但语义不同（`GROUP BY` 可带聚合），不要为了"快"盲目替换。

**12.14｜排序 + 分页 + 过滤同时存在时，索引怎么设计？**
`关联：索引设计`
**答**：按"等值过滤列 → 排序列 → 覆盖列"设计联合索引，让过滤和排序都走索引；如果排序列前有范围条件，排序无法靠索引，考虑延迟关联或业务限制范围。最后用 `EXPLAIN` 验证是否消除 filesort。

## 13. 场景排查题（14）

**13.1｜一条 SQL 昨天很快，今天突然变慢，你的排查步骤是什么？**
`关联：排障 / 执行计划`
**答**：先对比 `EXPLAIN`（type/key/rows 是否变了），再查统计信息是否过期、数据量是否突增、是否有新索引/DDL/发布、是否被锁或长事务阻塞、参数是否变了、缓存是否被刷掉。最后用 `optimizer_trace` 看优化器为什么改主意。

**13.2｜线上 CPU 突然 100%，怎么定位是不是 SQL 导致的？**
`关联：排障 / 监控`
**答**：`SHOW PROCESSLIST` 按 Time 排序找长查询；看 `performance_schema` digest 的 Top SQL；系统层 `top -H` 找热点线程，再对回 MySQL 线程；同时排除非 SQL 因素（备份、DDL、锁自旋）。先止血（kill/限流），再分析。

**13.3｜加了一个索引，结果另一条 SQL 变慢了，为什么？**
`关联：优化器 / 索引`
**答**：优化器可能为新索引估了更低的成本而改选它，但新索引对这个查询选择性差、回表更多；也可能是 index merge、统计信息变化、buffer pool 被新索引挤占、写放大。对比两条 SQL 加索引前后的 `EXPLAIN` 就能看出来。

**13.4｜优化器选错了索引，你有哪几种处理方式？各自的代价是什么？**
`关联：优化器 / 索引提示`
**答**：① `ANALYZE TABLE` 刷新统计（首选，无侵入）；② `FORCE INDEX`/`USE INDEX` 或 8.0 的 `NO_INDEX` hint（快，但数据变化后可能更差）；③ 改写 SQL/加更合适的索引；④ 删除误导它的冗余索引。前两种是止血，后两种是根治。

**13.5｜千万级大表要加一个字段，怎么做才不影响业务？**
`关联：DDL / 在线变更`
**答**：MySQL 8.0.12+ 支持 `ALGORITHM=INSTANT` 加列（8.0.29 起支持任意位置），只改元数据、秒级；不满足 INSTANT 时用 `INPLACE` 或 `gh-ost`/`pt-osc`，在低峰期、限流、监控主从延迟。

**13.6｜千万级大表要加索引，怎么做？主从延迟怎么控制？**
`关联：DDL / 复制`
**答**：`ALTER TABLE ... ADD INDEX ..., ALGORITHM=INPLACE, LOCK=NONE` 走 Online DDL；大表更稳的是 `gh-ost`/`pt-osc`（影子表 + 增量同步）。控制延迟：低峰执行、限流、分批、监控 `Seconds_Behind_Source`，必要时暂停。

**13.7｜什么情况下应该分库分表？分片键怎么选？**
`关联：分库分表`
**答**：单表数据量过大（千万到亿级）、写入/QPS 达到单机瓶颈、连接数/磁盘扛不住、备份恢复太慢。分片键要：高基数、分布均匀、大多数查询都带它、尽量避免跨分片 JOIN 和分布式事务（如 `user_id`、`order_id`）。

**13.8｜读写分离后读到旧数据，怎么解决？**
`关联：复制 / 一致性`
**答**：写后短时间内强制走主库（会话粘性）、半同步复制、用 GTID 等待从库追上、关键读走主库、缓存双删/延迟双删。业务上要区分"必须最新"和"可以最终一致"的读。

**13.9｜热点行更新（比如库存扣减）怎么优化？**
`关联：并发 / 热点`
**答**：把热点行拆成多行（库存分桶）再汇总、用队列串行化、Redis/内存扣减 + 异步落库、乐观锁重试、缩短事务、把非核心逻辑移出事务。目标是减少同一行的锁竞争。

**13.10｜大表 `COUNT(*)` 很慢，业务又必须要，怎么办？**
`关联：聚合 / 架构`
**答**：维护计数表/汇总表（写入时 +1/-1）、Redis 计数器、定时预聚合、或接受近似值（`SHOW TABLE STATUS`）。实时精确 `COUNT(*)` 在千万级以上必然贵，要从产品口径上解决。

**13.11｜要导出 500 万行数据到文件，怎么避免 OOM 和锁表？**
`关联：导出 / JDBC`
**答**：流式读（`setFetchSize(Integer.MIN_VALUE)` 或服务端游标），按主键分页，边读边写文件，不要 `List` 全装；用只读事务/一致性快照（`--single-transaction`），低峰执行，压缩输出。

**13.12｜主从延迟越来越大，可能有哪些原因？**
`关联：复制`
**答**：大事务/大表 DDL、从库单线程回放、表无主键导致 ROW 回放慢、从库负载高/磁盘慢、网络带宽、长查询占用从库、锁冲突。看 `SHOW REPLICA STATUS`、`performance_schema` 的复制线程状态。

**13.13｜数据倾斜（某个 user_id 订单特别多）会带来什么问题？**
`关联：数据分布 / 分片`
**答**：分片时热点集中到一个库/表，CPU/IO/锁都压在一台；查询该用户仍然慢；统计信息也容易失真。解决：分片键加盐、热点用户单独拆分、缓存、或按范围二次分片。

**13.14｜业务说"查询超时"，但从库看起来不忙，可能是什么原因？**
`关联：排障`
**答**：连接池耗尽/等待连接、网络/DNS/TLS 问题、应用 GC 停顿、代理层超时、锁等待（但从库指标不高）、结果集太大传输慢、客户端读得慢。要同时看应用指标和数据库 `PROCESSLIST`。

## 14. 追问链（面试官的第二层、第三层）

> 这些不是新题，是"你答完上一句后，他大概率接着问的"。每条链都要能连续答下去。

### 链 1：你说"我加了联合索引 `(user_id, create_time)`"

**14.1｜为什么不是 `(create_time, user_id)`？**
`关联：联合索引 / 列序`
**答**：查询是 `user_id` 等值 + `create_time` 排序。`user_id` 在前，等值定位后 `create_time` 天然有序，能直接消除 filesort；反过来 `create_time` 在前，`user_id` 只能在时间范围内过滤，排序用不上。

**14.2｜如果查询是 `WHERE user_id > 100 AND create_time = ...`，这个索引还能用吗？**
`关联：联合索引 / 范围`
**答**：只能用 `user_id` 做范围扫描，`create_time` 的有序性被范围打断，不能用于定位/排序，最多做 ICP 过滤。这种查询更适合 `(create_time, user_id)`，或者业务上改成等值条件。

**14.3｜优化器一定会选它吗？如果不选，你怎么验证？**
`关联：优化器`
**答**：不一定。用 `EXPLAIN` 看 `key`，用 `optimizer_trace` 看候选方案和成本；如果不选，检查统计信息、回表成本、是否被别的索引误导。必要时 `ANALYZE TABLE` 或临时 `FORCE INDEX` 验证。

**14.4｜这个索引对 `WHERE create_time = ...` 有用吗？**
`关联：最左前缀`
**答**：基本没用（除非走覆盖扫描）。`create_time` 是第二列，单独用它跳过了最左列 `user_id`，无法定位；如果查询只需要索引里的列，可能做全索引扫描，但通常不如全表。

### 链 2：你说"用 `EXPLAIN` 看执行计划"

**14.5｜`rows` 是怎么算出来的？**
`关联：统计信息`
**答**：等值/范围用 index dive 采样索引页估算；全表用表行数 × 条件选择性；JOIN 时乘以前一层的 `filtered`。本质是统计信息 + 假设，不是实际值。

**14.6｜为什么 `rows` 和实际扫描行数差很多？**
`关联：估算误差`
**答**：采样少、数据倾斜、多列相关性、统计过期、函数/表达式选择性估不准，都会让估算偏离。极端情况下差几个数量级。

**14.7｜你怎么拿到实际扫描行数？**
`关联：Handler_read`
**答**：同一条连接上，执行前后各取一次 `SHOW SESSION STATUS LIKE 'Handler_read%'`，把 7 个计数器求和取差值；它不是精确行数，但能反映真实读了多少行/索引项。

**14.8｜`EXPLAIN ANALYZE` 为什么不能随便用？**
`关联：EXPLAIN ANALYZE`
**答**：它会**真的执行** SQL，重查询会消耗资源、甚至锁数据；生产上可能拖垮实例。只在测试环境或确认只读、可控的查询上使用。

### 链 3：你说"用 Handler_read 做实测"

**14.9｜`Handler_read_rnd_next` 和 `Handler_read_next` 分别代表什么？**
`关联：Handler / 扫描`
**答**：`rnd_next` 是全表/顺序扫描读下一行；`next` 是沿索引顺序读下一项（范围扫描）。前者大通常说明全表扫，后者大说明索引范围扫得多。

**14.10｜这些计数器是会话级还是全局级？**
`关联：Handler`
**答**：`SHOW SESSION STATUS` 是当前会话，`SHOW GLOBAL STATUS` 是全局累计。做单条 SQL 测量必须用 SESSION，并且同一条连接，避免别的请求污染。

**14.11｜它包含哪些你可能不想要的操作？**
`关联：Handler`
**答**：包含索引查找、回表、排序临时表、内部临时表等所有 handler 调用，不只是"扫描行数"；所以它是近似指标，报告里要说明口径。

**14.12｜为什么它也不是"精确扫描行数"？**
`关联：Handler`
**答**：计数器统计的是 handler 层调用次数，不是返回行数；同一行可能被多次读（回表、排序、重复扫描），索引项读取也会计数。它反映 IO 工作量，不是行数。

### 链 4：你说"规则引擎可以扩展"

**14.13｜新增一条规则要改哪些文件？**
`关联：规则引擎`
**答**：新建一个实现 `Rule` 的类（`id/title/severity/check`），注册到规则列表（或 SPI/配置），加一个 fixture JSON + 单测。主流程 `RuleEngine` 不用改。

**14.14｜两条规则对同一张表给出不同建议，听谁的？**
`关联：规则冲突`
**答**：先按 severity 选主问题，再按"证据强度"（AST + 计划同时支持）排序；索引建议只保留一条，其余作为 `related` 说明。不能简单按规则注册顺序。

**14.15｜规则误报怎么发现？只靠单测够吗？**
`关联：规则质量`
**答**：不够。单测覆盖已知反例，但真实数据会有新写法；要拿真实慢日志跑回归，人工抽查误报，把新反例补进 fixture。报告里标注"建议需人工确认"是最后一道防线。

**14.16｜规则阈值写死在代码里，换环境怎么办？**
`关联：配置`
**答**：抽到配置文件/启动参数，按数据量给默认值和相对阈值（占表行数比例）；报告里记录用了哪个阈值，方便复现和调参。

### 链 5：你说"用 JSqlParser 解析 AST"

**14.17｜5.x 和 4.x 的 API 有什么区别？**
`关联：JSqlParser`
**答**：5.x 删了 `SelectBody`，`Select` 成基类，`PlainSelect` 直接继承；`SelectItem` 泛型化；访问器方法变成 `<S> T visit(X, S context)`。4.x 的 `getSelectBody()` 不能再用。

**14.18｜遇到解析不了的方言 SQL 怎么办？**
`关联：健壮性`
**答**：降级为"仅 EXPLAIN 诊断"，关掉依赖 AST 的规则，报告标注；批量模式跳过并记录，不中断整批。必要时给解析器加方言配置或预处理（去 hint/注释）。

**14.19｜子查询里的 WHERE 你怎么遍历？**
`关联：AST / 子查询`
**答**：从 `ParenthesedSelect` 取内层 `Select`，再 `instanceof PlainSelect` 拿 `getWhere()`，递归处理；`IN/EXISTS` 的右表达式同理。注意别重复遍历同一子树。

**14.20｜怎么防止解析器被恶意 SQL 拖垮？**
`关联：安全 / 解析`
**答**：限制 SQL 长度/嵌套深度、解析超时、在独立线程池里跑、限制并发；解析器本身也可能有性能问题（超长 `IN` 列表、深嵌套），入口就要拒绝。

### 链 6：你说"优化后耗时下降了 90%"

**14.21｜怎么测的？跑了几次？**
`关联：性能测量`
**答**：同一连接、预热 2 次、正式 3 次取中位数，记录 `Handler_read_*` 差异；加索引前后用同一套流程。不是跑一次就下结论。

**14.22｜缓存是热的还是冷的？**
`关联：缓存`
**答**：热的。预热后 buffer pool 里有数据和索引页，所以数字偏乐观；报告里注明"热缓存"，冷缓存要另测（重启/`FLUSH` 有风险，不建议生产做）。

**14.23｜数据量多大？和生产是一个量级吗？**
`关联：数据规模`
**答**：100 万订单 + 10 万用户，是本机实验规模，比生产小；结论是"在这个量级上有效"，不能直接外推。生产要重新测。

**14.24｜有没有哪条 SQL 优化后反而变慢？**
`关联：测量诚实性`
**答**：有。比如范围 + 排序那条，加了索引也没消除 filesort，提升很小；还有一条因为优化器改选索引，耗时略升。报告里保留并解释，比全是好消息可信。

### 链 7：你说"这个列区分度低，不建议建索引"

**14.25｜区分度怎么算的？**
`关联：选择性`
**答**：`COUNT(DISTINCT col) / COUNT(*)`；优先用 `information_schema.STATISTICS.CARDINALITY / TABLE_ROWS`，避免全表 `COUNT(DISTINCT)`；没有统计信息才采样。

**14.26｜多低算低？阈值哪来的？**
`关联：选择性`
**答**：经验上等值查询 < 10% 就要谨慎，< 1% 基本不值得单独建；但阈值取决于数据分布和查询（范围查询可以更低）。最终看优化器成本，不看单一数字。

**14.27｜低区分度列放进联合索引就有效吗？**
`关联：联合索引`
**答**：可以。放在高区分度等值列之后，它能进一步过滤且可能帮助覆盖/排序；单独建索引才没意义。顺序仍是"高区分度等值列在前"。

**14.28｜如果业务就是只查这个列呢？**
`关联：索引设计`
**答**：如果确实高频且返回行数少（比如 `status=3` 只占 1%），可以建；如果返回行数多，考虑汇总表、缓存、或把条件改成"状态 + 时间范围"来缩小扫描。不要为了"有索引"而建。

### 链 8：你说"用了连接池"

**14.29｜池子多大？为什么是这个数？**
`关联：HikariCP`
**答**：先按 `CPU 核数 × 2 + 磁盘数` 估一个上限（本机约 10–20），再压测看吞吐和等待时间；不是越大越好。还要保证所有实例的连接总数不超过数据库 `max_connections`。

**14.30｜连接泄漏怎么发现？**
`关联：连接池`
**答**：开 `leakDetectionThreshold` 打印借用栈，观察 `activeConnections` 是否持续顶满、请求是否都在等连接；代码上强制 `try-with-resources`，review 时重点看异常分支。

**14.31｜数据库重启后连接池里的旧连接怎么办？**
`关联：连接池`
**答**：Hikari 会检测失效连接并剔除，`maxLifetime` 也会主动淘汰；应用侧要有重试和健康检查。重启期间请求会失败，最好配合重试/降级，而不是假设池里都是好连接。

**14.32｜长事务占着连接会怎样？**
`关联：事务 / 连接池`
**答**：连接不归还，池子可用数下降，其他请求排队超时；同时 undo/锁/复制延迟都变差。要设事务超时、拆事务、监控长事务并告警。

## 15. 白板/手写题

**15.1｜画出 B+ 树的三层结构，标出聚簇索引和二级索引的叶子节点内容。**
`关联：B+ 树`
**答**：画三层：根（键 + 子页指针）→ 中间层（同上）→ 叶子（数据 + 双向链表）。聚簇索引叶子写"整行：id, user_id, amount, create_time…"；二级索引叶子写"索引列 + 主键：user_id, id"。旁边标一句：二级索引查非索引列要拿 id 回聚簇索引。

**15.2｜画一条 `SELECT ... WHERE a=? ORDER BY b` 的执行路径，标出回表发生在哪一步。**
`关联：执行路径 / 回表`
**答**：连接器 → 解析器 → 优化器（选 `(a,b)` 索引）→ 执行器 → InnoDB 在二级索引上定位 `a=?` 并按 b 顺序扫描 → 拿到主键 → **回表**到聚簇索引取整行 → 返回。若 SELECT 的列都在 `(a,b)` 里，则跳过回表（覆盖索引）。

**15.3｜手写 `(a,b,c)` 联合索引能命中的查询组合表（至少 8 种）。**
`关联：联合索引`
**答**：

| 查询条件 | 能否用索引 | 用到几列 |
|---|---|---|
| `a=?` | 能 | a |
| `a=? AND b=?` | 能 | a,b |
| `a=? AND b=? AND c=?` | 能 | a,b,c |
| `a=? AND b>?` | 能（range） | a,b |
| `a=? AND b=? AND c>?` | 能（range） | a,b,c |
| `a=? ORDER BY b` | 能（免排序） | a,b |
| `a=? AND b=? ORDER BY c` | 能（免排序） | a,b,c |
| `b=?` | 不能 | 0 |
| `b=? AND c=?` | 不能 | 0 |
| `a=? AND c=?` | 部分（a 定位，c 过滤/ICP） | a |

**15.4｜给一条 SQL，现场写出应该建的索引，并说明列序理由。**
`关联：索引设计`
**答**：以 `SELECT * FROM t_order WHERE user_id=? AND status=? ORDER BY create_time DESC LIMIT 20` 为例：建 `(user_id, status, create_time)`。`user_id`、`status` 是等值，按区分度 `user_id` 在前；`create_time` 排最后，等值前缀之后天然有序，消除 filesort。`SELECT *` 无法覆盖，接受回表。

**15.5｜给一个 `EXPLAIN` 输出，现场判断：驱动表是谁、有没有回表、有没有 filesort。**
`关联：执行计划`
**答**：看三处：① 第一行/`nested_loop` 第一个是驱动表；② 被驱动表的 `type=ref/eq_ref` 且有 `key` 说明走索引，`Extra` 没有 `Using index` 就要回表；③ `Extra` 有 `Using filesort` 表示额外排序，有 `Using temporary` 表示临时表。再结合 `rows` 和 `filtered` 判断扫描量。

**15.6｜手写一个规则类（实现 `Rule` 接口），判断"WHERE 列被函数包裹"。**
`关联：规则引擎 / AST`
**答**：

```java
public final class FunctionWrapRule implements Rule {
    public String id() { return "R03"; }
    public String title() { return "WHERE 列被函数包裹"; }
    public Severity severity() { return Severity.HIGH; }

    public List<Issue> check(QueryContext ctx) {
        List<Issue> out = new ArrayList<>();
        for (String col : ctx.features().getFunctionWrappedColumns()) {
            out.add(new Issue(id(), title(), severity(),
                    "函数包裹列: " + col,
                    "把函数移到常量侧，或建函数索引",
                    List.of(col)));
        }
        return out;
    }
}
```

**15.7｜手写 SQL：查每个城市订单总额 Top 10，并给出索引建议。**
`关联：SQL / 索引`
**答**：

```sql
SELECT u.city, SUM(o.amount) AS total
FROM t_order o
JOIN t_user u ON o.user_id = u.id
GROUP BY u.city
ORDER BY total DESC
LIMIT 10;
```

索引：`t_user(city)` 可减少驱动表扫描；`t_order(user_id, amount)` 做覆盖，避免回表。若数据量大，考虑按城市预聚合的汇总表。

**15.8｜手写 SQL：删除重复数据只保留 id 最小的一条。**
`关联：SQL / 去重`
**答**：

```sql
DELETE o FROM t_order o
JOIN (
  SELECT order_no, MIN(id) AS keep_id
  FROM t_order
  GROUP BY order_no
) d ON o.order_no = d.order_no AND o.id > d.keep_id;
```

先 `SELECT` 验证影响行数；大表分批删，避免长事务和锁表。

**15.9｜手写 SQL：统计连续 3 天有下单的用户。**
`关联：SQL / 窗口函数`
**答**：

```sql
SELECT DISTINCT user_id
FROM (
  SELECT user_id, d,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY d) AS rn
  FROM (SELECT DISTINCT user_id, DATE(create_time) AS d FROM t_order) x
) y
GROUP BY user_id, DATE_SUB(d, INTERVAL rn DAY)
HAVING COUNT(*) >= 3;
```

思路：连续日期减去行号会得到同一个分组键，再按组计数。

**15.10｜解释一段你项目里的代码（面试官会指着他感兴趣的那行问"这行为什么这么写"）。**
`关联：项目表达`
**答**：提前准备 3 段：① `ExplainParser.walk` 为什么递归（JOIN 的 `nested_loop`）；② 索引建议里为什么 `range` 之后不再加 `order` 列；③ `Benchmark` 为什么预热 + 中位数。每段都能说出"不这么写会错在哪"。

## 附录 A：周边技术快问（14）

**A.1｜Jackson 的 `readTree()` 和 `readValue()` 有什么区别？解析 EXPLAIN 时你为什么选树模型？**
`关联：Jackson / JSON`
**答**：`readValue` 绑定到固定 POJO；`readTree` 返回 `JsonNode` 树，字段可缺、可多、可动态。EXPLAIN 的层级随 JOIN/排序变化，用树递归遍历最稳，不需要为每种形状建类。

**A.2｜JSON 字段缺失、值为 `null`、类型不一致时，你的解析代码怎么不崩？**
`关联：Jackson / 健壮性`
**答**：用 `path()` 而不是 `get()`（缺失返回 `MissingNode`），`asLong(default)`/`asText(default)` 给默认值；先判 `isArray`/`isObject` 再遍历；对 `key` 这类可能是 `null` 的字段单独判 `isNull()`。

**A.3｜解析一个 1MB 的执行计划 JSON，有什么性能注意点？**
`关联：JSON / 性能`
**答**：不要反复 `toString()` 或深拷贝；流式/树模型只遍历一次；缓存解析结果；避免在循环里 `readTree` 同一段。1MB 对 Jackson 不算大，真正的瓶颈通常是数据库往返，不是解析。

**A.4｜为什么用 Jackson 而不是 Gson / fastjson？Jackson 常见的坑有哪些？**
`关联：JSON 库`
**答**：Jackson 生态成熟、Spring 默认、树模型和流式 API 都全。坑：未知字段默认报错（需 `FAIL_ON_UNKNOWN_PROPERTIES=false`）、日期/时区默认行为、`null` 与缺失字段区分、泛型反序列化要用 `TypeReference`。

**A.5｜`com.sun.net.httpserver.HttpServer` 的线程模型是什么？默认 executor 是什么？**
`关联：HttpServer`
**答**：它用 `Executor` 处理请求；不设置时是**单线程**（在创建线程里串行处理），一个慢请求会阻塞所有请求。所以必须 `setExecutor`。

**A.6｜为什么必须 `server.setExecutor(...)`？不设置会怎样？**
`关联：HttpServer`
**答**：默认实现是单线程，诊断一条慢 SQL 可能几秒，期间其他请求全部排队。设成固定线程池（如 8）并配合超时，才能并发服务。

**A.7｜你的 `/api/analyze` 怎么读 POST body？怎么处理 `Content-Type` 和超时？**
`关联：HTTP`
**答**：校验 `Content-Type: application/json`，限制 `Content-Length`，用 `readAllBytes()`（Java 9+）或限长流读取；解析失败返回 400；对执行加 `MAX_EXECUTION_TIME` 和请求超时，避免线程被占死。

**A.8｜一个公开的 JSON API，怎么防住超大请求、慢请求和恶意 SQL？**
`关联：安全`
**答**：限制 body 大小、SQL 长度、并发数；只允许 SELECT（AST 判断）；只读账号；`max_execution_time`；结果行数上限；错误信息脱敏；必要时加限流/鉴权。

**A.9｜SLF4J 和 Logback 是什么关系？为什么代码里只依赖 SLF4J API？**
`关联：日志`
**答**：SLF4J 是门面/API，Logback 是实现；代码只依赖门面，换实现（Log4j2）不用改代码。运行时通过 `StaticLoggerBinder`/ServiceLoader 绑定实现。

**A.10｜什么信息该打 INFO、什么该打 DEBUG？日志里能不能打完整 SQL 和参数？**
`关联：日志 / 安全`
**答**：INFO 打关键流程（开始诊断、耗时、规则命中数）；DEBUG 打细节（AST 特征、JSON 片段）。完整 SQL 和参数可能含敏感数据，生产要脱敏/截断，避免日志泄露和膨胀。

**A.11｜数据库地址、账号、密码放在哪？配置文件、环境变量、启动参数各自的风险是什么？**
`关联：配置 / 安全`
**答**：配置文件易误提交；环境变量可能被同机进程看到；启动参数会出现在 `ps` 里。生产用密钥管理/云 IAM，配置只放非敏感项，密码定期轮换、最小权限。

**A.12｜Windows 控制台输出中文乱码，你会从哪几个层面排查？**
`关联：编码`
**答**：源文件编码（UTF-8）、`javac -encoding`、JVM `file.encoding`/`stdout.encoding`、控制台代码页（`chcp 65001`）、日志文件编码。Maven 里设 `project.build.sourceEncoding=UTF-8`。

**A.13｜你的 HTTP 接口怎么区分 200 / 400 / 500？异常信息要不要原样返回？**
`关联：HTTP / 错误处理`
**答**：200 成功；400 参数/SQL 不合法（用户可修）；500 服务端异常。返回统一结构 `{code, message, data}`，异常只给摘要和 traceId，堆栈写日志，不回给前端。

**A.14｜如果要并发诊断 20 条 SQL，线程池怎么设计？怎么避免把数据库打爆？**
`关联：并发 / 连接池`
**答**：固定小线程池（如 4–8，和连接池上限匹配）、有界队列、`CallerRunsPolicy` 或快速失败；每条 SQL 加超时；限制同时执行的诊断数。并发度不能超过连接池可用连接数，否则全在等连接。
