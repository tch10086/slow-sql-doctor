## 1. 一句话与 30 秒版本

**一句话**：输入一条 SQL，输出"为什么慢 + 该建什么索引 + 加完能快多少"的可验证报告。

**30 秒版**：

> 线上慢 SQL 排查通常靠 DBA 手动 `EXPLAIN`，能看出没走索引，但很难快速回答"为什么"和"该建什么索引"。我做了个工具：用 JSqlParser 解析 AST 抽取查询特征，采集 `EXPLAIN FORMAT=JSON` 和 `Handler_read_*` 实测指标，通过 10 条规则识别全表扫描、索引失效、回表、filesort 等问题，再按"等值 → 范围 → 排序 → 覆盖"生成索引建议，并和 `information_schema` 里的现有索引比对，最后输出优化前后对比报告。在 100 万行数据上，Q08 从 254ms 降到 1ms 以内，扫描行数从 100 万降到 11。

## 3. 范围：做了什么、没做什么

### 做了（MVP）

- 单条 `SELECT` 的诊断：AST 特征 + EXPLAIN JSON + 规则 + 索引建议 + 报告；
- 16 条典型慢 SQL 的基线采集（`BaselineRunner`）；
- 10 条规则、31 个单测；
- 慢日志批量聚合（归一化 + 指纹 + 按总耗时排序）；
- CLI 入口 + Markdown/HTML 报告。

### 没做（主动写进 README）

- 子查询 / UNION / CTE / 窗口函数；
- Web 界面（CLI 足够演示，避免把时间花在 UI）；
- 自动执行 DDL（风险太高，只生成建议）；
- 生产级慢日志解析（字符串里带分号会误判）。

> 面试时主动说"我没做什么"，比被追问出来可信。

## 4. 技术选型与替代方案

| 选择 | 用来做什么 | 为什么 | 替代方案 / 代价 |
|---|---|---|---|
| Java 17 | 全部代码 | 最熟；JDBC/HikariCP 现成；强类型适合 AST 模型 | Python 开发快，但生态和打包不如 Java |
| JSqlParser 5.3 | SQL → AST | 纯 Java、无额外依赖、AST 模型直观 | Druid 偏连接池生态；Calcite 太重；ANTLR 自写文法成本高 |
| MySQL 8.0 | 被测库 | 支持 `EXPLAIN FORMAT=JSON`、函数索引、直方图 | 5.7 的 JSON 字段较少 |
| JDBC + HikariCP | 连接与执行 | 复用 JDBC 能力；连接池是简历点 | 原生 DriverManager 每次建连接太慢 |
| Jackson | 解析 EXPLAIN JSON | 树模型适合动态嵌套 | Gson 也可以；Jackson 生态更成熟 |
| JUnit 5 | 单测 | 参数化、fixture 方便 | 无 |
| Maven | 构建 | 标准、插件生态 | Gradle 更灵活，但没必要 |

## 5. 架构与数据流

```
SQL 文本
   │
   ├─► SqlAnalyzer (JSqlParser) ──► SqlFeatures
   │      tables / eq / range / join / order / group
   │      functionWrapped / leadingWildcard / or / cartesian / limit
   │
   ├─► ExplainCollector ──► EXPLAIN FORMAT=JSON + SHOW WARNINGS
   │      └─► ExplainParser (Jackson 递归) ──► ExplainPlan / TableAccess
   │
   ├─► TableMetaLoader ──► information_schema
   │      columns / indexes / cardinality / row count
   │
   ├─► RuleEngine ──► 10 条规则 ──► List<Issue>
   │
   ├─► IndexAdvisor ──► List<IndexSuggestion>
   │
   └─► ReportGenerator ──► Markdown + HTML
```

一次诊断的调用链：

```
Main
 └─ DiagnosisService.analyze
     ├─ SqlAnalyzer.analyze
     ├─ ExplainCollector.collect
     │   ├─ EXPLAIN FORMAT=JSON
     │   ├─ ExplainParser.parse
     │   └─ SHOW WARNINGS（改写后的 SQL）
     ├─ TableMetaLoader.load
     ├─ RuleEngine.analyze
     ├─ IndexAdvisor.advise
     └─ Benchmark.measure（笛卡尔积跳过）
```

## 6. 完整构建过程（按阶段讲）

### 阶段 0：环境与数据（D0–D2）

**做什么**

- JDK 21（编译目标 17）、Maven、MySQL 8.0；
- 建库 `slow_sql_lab`，建两个账号：`sqlquery`（读写 + DDL）、`sqlquery_ro`（只读）；
- 建表：
  - `t_user` 10 万行，`city`、`username` 有索引；
  - `t_order` 100 万行，`user_id`、`order_no` 有索引；`create_time` **故意不建索引**，`status` 低区分度；
- 造数：80% 订单分给 2 万热用户（人均约 40 单），20% 分给 8 万冷用户（人均 2–3 单）。

**为什么这样设计**

- 没有 100 万行，测不出扫描行数和索引收益；
- 均匀分布测不出"选择性"，必须让 `user_id` 有倾斜；
- 预留 `create_time` 无索引、`status` 低区分度，才能演示全表扫描、filesort、临时表。

**验收**

```sql
SELECT COUNT(*) FROM t_order;                             -- 1000000
SELECT COUNT(DISTINCT user_id) / COUNT(*) FROM t_order;   -- ≈ 0.09
```

> 一开始我把 `DATE(create_time)='2026-10-01'` 当示例，结果数据范围是 2025-10-01 到 2026-09-30，查询返回 0 行。后来改成 `2026-03-01`，才测出 2725 行。这个小坑说明：**造数范围要和示例 SQL 对得上**。

### 阶段 1：最小闭环——先拿到 EXPLAIN JSON（D3–D4）

**做什么**

- `AppConfig`：读环境变量，默认连本地库；
- `Db`：HikariCP 连接池；
- `ExplainCollector`：执行 `EXPLAIN FORMAT=JSON`，再 `SHOW WARNINGS` 拿优化器改写后的 SQL；
- `ExplainParser`：Jackson 递归遍历，遇到 `table` 节点就解析，遇到 `using_filesort` / `using_temporary_table` 就打标记。

**关键点**

- 单表时 `table` 在 `query_block` 下；JOIN 时在 `nested_loop` 数组里；排序/分组时在 `ordering_operation` / `grouping_operation` 里。所以**不能按固定路径取**。
- `rows` 是估算，不能当证据；后面补 `Handler_read_*` 实测。

**验收**

```bash
java -jar target/slow-sql-doctor-1.0.0.jar -v "SELECT ..."
```

能看到原始 JSON、`type/key/rows/used_columns`、耗时和 Handler。

### 阶段 2：AST 特征抽取（D5）

**做什么**

- `SqlAnalyzer` 用 JSqlParser 解析单条 `PlainSelect`；
- 抽取：
  - 表与别名映射；
  - SELECT 列 / `SELECT *`；
  - WHERE 顶层 AND 的合取项，分成等值、范围、LIKE、IS NULL；
  - JOIN 的 ON 列（两侧都记录，索引建议阶段再按执行计划取舍）；
  - ORDER BY / GROUP BY；
  - 函数包裹列（`DATE(create_time)`、`SUBSTRING(order_no,1,3)`）；
  - 前导通配 `LIKE '%x'`；
  - OR、笛卡尔积、LIMIT offset；
  - 列 vs 字面量类型（判断隐式转换方向）。

**遇到的坑**

JSqlParser 5.3 把 `a IN (1,2) AND b > 3` 解析成"`IN` 的右表达式是一个 `AndExpression`"，导致范围条件丢失。我在 `flattenAnd` 里做了 AST 修复：把 `IN` 的右表达式还原成列表，再把 AND 右侧拆成独立合取项。这个问题写进 README 的已知局限/版本说明，面试时是一个很好的"你读过解析器行为"的例子。

**验收**：9 个 `SqlAnalyzerTest` 用例，覆盖 Q01/Q02/Q03/Q04/Q09/Q11/Q12/Q13/Q14。

### 阶段 3：规则引擎（D6–D7）

**做什么**

- `Rule` 接口：`id/title/severity/check`；
- 10 条规则，每条一个类；
- `RuleEngine` 遍历规则、按 `(ruleId, columns)` 去重、按严重度排序；单条规则抛异常只记日志，不影响整体；
- 规则只报"AST + 执行计划同时有证据"的问题。

**10 条规则**

R01 全表扫描、R02 索引未命中、R03 函数失效、R04 隐式转换、R05 前导通配、R06 OR 失效、R07 回表、R08 filesort/临时表、R09 深分页、R10 笛卡尔积。

**怎么防误报**

- 单测覆盖正例 / 反例 / 边界；
- 典型反例：数字列 = 字符串**不**失效（转的是常量），只有字符串列 = 数字才失效；
- 报告里标注"建议需人工确认"；
- 真实数据跑一遍，把误报补进测试。

### 阶段 4：索引建议（D8）

**做什么**

- `TableMetaLoader` 从 `information_schema` 读表行数、列类型、索引列序、Cardinality；
- `IndexAdvisor`：
  1. JOIN 列 + 等值列，按选择性降序；
  2. 范围列最多 1 个；
  3. 有范围列时不追加排序列；
  4. SELECT 列能覆盖时追加为覆盖索引（最多补 3 列）；
  5. 候选是现有索引前缀 → 跳过；现有索引是候选前缀 → 提示可能冗余；
  6. 生成 `ALTER TABLE` + 理由 + 风险，不执行。

**遇到的坑**

- EXPLAIN 里 JOIN 的 `table_name` 是别名（`u` / `o`），直接拿它查 `information_schema` 查不到。解决：`ExplainPlan.remapTableNames` 用 AST 的别名映射还原真实表名。
- 索引建议一开始对驱动表也加 JOIN 列，导致建议 `(id, city)` 这种废话。解决：按执行计划顺序，只给被驱动表加 JOIN 关联列。

### 阶段 5：基准测量与报告（D9–D10）

**做什么**

- `Benchmark`：预热 2 次，正式 3 次，取中位数；每次记录 `Handler_read_*` 差值；
- `ReportGenerator`：Markdown + HTML，包含 SQL、执行计划、问题、建议、理由/风险、实测、复现命令、已知局限；
- `BaselineRunner`：对 16 条 SQL 批量采集，写 `docs/baseline.csv`；Q12 只 EXPLAIN。

**怎么保证数字可信**

- 同一连接、同一参数；
- 预热把数据和索引页读进 buffer pool；
- 中位数抗抖动；
- 报告里写明"热缓存、单连接、无并发"；
- 同时给 `rows`（估算）和 `Handler`（实测），不混用。

### 阶段 6：慢日志批量（D11–D12）

**做什么**

- `SlowLogParser`：按 `# Time` / `# Query_time` / 分号切分，解析 FILE 格式；
- `SlowLogAggregator`：字面量 → `?`、IN 列表折叠、SHA-256 指纹、按总耗时排序；
- CLI：`slowlog <file>` 打印 Top 20。

**局限**：字符串/注释里带分号会误判；生产级要用 `pt-query-digest` 或 `performance_schema` digest。

### 阶段 7：测试与交付（D13–D14）

- 31 个 JUnit 测试：解析器 5、AST 9、规则 8、索引建议 4、报告 2、慢日志 2、冒烟 1；
- README：架构、快速开始、规则表、效果、局限；
- Git：分阶段提交，README 里能一条命令跑起来。

## 7. 关键设计决策（面试最容易被问）

| 问题 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 为什么不用正则解析 SQL | AST | 函数、OR、别名、子查询正则不可靠 | 引入 JSqlParser，学习 API |
| 为什么用 JSON EXPLAIN | `FORMAT=JSON` | 能拿到 STRUCT 层级、used_columns、cost | 解析复杂，要递归 |
| 为什么同时看 Handler | 实测计数 | `rows` 是估算，不能当证据 | 只能会话级、含内部操作 |
| 为什么规则用接口 | 独立类 | 可单测、可开关、可解释 | 类变多 |
| 为什么建议不自动执行 | 只生成 DDL | DDL 锁元数据、影响写入 | 需要人工确认 |
| 为什么只支持 PlainSelect | 明确边界 | 子查询/UNION 复杂度高，先做闭环 | 覆盖面小，写进局限 |

## 8. 实测数据（写简历直接用）

数据：`t_order` 100 万、`t_user` 10 万；热缓存、单连接、3 次中位数。

| 场景 | 优化前 | 优化后 | 手段 |
|---|---:|---:|---|
| Q08 排序 + 全表扫描 | 254 ms / 1,000,003 Handler | 0 ms / 11 | 加 `create_time` 索引 |
| Q02 `DATE(create_time)` | 232 ms / 1,000,003 | 8 ms / 2,726 | 改写为范围 + 索引 |
| Q03 `order_no = 数字` | 395 ms / 1,000,003 | 0 ms / 2 | 字面量加引号，走已有索引 |
| Q01 等值 + 排序 | 0 ms / 41 | 0 ms / 20 | `(user_id, create_time)` 消除 filesort |
| Q14 `GROUP BY status` | 206 ms / 2,000,010 | 98 ms / 1,000,002 | `status` 索引消除临时表 |

> 简历上写"Q08 从 254ms 降到 1ms 以内，Handler 从 100 万降到 11"，比笼统的"性能提升 90%"可信。

## 9. 三个可以讲的故事

### 故事 1：`rows` 不是证据

最初报告只写 `EXPLAIN rows=997376`，面试官追问"这是实际扫描行数吗？"我答不上来。后来补了 `Handler_read_*` 前后差值，报告里同时给估算和实测，并注明口径。**这件事让我理解了优化器统计信息和真实执行的区别。**

### 故事 2：JSqlParser 的 IN + AND 怪癖

`user_id IN (1,2) AND create_time >= ...` 解析后范围条件丢了。打印 AST 才发现，`IN` 的右表达式被解析成了 `AndExpression`。我在 `flattenAnd` 里做了修复，并补了 Q13 的测试。**结论：解析器不是黑盒，遇到怪行为要打印 AST。**

### 故事 3：EXPLAIN 的别名

JOIN 查询的 `table_name` 是 `u` / `o`，不是 `t_user` / `t_order`，导致元数据查不到、索引建议为空。后来加了别名映射，并调整索引建议只给被驱动表加 JOIN 列。**结论：执行计划和 AST 要结合起来用。**

## 10. 面试讲述脚本

### 3 分钟版

- **0:00–0:30 问题**：慢 SQL 排查靠人肉 EXPLAIN，知道没走索引，但不知道该建什么、建完有没有效。
- **0:30–1:30 做法**：JSqlParser 抽 AST 特征 + EXPLAIN JSON + Handler 实测 → 10 条规则 → 索引建议（等值/范围/排序/覆盖，比对 information_schema）→ 前后 3 次中位数报告。
- **1:30–2:30 难点**：`rows` 是估算，用 Handler 补实测；JSqlParser 的 IN+AND 解析怪癖；JOIN 别名映射。
- **2:30–3:00 数据与局限**：100 万行、16 条 SQL、31 个测试；Q08 254ms→<1ms，Handler 100 万→11；只支持 PlainSelect，子查询/UNION 没做。

### 10 分钟版

按第 6 节"完整构建过程"讲：数据 → 最小闭环 → AST → 规则 → 建议 → 测量 → 报告 → 批量 → 测试。每段讲"做什么、为什么、遇到什么坑、怎么验收"。

## 11. 简历写法（4 条）

> **MySQL 慢 SQL 诊断与索引优化工具** ｜ 个人项目 ｜ 2026.09–2026.10
> - 基于 JSqlParser 5.3 解析 SQL AST，抽取等值/范围/JOIN/排序/函数/通配等特征，结合 `EXPLAIN FORMAT=JSON` 与 `Handler_read_*` 实测指标，实现 10 条规则识别全表扫描、索引失效、回表、filesort、深分页等问题。
